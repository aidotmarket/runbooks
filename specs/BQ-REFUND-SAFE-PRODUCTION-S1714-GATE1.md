## 2. Required behavior

A full validated refund converges order, linked human or agent transaction, access rights, finance Payment/Refund/journal and event processing to one consistent result. Replayed, reordered or concurrent notifications do not double-debit agent spend or duplicate journals/events. A finance or outer-session failure remains retryable and must never be acknowledged as successful completion. Missing async session must fail, not skip finance.

Direct settlement and scheduler execution share one authoritative eligibility policy: confirmed transaction, unique consistent linked order, genuine elapsed hold, and no full refund, revocation, dispute or pending refund operation that makes payout unsafe. Invalid/missing contradictory state fails closed with durable audited refusal. The direct execution path rechecks eligibility under the concurrency protocol immediately before provider dispatch; scheduler filtering alone is insufficient. Positive eligible payments still settle exactly once under Stripe idempotency.

Refund/confirmation/revocation and payout concurrency needs a documented common lock order and durable operation state. A read-check followed by unlocked network transfer is inadequate. Specify the point at which payout ownership is reserved, how refund/revoke competes with that reservation, how crash-after-provider-success is reconciled without duplicate Transfer, and what happens if provider payout won before refund arrived. Never claim database rollback undoes a Stripe call. Late externally initiated refunds must be reconciled/audited without inventing automatic Transfer reversal authority or silently pretending no payout occurred. Gate2 must enumerate every participating writer and call path; guard only in settlement_service is not enough if another writer races it.

Validate provider refund identities, amount, currency, ownership and payment binding. Do not invent fallback refund identities or take an arbitrary first element from a truncated refund collection. For cumulative/multiple partial refunds, specify per-refund identity and monotonic aggregate semantics sufficient to preserve existing partial-refund behavior and prevent double adjustment. No broad credit-pack redesign. Full-refund production proof cannot be satisfied by synthetic allowlisting that hides a defective normal handler.

**Revocation policy.** Apply the stricter original settlement-exclusion requirement to ALL revoked orders, including bare access revocation, not only refund-linked revocation. A revoked purchased right cannot remain a newly eligible payout under this release contract. Preserve already completed Transfers as historical facts; no automatic reversal. CC M1's proposed bare-revoked-but-pays case would contradict the explicit original refunded/revoked exclusion and GLM's negative revoked case, so it is not selected. Add positive unrevoked payout and negative bare-revoked refusal, then negative full-refund refusal. Any business reason for retaining payout despite revocation must be a separately reviewed policy, not inferred by a reviewer or hidden fixture exception.

**Refund model.** Select a durable admission checkpoint followed by one atomic async effects transaction, not a general rewrite of the whole webhook dispatcher. After signature/scope validation, the existing sync event path commits a retryable refund-pending admission record and releases its transaction before async processing. No sync row lock remains across the async session. Resolve authoritative provider refund objects with complete pagination outside database locks; validate immutable charge/payment/refund bindings and all succeeded refund amounts. Use unique real provider refund IDs and reject synthetic fallback IDs. Pending/failed/canceled refunds have explicit non-applied states; only succeeded deltas affect finance/access/spend. Missing/truncated/inconsistent provider results remain retryable failures.

The async effects transaction claims the event, acquires the common order then linked-transaction lock, then locks finance Payment and sorted per-refund records. It validates all existing phase records, applies each succeeded refund once, writes its unique journal/agent-spend delta marker and associated order/transaction/access state atomically, and records phase completion. Event completion is acknowledged only after this commit; a crash before final acknowledgment replays the validated committed effects without reapplication. The outer sync error path must preserve retryable state, never overwrite a completed effect as absent; finally:break and missing-session success are forbidden on this path. Gate2 must prove this lock order against the actual BillingService stripe-event lock and every caller, not merely restate it. Existing event IDs may differ for the same per-refund identity. Provider aggregate and the complete succeeded-refund ledger must agree; a stale notification may trigger a newer authoritative read but must not decrease the aggregate or overwrite newer outcomes.

**Payout reservation.** Select one shared durable order-bound money-operation authority used by transaction settlement, legacy order payout, and participating refund/revoke/confirm writers. Lock order is order row before linked transaction, followed by operation/payment/refund rows in deterministic order. Eligibility and durable dispatch reservation are committed before external I/O; no database lock held across Stripe. States must distinguish reserved-but-not-dispatched, dispatching/unknown, succeeded, rejected/canceled and reconciliation-required. A competing local refund/revoke before dispatch cancels eligibility; after dispatch ownership it records an audit/reconciliation outcome and must not falsely certify that no Transfer occurred. Once dispatch may have occurred, timeout/lease expiry alone can NEVER authorize a new Transfer identity or reset ownership. Reconcile using the original provider identity/idempotency request and exact amount/currency/destination/group; preserve indefinite uncertainty rather than duplicate money movement. Gate2 must name the actual supported Stripe retrieval/list mechanism: an idempotency key is not by itself a GET endpoint. Query complete provider results; multiple or contradictory matches fail closed. Existing stable settle_<tx_number> identity must not change on retry.

A final provider refund read before dispatch reduces stale-state exposure but is not atomic with Transfer. Therefore the guarantee is: no locally admitted refund/revocation is bypassed by a competing local payout; external refund arriving after payout reservation/dispatch is detected, classified and reconciled as a post-payout exception, never reported as prevented or auto-reversed. Gate2 must distinguish pre-dispatch cancellation, uncertain provider state and known provider payout before late refund. No new unreviewed refund/Transfer-reversal operation is added.
