## 1. The defect, as the Council established it

A seller with a live verified preview moves hosting (or changes anything that touches `listings`, `listing_versions` or `listing_summary_sources`). The triggers `invalidate_listing_summary` / `invalidate_listing_summary_source` (`alembic/versions/20260915_002:20-55`) set the summary record to `invalidated` and null its approval/disclosure pointers; the trigger `invalidate_preview_summary` (`20260917_003:55-61`) then sets `listing_preview_disclosure_heads.eligible=false` on **any** update of `listing_summary_records`. AIM Data's `transport.ensure_summary()` (`preview_marketplace_transport.py:136-157`) sees `state != approved` and `POST … /at-a-glance/approve` with `sample_decision: "none"` (`listing_summary.py:514,570,575`) **before** allocating the replacement candidate. That approval commits a new P1 disclosure that no longer matches the previous preview's binding, so `current_manifest()` (`app/services/listing_preview_projection.py:158-205`) returns no manifest and the public manifest 404s. The later `stale_source_revision` (AIM Data never sent `previous_commitment_id`) only stops the replacement. Net effect: a failed refresh leaves the seller with less than before. Also: the AIM Data UI "Retire previous package" button issues a live withdrawal (`app/routers/preview_builds.py:231`).

Council Gate 3 findings to discharge (all three verdicts): (F-A, HIGH, GLM) the prior verified preview must stay eligible until the replacement is atomically accepted, or the destructive transition must be staged; (F-B, HIGH, Gemini / MEDIUM, GLM) the backend's typed error body must stay `{"detail": …}`-compatible for the AIM Data client (or carry both `detail` and `code`), with a contract test; (F-C, MEDIUM, all three) only `stale_source_revision` may map to 409; signing-availability, checkpoint/log-integrity and unexpected append failures stay 503 with a correlation id; (F-D, MEDIUM, DeepSeek/Gemini) an end-to-end regression that fires the real triggers, runs the refresh with `previous_commitment_id`, and asserts `current_manifest` non-null and `head.eligible=true` afterwards, capturing state after every boundary (hosting move, GET preview, P1 approve, candidate allocation, submit failure); (F-E, MEDIUM per Gemini, LOW per GLM/DeepSeek) uniform rollback treatment on the candidate and regenerate routes.

## 2. Design (the invariant)

**I-1. A source change marks the live preview stale; it never removes it.** The trigger `invalidate_preview_summary` (`20260917_003:55-61`) stops flipping `eligible`. A new column `listing_preview_disclosure_heads.stale_since timestamptz NULL` is set **monotonically**: `SET stale_since = COALESCE(stale_since, now())` — the trigger fires on every `listing_summary_records` update (including the later P1 re-approval) and must not move the timestamp. `eligible` changes only by an explicit decision: an accepted replacement (`decide_preview`, `listing_preview_disclosure.py:325`) or an explicit withdrawal. The summary triggers of `20260915_002:20-55` are unchanged: the summary still becomes `invalidated` with null pointers, which is correct for the summary.

**I-2. The public manifest serves the stale head from immutable evidence.** `current_manifest` lives in `app/services/listing_preview_projection.py:158-261` (not in `listing_preview_disclosure.py`; r1 misattributed it). Today it requires the listing's `current_dataset_commitment_id` to equal the event's commitment and the live summary record to be `approved` with matching pointers (`:177-180`), the source revision, hashes, content revision and version to match (`:193-202`), and `revalidate_release` to pass (`:237-248`), so after a source change it returns `None` and `public.py:914-916` 404s. Change: when `head.eligible` is true **and** `head.stale_since` is not null, take a **stale-read branch** that builds the manifest from the immutable event data (`event.request`, `event.manifest`, `event.source_anchor`).

Skipped on the stale branch (they describe the *current* summary/source, which has legitimately moved): `record.state == "approved"` and the approval/disclosure pointer equality (`:179-180`), `listing.current_dataset_commitment_id == binding.commitment_id` (`:178`; the stale preview is served for its *old* commitment, which `source_stale` discloses), the source-revision/hash/render/content/version equalities (`:193-202`), and `revalidate_release` (call at `:237-248`; helper `:105-155`), which is replaced by an immutable-only recheck: `head.eligible`, `event.decision == "approve"`, `binding.sample_decision == "approved"`, `event.manifest is not None`, and `listing.status in ("published", "unlisted")` — the same status set the route allows today (`:177`, `listing_enrichment.py:91-95`, `tests/test_listing_summary_signed_payload.py:45-70`); any other status, a withdrawn head, or a listing with no head → `None`. No visibility policy changes.

Retained on the stale branch, unchanged — the complete verifier chain, fail-closed (`None` on any failure, `:250-261`): stored-request schema validation and signer/key trust (current signer authority, trusted key id, key equality; `:206-218`), `verify_authenticated_request` (platform envelope, request binding, seller disclosure signature, commitment signature, proof signatures, signer evidence; `:220`), `verify_checkpoint` and `verify_log_evidence` (`:234-235`), `ListingPreviewManifest.model_validate` (`:236`), and the independent P1 freshness expiry (`:184-191`).

The response carries an **unsigned overlay** on `ListingPreviewManifest` (`app/schemas/listing_preview.py:373`, a closed WireModel — add the fields there): `source_stale: bool` and `source_stale_since: datetime | None`. These names are distinct from the existing top-level `stale` (`listing_preview_projection.py:44-46`, which means *freshness* staleness) and are **not** added to `PlatformEnvelope` (`listing_preview.py:314-321`), so `platform_envelope_bytes` (`preview_signing.py:105-118`) and every stored event, seller signature and manifest stay byte-identical. The frontend listing page shows a "sample predates the current version (since <date>)" notice when `source_stale` is true. JSON-LD/agent exposure of the two fields is **out of scope** for this amendment (no named files; the agent surface reads the same manifest and will see the fields when it is next touched).

**I-3. P1 stays as it is; no carry-forward.** `POST /at-a-glance/approve` keeps `sample_decision = 'none'` (`ck_listing_summary_no_sample`, `20260915_002:112`); AIM Data's `ensure_summary()` call is unchanged and is never refused. r1's carry-forward/refusal rule (`preview_carry_forward_required`) is withdrawn: with I-1 and I-2 the P1 re-approval no longer removes the preview, and the head's own binding already carries the real sample decision. No CHECK migration, no new refusal code.

**I-4. Replacement is atomic.** `submit` (backend `build/s1732-preview-refresh-atomic` keeps its explicit rollback) accepts the replacement only when `previous_commitment_id` equals the head's current commitment; on acceptance it updates the head (event, commitment, `eligible=true`, `stale_since=NULL`) and appends to the transparency log in one transaction; on any failure nothing about the prior preview changes. AIM Data sends `previous_commitment_id=prior["commitment_id"]` (aim-data `6b702e5d`, one line, already correct).

**I-5. Error wire format and exhaustive status map (F-B, F-C).** Body: `{"detail": "<code>", "code": "<code>", "correlation_id": "<id>"}` — `detail` **equals the code**, so the current AIM Data client (keyed on `detail` at `aim-data@6b702e5d:app/services/preview_marketplace_transport.py:94-97`; messages at `:16-34`) keeps its typed mapping in either deploy order; a later client reads `code`. Status is an explicit, exhaustive registry in `app/api/v1/preview_route.py` (`_typed_error_code` / `_typed_error_status`; branch `233c23ad:16-66`), one row per emitted code, matching the status each raise site emits today unless a deliberate change is listed; no type-derived status; a chunk B fixture (`tests/test_listing_preview_http.py::test_error_registry_exhaustive`) parses these six files with `ast` — `app/services/listing_preview_disclosure.py`, `app/services/listing_preview_projection.py`, `app/services/listing_summary.py`, `app/services/transparency_log_service.py`, `app/utils/preview_signing.py`, `app/api/v1/preview_route.py` — collecting the first string argument of every `fail(...)`, `SigningError(...)`, `TransparencyAppendError(...)` and `HTTPException(...)` call, whitelists the two human details in the Exempt row, and fails if that set and the registry differ in either direction. The Gate 3 sentence "only `stale_source_revision` may map to 409" is superseded by this table: 409 is the class of client/state conflicts a refresh can resolve, of which `stale_source_revision` is one.

`_SAFE_SIGNING_ERROR_CODES` on the branch currently lets `checkpoint_signature_invalid` cross as 422 — it moves to 503. `transparency_log_service.py:384-395` keeps converting unexpected append failures to `transparency_append_failed` (503). AIM Data's `REFUSAL_MESSAGES` gains a row for every 409/413/422 code above that it lacks, with a seller-readable message.

**I-6. UI withdrawal is deliberate.** "Retire previous package" in AIM Data becomes a two-step confirm that states the public preview will disappear until a replacement is accepted; it calls the same withdrawal as today (`app/routers/preview_builds.py:231`). No withdrawal from any refresh path.

**I-7. Rollback uniformity (Gemini Gate 3 Finding 3, MEDIUM).** Candidate allocation (`allocate_candidate`, `listing_preview_disclosure.py:113-145`, insert-only) and the regenerate/approve summary routes get the same explicit rollback wrapper as submit, so behaviour under commit-on-exit session owners and cancellation is identical across the routes.

**I-8. Rollback of the change itself is forward-only.** Downgrading the trigger does not restore summary state, and deploying the old projection against a head that has entered the stale state reproduces the 404 with no further source change. The migration therefore has **no downgrade** for the trigger function (it raises with the recovery text), and `stale_since` is nullable so the old code ignores it. Operational recovery if the projection must be rolled back: the runbook documents it as "sellers with a stale head lose the public preview until they re-attest", and chunk D's test proves that statement. No feature flag: I-1 is the fix for all listings.

Out of scope: a new staged-candidate endpoint or state machine (GLM/DeepSeek BETTER); multi-version preview history; any change to the disclosure signing format, `PlatformEnvelope` or the D0 manifest.

## 6. Chunk D amendment note — defect #11 (S1735, Gate 3 r1)

The seller re-walk on aim-data v1.25.4-rc.1 exposed a second defect on the same path: a chained refresh submit for a listing whose head was ineligible with NULL `stale_since` failed 503 `transparency_append_failed`. Root cause (GLM r1, confirmed): a hosting move re-attests the SAME seller dataset version, and `uq_dataset_commitments_listing_version` allowed only one commitment per `(listing_id, seller_dataset_version)`; the IntegrityError was swallowed by the generic handler.

Contract change (binding, extends §2): repeated immutable commitments for one seller dataset version are permitted only as re-attestations of the SAME dataset content — identical `schema_digest`, `dataset_merkle_root` and `leaf_count` as the latest commitment for that `(listing_id, seller_dataset_version)`. Changed content must carry a new `seller_dataset_version`; otherwise the append refuses with typed 409 `dataset_version_content_mismatch` (in the `preview_route.py` registry). The check runs in `append_commitment` under the existing per-listing advisory lock; there is intentionally no replacement DB uniqueness constraint (any key that also distinguished the commitment would be vacuous). Migration `s1294_same_content_reattest` (forward-only) drops the old constraint. The swallowed-exception log carries the exception class name and traceback only, never SQL statement text or bound values. AIM Data's user-facing message row for the new code is deferred to a later chunk.
