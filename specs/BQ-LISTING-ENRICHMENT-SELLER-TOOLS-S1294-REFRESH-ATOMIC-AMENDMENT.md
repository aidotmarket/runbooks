## 1. The defect, as the Council established it

A seller with a live verified preview moves hosting (or changes anything that touches `listings`, `listing_versions` or `listing_summary_sources`). The triggers `invalidate_listing_summary` / `invalidate_listing_summary_source` (`alembic/versions/20260915_002:20-55`) set the summary record to `invalidated` and null its approval/disclosure pointers; the trigger `invalidate_preview_summary` (`20260917_003:55-61`) then sets `listing_preview_disclosure_heads.eligible=false` on **any** update of `listing_summary_records`. AIM Data's `transport.ensure_summary()` (`preview_marketplace_transport.py:136-157`) sees `state != approved` and `POST … /at-a-glance/approve` with `sample_decision: "none"` (`listing_summary.py:514,570,575`) **before** allocating the replacement candidate. That approval commits a new P1 disclosure that no longer matches the previous preview's binding, so `current_manifest()` (`listing_preview_disclosure.py:284-318`) returns no manifest and the public manifest 404s. The later `stale_source_revision` (AIM Data never sent `previous_commitment_id`) only stops the replacement. Net effect: a failed refresh leaves the seller with less than before. Also: the AIM Data UI "Retire previous package" button issues a live withdrawal (`app/routers/preview_builds.py:231`).

Council findings to discharge (all three verdicts): (F-A, HIGH, GLM) the prior verified preview must stay eligible until the replacement is atomically accepted, or the destructive transition must be staged; (F-B, HIGH, Gemini / MEDIUM, GLM) the backend's typed error body must stay `{"detail": …}`-compatible for the AIM Data client (or carry both `detail` and `code`), with a contract test; (F-C, MEDIUM, all three) only `stale_source_revision` may map to 409; signing-availability, checkpoint/log-integrity and unexpected append failures stay 503 with a correlation id; (F-D, MEDIUM, DeepSeek/Gemini) an end-to-end regression that fires the real triggers, runs the refresh with `previous_commitment_id`, and asserts `current_manifest` non-null and `head.eligible=true` afterwards, capturing state after every boundary (hosting move, GET preview, P1 approve, candidate allocation, submit failure); (F-E, LOW) uniform rollback treatment on the candidate route.

## 2. Design (the invariant)

**I-1. A source change marks the live preview stale; it never removes it.** `invalidate_preview_summary` stops flipping `eligible`. Instead a new column `listing_preview_disclosure_heads.stale_since timestamptz NULL` is set. The public manifest keeps serving the last accepted preview with `"stale": true` and `stale_since` in the platform envelope so a buyer (and an agent) can see the sample predates the current version. `eligible` changes only by an explicit decision: an accepted replacement (`decide_preview`, `listing_preview_disclosure.py:325`) or an explicit withdrawal.

**I-2. `ensure_summary` never downgrades a preview-enabled listing.** The `POST /at-a-glance/approve` path (`listing_summary.py:514-575`) carries forward the preview's `sample_decision` and the previous disclosure's binding fields when the listing has a head with `eligible=true`: the re-approval is a *carry-forward approval* (`sample_decision` = the head's current value, `supersedes_id` = the invalidated approval). A request that would set `sample_decision: "none"` on a listing with an eligible head is refused with 409 `preview_carry_forward_required` unless it carries `withdraw_preview: true`. AIM Data's `ensure_summary()` does not change its call; the server does the right thing.

**I-3. Replacement is atomic.** `submit` (backend `build/s1732-preview-refresh-atomic` keeps its explicit rollback) accepts the replacement only when `previous_commitment_id` equals the head's current commitment; on acceptance it updates the head (event, commitment, `eligible=true`, `stale_since=NULL`) and appends to the transparency log in one transaction; on any failure nothing about the prior preview changes. AIM Data sends `previous_commitment_id=prior["commitment_id"]` (aim-data `6b702e5d`, one line, already correct).

**I-4. Error taxonomy (F-B, F-C).** Backend response body for typed failures is `{"detail": "<human message>", "code": "<code>", "correlation_id": "<id>"}` so the current AIM Data client (`preview_marketplace_transport.py:16-34`, keyed on `detail`) keeps working and a later client can key on `code`. Status mapping is an explicit allowlist, not type-derived: `stale_source_revision`, `stale_summary`, `approval_binding_mismatch`, `preview_carry_forward_required` → 409; malformed or signature-invalid requests → 422; `listing_not_found` → 404; the four signing-availability codes, `checkpoint_root_mismatch`, `checkpoint_sequence_mismatch`, `checkpoint_missing`, `transparency_node_mismatch`, `transparency_append_failed` and anything else → 503 via `_unexpected_error_response` with correlation id. `_typed_error_code()` returns `None` for every code outside the allowlist.

**I-5. UI withdrawal is deliberate.** "Retire previous package" in AIM Data becomes a two-step confirm that states the public preview will disappear until a replacement is accepted; it calls the same withdrawal as today. No silent withdrawal from any refresh path.

**I-6. Rollback uniformity (F-E).** Candidate allocation (`allocate_candidate`, `listing_preview_disclosure.py:113-145`) is documented as non-destructive (insert-only) and gets the same explicit rollback wrapper as submit, so behaviour under commit-on-exit session owners and cancellation is identical across the three routes.

Out of scope: a new staged-candidate endpoint or state machine (GLM BETTER); multi-version preview history; any change to the disclosure signing format or the D0 manifest.
