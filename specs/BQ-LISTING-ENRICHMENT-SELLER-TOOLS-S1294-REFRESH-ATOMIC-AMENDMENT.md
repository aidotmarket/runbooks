## 1. The defect, as the Council established it

A seller with a live verified preview moves hosting (or changes anything that touches `listings`, `listing_versions` or `listing_summary_sources`). The triggers `invalidate_listing_summary` / `invalidate_listing_summary_source` (`alembic/versions/20260915_002:20-55`) set the summary record to `invalidated` and null its approval/disclosure pointers; the trigger `invalidate_preview_summary` (`20260917_003:55-61`) then sets `listing_preview_disclosure_heads.eligible=false` on **any** update of `listing_summary_records`. AIM Data's `transport.ensure_summary()` (`preview_marketplace_transport.py:136-157`) sees `state != approved` and `POST … /at-a-glance/approve` with `sample_decision: "none"` (`listing_summary.py:514,570,575`) **before** allocating the replacement candidate. That approval commits a new P1 disclosure that no longer matches the previous preview's binding, so `current_manifest()` (`app/services/listing_preview_projection.py:158-205`) returns no manifest and the public manifest 404s. The later `stale_source_revision` (AIM Data never sent `previous_commitment_id`) only stops the replacement. Net effect: a failed refresh leaves the seller with less than before. Also: the AIM Data UI "Retire previous package" button issues a live withdrawal (`app/routers/preview_builds.py:231`).

Council Gate 3 findings to discharge (all three verdicts): (F-A, HIGH, GLM) the prior verified preview must stay eligible until the replacement is atomically accepted, or the destructive transition must be staged; (F-B, HIGH, Gemini / MEDIUM, GLM) the backend's typed error body must stay `{"detail": …}`-compatible for the AIM Data client (or carry both `detail` and `code`), with a contract test; (F-C, MEDIUM, all three) only `stale_source_revision` may map to 409; signing-availability, checkpoint/log-integrity and unexpected append failures stay 503 with a correlation id; (F-D, MEDIUM, DeepSeek/Gemini) an end-to-end regression that fires the real triggers, runs the refresh with `previous_commitment_id`, and asserts `current_manifest` non-null and `head.eligible=true` afterwards, capturing state after every boundary (hosting move, GET preview, P1 approve, candidate allocation, submit failure); (F-E, MEDIUM per Gemini, LOW per GLM/DeepSeek) uniform rollback treatment on the candidate and regenerate routes.

## 2. Design (the invariant)

**I-1. A source change marks the live preview stale; it never removes it.** The trigger `invalidate_preview_summary` (`20260917_003:55-61`) stops flipping `eligible`. A new column `listing_preview_disclosure_heads.stale_since timestamptz NULL` is set **monotonically**: `SET stale_since = COALESCE(stale_since, now())` — the trigger fires on every `listing_summary_records` update (including the later P1 re-approval) and must not move the timestamp. `eligible` changes only by an explicit decision: an accepted replacement (`decide_preview`, `listing_preview_disclosure.py:325`) or an explicit withdrawal. The summary triggers of `20260915_002:20-55` are unchanged: the summary still becomes `invalidated` with null pointers, which is correct for the summary.

**I-2. The public manifest serves the stale head from immutable evidence.** `current_manifest` lives in `app/services/listing_preview_projection.py:158-205` (not in `listing_preview_disclosure.py`; r1 misattributed it). Today it requires the live summary record to be `approved` (`:179`), the approval pointers to match the binding (`:204-205`) and the source revision, hashes, content revision and version to match (`:193-202`), so after a source change it returns `None` and `public.py:914-916` 404s. Change: when `head.eligible` is true **and** `head.stale_since` is not null, take a **stale-read branch** that builds the manifest from the immutable event data (`event.request`, `event.manifest`, `event.source_anchor`) and skips the live-record gates listed above; the checks that remain mandatory on the stale branch are: the event is approved (`head.eligible`), the listing is public and listed, the platform envelope verifies against the stored bytes, the independent P1 freshness expiry (`:182-188`) still applies, and a withdrawn or non-public listing still returns `None`. The response carries an **unsigned overlay** on `ListingPreviewManifest` (`app/schemas/listing_preview.py:373`, a closed WireModel — add the fields there): `source_stale: bool` and `source_stale_since: datetime | None`. These names are distinct from the existing top-level `stale` (`listing_preview_projection.py:44-46`, which means *freshness* staleness) and are **not** added to `PlatformEnvelope` (`listing_preview.py:314-321`), so `platform_envelope_bytes` (`preview_signing.py:105-118`) and every stored event, seller signature and manifest stay byte-identical. The frontend listing page shows a "sample predates the current version (since <date>)" notice when `source_stale` is true; the JSON-LD/agent surface exposes the same two fields.

**I-3. P1 stays as it is; no carry-forward.** `POST /at-a-glance/approve` keeps `sample_decision = 'none'` (`ck_listing_summary_no_sample`, `20260915_002:112`); AIM Data's `ensure_summary()` call is unchanged and is never refused. r1's carry-forward/refusal rule (`preview_carry_forward_required`) is withdrawn: with I-1 and I-2 the P1 re-approval no longer removes the preview, and the head's own binding already carries the real sample decision. No CHECK migration, no new refusal code.

**I-4. Replacement is atomic.** `submit` (backend `build/s1732-preview-refresh-atomic` keeps its explicit rollback) accepts the replacement only when `previous_commitment_id` equals the head's current commitment; on acceptance it updates the head (event, commitment, `eligible=true`, `stale_since=NULL`) and appends to the transparency log in one transaction; on any failure nothing about the prior preview changes. AIM Data sends `previous_commitment_id=prior["commitment_id"]` (aim-data `6b702e5d`, one line, already correct).

**I-5. Error wire format and exhaustive status map (F-B, F-C).** Body: `{"detail": "<code>", "code": "<code>", "correlation_id": "<id>"}` — `detail` **equals the code**, so the current AIM Data client (`preview_marketplace_transport.py:16-34`, keyed on `detail`) keeps its typed mapping in either deploy order; a later client reads `code`. Status is an explicit, exhaustive table in `app/api/v1/preview_route.py` (`_typed_error_code` / `_typed_error_status`; branch `233c23ad:16-66`), one row per emitted code; no type-derived status:

| Status | Codes |
| --- | --- |
| 409 (client/state conflict, retryable by refreshing) | `stale_source_revision`, `stale_summary`, `stale_expected_head`, `approval_binding_mismatch`, `candidate_binding_mismatch`, `commitment_binding_mismatch`, `commitment_not_current`, `summary_binding_mismatch`, `approval_expired`, `idempotency_conflict`, `request_id_conflict`, `decision_mismatch`, `registration_evidence_stale` |
| 422 (request malformed or its own signatures/evidence invalid) | `disclosure_signature_invalid`, `commitment_signature_invalid`, `proof_signature_invalid`, `signer_authority_invalid`, `signer_evidence_invalid`, `signer_evidence_missing`, `signer_fingerprint_mismatch`, `registration_key_mismatch`, `registration_owner_mismatch`, `envelope_binding_mismatch`, `contract_mismatch`, `aggregate_hash_mismatch`, `invalid_evidence_policy`, `invalid_public_key`, `dictionary_must_match_committed_dataset_schema_republish_through_aim_data` |
| 404 | `listing_not_found` |
| 503 (server signing availability, log integrity, unexpected) — opaque, correlation id, no code beyond `unexpected_error` | `signing_configuration_unavailable`, `signing_environment_not_allowed`, `signing_key_unavailable`, `signing_key_invalid`, `checkpoint_signature_invalid`, `platform_signature_invalid`, `platform_key_alias`, `checkpoint_root_mismatch`, `checkpoint_sequence_mismatch`, `checkpoint_missing`, `transparency_node_mismatch`, `log_entry_mismatch`, `log_inclusion_invalid`, `log_predecessor_mismatch`, `log_consistency_invalid`, `transparency_append_failed`, and any code not in this table |

`_SAFE_SIGNING_ERROR_CODES` on the branch currently lets `checkpoint_signature_invalid` cross as 422 — it moves to 503. `transparency_log_service.py:384-395` keeps converting unexpected append failures to `transparency_append_failed` (503). AIM Data's `REFUSAL_MESSAGES` gains a row for every 409/422 code above that it lacks, with a seller-readable message.

**I-6. UI withdrawal is deliberate.** "Retire previous package" in AIM Data becomes a two-step confirm that states the public preview will disappear until a replacement is accepted; it calls the same withdrawal as today (`app/routers/preview_builds.py:231`). No withdrawal from any refresh path.

**I-7. Rollback uniformity (Gemini Gate 3 Finding 3, MEDIUM).** Candidate allocation (`allocate_candidate`, `listing_preview_disclosure.py:113-145`, insert-only) and the regenerate/approve summary routes get the same explicit rollback wrapper as submit, so behaviour under commit-on-exit session owners and cancellation is identical across the routes.

**I-8. Rollback of the change itself is forward-only.** Downgrading the trigger does not restore summary state, and deploying the old projection against a head that has entered the stale state reproduces the 404 with no further source change. The migration therefore has **no downgrade** for the trigger function (it raises with the recovery text), and `stale_since` is nullable so the old code ignores it. Operational recovery if the projection must be rolled back: the runbook documents it as "sellers with a stale head lose the public preview until they re-attest", and chunk D's test proves that statement. No feature flag: I-1 is the fix for all listings.

Out of scope: a new staged-candidate endpoint or state machine (GLM/DeepSeek BETTER); multi-version preview history; any change to the disclosure signing format, `PlatformEnvelope` or the D0 manifest.
