### Original-request recovery policy to review

Installed qualification SDK already sets max_network_retries=2. Its RequestsClient default timeout is80seconds, while this candidate abandons its executor await after20seconds. Extra retries are not the fix. Configure a request-local client for this flow with explicit bounded network timeouts and retain the SDK's retry algorithm; do not change global settings. Choose and verify the SDK/network budget so it fits inside the outer operation budget and the retained idempotency window. Capture late original completion using the same saved request identity; cancellation of an asyncio waiter does not prove the network request stopped.

Known PI: use existing read/revalidate/reconcile, never create another PI. Unknown PI with a fully valid durable original request: within a conservative23-hour window from prepared_at, a reviewed recovery call may retry exactly the same original request and idempotency key using standard Stripe idempotency. This explicitly amends the prior one-shot no-retry rule; it is not already approved or implemented. The window is earlier than Stripe's minimum24-hour retention and must include remaining request/retry time. No changed amount, metadata, customer, payment method, account or key is allowed. Same-key concurrent retries may refuse transiently; they must never switch keys. Provider/network calls hold no money locks.

Crash after prepare commit but before dispatch: local prepared state cannot distinguish this from lost response. Inside the window, the same-key request safely starts the original purchase if absent or returns its prior result if present. Outside the window, neither case authorizes another create: retain unresolved state and let the existing finance agent collect original provider/event evidence. Do not infer absence from a failed search or absence of a webhook. Do not release held spend without definitive original no-liability evidence. Terminal, expired or contradictory cases remain agent-investigated via the same protected command and provider-read tooling; no manual DB edits or Max Dashboard work is the normal path.

Acceptance must demonstrate the actual authenticated existing-agent caller, not only direct helper calls. Cover knownPI recovery, no-dispatch crash, lost response, late original thread completion, absent webhook, same-key concurrent retry, changed-parameter refusal, retry-window boundary, missing credentials/provider outage, terminal repeat, and insufficient/foreign liability refusal. Prove the clock/network budget and source SDK version together. Preserve signed-event recovery, all original tests and the separate synchronized original concurrent-preparation winner proof. If no existing agent has a real invocation trigger, expose that remaining integration gap rather than inventing a new scheduler or declaring automation from a callable method.
