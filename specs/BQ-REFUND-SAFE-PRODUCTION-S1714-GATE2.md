## 1. Outcome, authority, boundaries

A refunded or revoked order cannot acquire new seller-payout ownership. Refund admission competes with payout through the same order lock. One atomic effects transaction makes finance, human/agent transaction, order/access, per-refund spend and event completion converge. Exactly one succeeded-refund aggregate drives full/partial state. A late external refund after payout ownership is a recorded reconciliation exception, not a claim that payout was prevented. No automatic reversal.

Max's supplied S1713 plan section4 requires settlement to refuse refunded/revoked orders (#4067). Max directed Mars to follow that plan and subsequently authorized all necessary production dependencies in Event99af61fd-db46-42fd-a18d-1d0698e457d1 (bus4096). This is the policy-owner acceptance for strict all-revoked exclusion requested by CC RM3; no bare-revoked-pays exception. Existing completed Transfers are preserved. Refunds involving partial amounts retain access unless independently revoked; automatic payout is refused for any positive succeeded refund total, because a new prorated fee/payout policy is outside this change.

Unrelated credit-grant logic, metering payouts, general dispute UX, fresh real-money first sale and buyer-download redesign remain excluded. Narrow guards preventing an old payment/dispute writer from erasing refunded state are included. ## 4. Lock order and acknowledgment protocol

Choose an explicit event mutex followed by the common order sequence. Every refund phase first locks its own stripe_events row, then unique order (if present), linked transaction, order_money_states, Payment, then Refund rows sorted by stripe_refund_id ascending, then the linked agent_api_keys row. Payout/revoke/confirm paths start at order and never acquire an existing stripe_events row after it. Dispute webhook already owns its own event mutex, then follows order/transaction/authority. No path locks another event's row while owning an order. Refund dispatch to BillingService occurs before BillingService's generic event acquisition so it cannot silently reverse the sequence.

This is a refinement of Gate1's common order-first money lock: the event mutex is an outer same-event serialization boundary, not a money-operation lock acquired in reverse. A lock graph and deterministic same-event/different-event tests must prove no event/order cycle. Resolve order IDs with nonlocking lookups first, then validate all bindings again under locks. Conflicting/multiple/missing reverse links fail closed; never select the first matching order.

The signed refund reaches the existing suppression decision. Only an admitted normal event (or separately approved exact TEST predicate) proceeds. Existing raw dedup's uncommitted processing row is not a durable admission. Under the above locks, validate event identity/binding, record refund_phase=admitted, status=failed/error_message=refund_pending, and commit. All sync locks are released. A pending admission without an order remains bound by PI and blocks a later order with that PI; provider reads and delayed payment records may complete it later.

Read provider objects outside database locks, then run the atomic async effects transaction in the same HTTP request. HTTP2xx occurs ONLY after effects and event completion commit. There is no fire-and-forget task or new refund worker. Duplicate completed protocol events validate their applied binding and return2xx without effects. Failed/pending events remain retriable; unavailable async session, provider inconsistency and finance failures return500. Signature/scope validation retains existing400/suppression policy. A legacy completed refund event with no protocol marker is classified for reconciliation, not treated as a newly safe applied refund.

Atomic effects acquire locks in the same order, revalidate provider/payment/order bindings and pending phase, apply new succeeded deltas, update order/transaction/access/Payment, mark event refund_phase=applied and raw status=completed/processed_status=processed, then commit. Remove old _handle_refund effect writes; its replacement only admits. Existing unconditional outer error upsert must not overwrite a committed applied/completed refund: conditional update only where refund_phase is not applied and status is not completed. A crash after effects commit/before HTTP acknowledgment converges on replay.

Provider succeeded-set sum must equal the authoritative refunded total and never exceed original gross. Reads that straddle provider changes or contradict stored successful identities retry rather than lower totals. Pending/failed/canceled entries can be observed but apply no journal/spend delta; succeeded state cannot regress. Unexpected provider status fails retryably.

Under the Payment/refund locks, each real succeeded refund with no applied effects is posted once through existing FinanceEngine.record_refund (which flushes, not commits). Existing source_ref refund:<re_ID> must match payment/entity/amount and balanced journal; unmatched historical entries require reconciliation rather than duplicate postings. Apply agent spend once per newly succeeded refund, preserving the existing zero floor: actual decrement=min(new refund amount,current nonnegative spend_used), and record that actual delta on Refund together with the gross refund amount already in the row. A smaller current counter is not by itself grounds to block a valid refund. Wrong key/owner or negative/corrupt counter is a reconciliation condition. Never subtract the cumulative charge-refunded total on each partial event.

One sum of applied succeeded Refund amounts drives Payment.status=partially_refunded/refunded and order.refund_amount_cents/status identically. Partial leaves current transaction status and access; full sets order revoked/refunded and both human and agent transaction refunded using a caller-owned noncommitting transition helper, with one transition event. Settled transactions may record refunded as a financial outcome while preserving settled_at, old settled event and Transfer ID; order-money state becomes reconciliation_required. Add REFUNDED transitions only for paid/fulfilling/delivered/confirmed/disputed/dispute_resolved/settled states with validated provider proof; generic user transition APIs cannot manufacture it.

Payment-intent replay cannot reset a refunded Payment to succeeded. Confirmation cannot overwrite full refund or independent revocation. Dispute-won handlers clear only their own dispute restriction when there is no independent revocation, pending/positive refund or reconciliation condition. Existing revoked state is adopted conservatively as independent unless provenance proves it is exclusively the current resolved dispute. No provider dispute outcome invents a real Refund ID or journal.

Preserve provider identities: transaction key settle_<tx_number>, group tx_number; legacy key transfer_<order UUID>, group order_number. Fetch final provider refund facts outside locks, then re-lock order/transaction/authority and recheck current admission/revision/eligibility. Commit dispatching plus unique dispatch token. THIS dispatching commit is the linearization point: refund/revoke admitted before it prevents Transfer; an arrival afterward records a post-ownership reconciliation exception. Do not use the loose phrase 'before network dispatch' as an atomic guarantee.

Only the request owning that committed token may issue the initial Transfer.create outside locks. On success re-lock and record Transfer plus settlement atomically; if refund/revoke won later, preserve successful Transfer and reconciliation-required rather than overwriting refunded state. On any uncertain response or crash leave unknown/dispatching; never use lease expiry or a fresh key to re-dispatch.

Recovery: retrieve known Transfer ID or completely paginate Transfer.list(transfer_group=...,destination=...). Exactly one match requires same amount,currency,destination,group,order/transaction metadata and nonreversed state; finalize only that identity. Zero matches after possible dispatch is still uncertain; multiple/contradictory matches require reconciliation. Recovery command never creates a Transfer or reversal. Explicit provider rejection also refuses automatic new-identity creation; operator must diagnose before a separately reviewed retry. Existing scheduler retry metadata cannot override this state.
