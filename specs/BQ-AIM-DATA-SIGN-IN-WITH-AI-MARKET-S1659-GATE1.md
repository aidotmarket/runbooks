## 1. Problem

AIM Data's login UI requires email/password or a pending six-digit 2FA challenge. Its backend proxies marketplace password login and then marketplace 2FA; it has no provider-choice flow in that UI. Evidence: `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:frontend/src/pages/LoginPage.tsx:22-63`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:frontend/src/pages/LoginPage.tsx:89-162`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/routers/auth.py:456-576`.

The marketplace password endpoint rejects a missing password hash. Provider signup creates an account with `password_hash=None`; therefore a provider-only account cannot use this AIM Data password route. This is a source-supported incompatibility, not a conclusion drawn from the account count. Evidence: `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:531-563`, `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/auth/oauth.py:391-411`.

Max reports a production read-only count on 2026-09-07 of **26 of 71 real accounts** and his own inability to sign in. No pinned query/result artifact was supplied or found in the inspected sources; this specification records that number as **directive-reported, not independently verified**. Gate 1 must not present it as audited production evidence. No customer database was queried for this authoring task.

The main site's existing Google, GitHub, password, magic-link and 2FA flows are the authentication authority. Source: `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:945-998`, `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:531-563`, `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:846-942`, `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:1110-1117`; the shared success path creates a pre-auth challenge before issuing a session when TOTP is enabled: `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/api/v1/endpoints/auth.py:202-216`.

## 2. Frozen product and trust decisions

The following are binding **proposed design decisions for Gate 1 approval**, not claims that the features already exist.

1. Add **Sign in with ai.market** as the primary AIM Data login action. Use the seller's normal system browser and the real ai.market login UI. Do not embed the provider UI or implement Google/GitHub OAuth in AIM Data.
2. AIM Data is a **public first-party client**, using authorization code with mandatory **PKCE S256**. The production client ID is the public constant `aim_data_desktop_v1`, baked into the image. No per-install client registration, shared secret, provider secret or marketplace signing key is distributed.
3. Production callback is exactly `http://127.0.0.1:<published-port>/api/auth/aim-market/callback`. The port is variable; scheme, literal host and path are fixed. `localhost`, IPv6, LAN addresses and arbitrary HTTPS callbacks are not alternate registrations in this slice. Users who opened AIM Data at `localhost` first reopen it at the numeric loopback origin before starting.
4. The browser must reach the loopback port on its own machine. Remote-host use of this button is unsupported in v1; document the existing password fallback and its provider-only limitation. SSH-tunnel support/proof stays tracked in section 7.1; tunnel-free login and a cloud callback relay remain out of scope.
5. Use one first-party account-session scope, **`aim_data.session`**, only for the operator-provisioned client. It grants the same account authority as password sign-in, subject to the same server role, ownership, readiness and step-up checks. It is not a claim of endpoint-level least privilege or an OpenID Connect implementation; no `openid` scope or ID token is introduced.
6. Skip the generic third-party scope-consent form for this reserved client, but **do not silently authorize it**: ai.market must show “Continue to AIM Data as [account]” and require an explicit Continue or Cancel. Explain that the customer-hosted app receives account access equivalent to password login. A public client ID is not proof that the running binary is genuine.
7. Reuse AIM Data's connected token completion, local user link, cache and install-registration path. Preserve the existing local API-key/JWT-cookie flows; do not invent an API key or local admin session for an OAuth account.
8. Preserve website S916 posture: browser refresh token remains HttpOnly, website access token stays in memory. Preserve AIM Data's **actual current storage** in this slice, with its risks expressly disclosed in section 5. Applying S916 storage to AIM Data as well would require a separately approved storage migration; this document does not pretend AIM Data already has it.
9. Keep the pre-1.23 email/password UI and backend route, including its 2FA path. Fix only its transport compatibility with the current marketplace cookie response where necessary. The OAuth kill switch never disables password or local operator login.
10. Buyer-only accounts may authenticate, with existing account permissions, but login does not create seller status, Connect readiness or publish authority. Unverified email and 2FA remain decisions enforced by ai.market, never bypassed locally.

## 4. Binding flow and transport

### 4.1 First-party provisioning

An idempotent operator-controlled migration/seed provisions `aim_data_desktop_v1`, name `AIM Data`, authentication method `none`, allowed grants `authorization_code refresh_token`, mandatory S256, exact scope `aim_data.session`, and the loopback redirect policy. Store no usable secret. The script refuses an existing row with conflicting metadata; it does not turn a third-party row into a first-party row by name matching. Public registration/update/regenerate APIs cannot assign this reserved ID, auth method, trust flag or scope, and cannot mutate the reserved row. Existing confidential clients remain confidential.

Provide one independent client record per environment using the same non-secret ID; trust is the pinned issuer/API origin plus its registry, not the ID alone. Production browser origin is `https://ai.market`; API URLs derive only from trusted installation configuration and the website's configured API origin. Test overrides use only the isolated test issuer; no runtime user URL or callback parameter may select the token host. ### 4.2 Docker callback and local transaction

The supplied Compose file publishes `${AIM_DATA_PORT:-8080}:80`; nginx forwards `/api/` unchanged to `127.0.0.1:8000`, and FastAPI mounts auth under `/api/auth`. Thus the correct default callback is **`http://127.0.0.1:8080/api/auth/aim-market/callback`**, not container port 8000 or a new listener. Sources: `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:docker-compose.aim-data.yml:17-18`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:deploy/nginx.conf:28-40`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/main.py:489-493`.

1. Serve the new action on the existing login page. On a numeric-loopback UI origin, perform a same-origin JSON **POST `/api/auth/aim-market/start`**. Require exact Origin, non-simple content type, a page bootstrap CSRF nonce and rate limiting. No permissive local CORS. New login starts invalidate older pending attempts for that browser; other browsers have distinct attempts.
2. Configure proposed `AIM_DATA_OAUTH_LOOPBACK_PORT` to the browser-visible port (default 8080; installer sets it consistently with the published port). Do not trust the raw Host, `X-Forwarded-Host` or an arbitrary supplied redirect: nginx currently sets Host to `$host`, which loses the published port (`aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:deploy/nginx.conf:29-34`). Validate the initiating Origin against the configured literal loopback origin. Reject mismatches with instructions before navigating away. Bind loopback deployments explicitly to `127.0.0.1:<port>:80`; do not claim the existing Compose shorthand already limits exposure.
3. Backend generates independent 32-byte random state, browser-binding nonce and PKCE verifier; verifier is base64url without padding and challenge is base64url(SHA256(verifier)). Store pending transaction server-side in bounded memory for **10 minutes**: state hash, browser-binding hash, verifier, exact redirect, issuer, client, scope, creation time, fixed success path `/datasets`, and status. Restart expires attempts. Gate 2 admission must record the actual worker count and pin one serving process for these routes, or require a shared atomic TTL store before merge. Test start/callback on different workers for the shared-store option; for single-worker mode, prove multi-worker startup is rejected. Verifier never enters browser storage or any URL.
4. Set host-only HttpOnly SameSite=Lax browser-binding cookie, scoped `/api/auth/aim-market`, Max-Age 600; Secure on HTTPS, omitted only for this HTTP loopback deployment. Cookies are not port-isolated, so cookie names include the configured port, while transaction verification also checks the exact Origin/redirect and process-held state. Send only the generated authorization URL back to the UI and navigate the same browser tab.
5. Browser goes to the configured API's **GET `/api/v1/oauth/authorize`** with `response_type=code`, client ID, exact callback, `scope=aim_data.session`, state, S256 challenge and method. No login token or provider secret crosses this URL.
6. Callback is unauthenticated **GET `/api/auth/aim-market/callback`**, but requires matching state and browser-binding cookie and an unexpired, unconsumed transaction before code exchange. Validate errors by the same rules. Exchange from inside the container to **POST `/api/v1/oauth/token`**, form-encoded `grant_type=authorization_code`, `code`, `client_id`, exact stored `redirect_uri`, `code_verifier`; omit client secret. Do not follow token-endpoint redirects. Timeouts terminate the attempt and require a fresh start; do not blindly replay an uncertain exchange.
7. After valid exchange, invoke the shared connected-login completion with `/auth/me` verification and `_handle_ai_market_token`, then the existing registration attempt. A failed identity validation is a failed login; registration failure is a distinct recoverable not-ready state, never evidence of publish success. Store a one-use completed response for at most **60 seconds**, erase verifier/code, and 303 to fixed `/login/complete` with no credentials or state in the URL.
8. The local SPA makes same-origin CSRF-protected **POST `/api/auth/aim-market/complete`** with the binding cookie and a fresh page nonce; only then receive the existing connected-login response and run shared `completeLogin`. Consume the response atomically and clear the transaction cookie. Tokens never appear in callback HTML, query, fragment or `postMessage`. There is no polling or copy/paste token step.

The registered `redirect_uri` policy requires exact `http`, literal host `127.0.0.1`, canonical decimal port **1024–65535** (no leading zeros), and exact path `/api/auth/aim-market/callback`; reject query, userinfo, fragment, backslashes, controls, encoded path tricks, alternate numeric addresses, trailing-dot hosts and DNS names. Only the port varies for this client; exchange compares the original query-free URI byte-for-byte. The callback request separately permits only `code` and `state`, or `error=access_denied` and state on Cancel (other validated protocol failures carry only an allowlisted error and state); reject duplicates and extra parameters. The one-use code, expiring in **60 seconds**, is allowed only transiently in the exact ai.market → AIM Data loopback callback transport and must be absent from final UI URLs, application/proxy logs, support exports, screenshots and evidence. Access tokens, refresh tokens, verifiers and persistent credentials are forbidden in all URLs and every such disclosure surface, with no callback exception; intentional backchannel transport/current token storage remain as specified in sections 4.4/5.1.

Remote-host button support and S1656 paid evidence are post-P0 follow-ups in section 7.1, with no P0 dependency on an S1656 origin amendment.

## 5. Security and account behavior

### 5.1 CSRF, interception, trust and storage

- **CSRF and login substitution:** independent state, browser binding and PKCE; protected local start/complete, bound server authorization transaction, authenticated user confirmation and atomic one-use code. Reject duplicate query parameters and ambiguous parsing. A callback from another browser, install, port, issuer or login attempt cannot complete. Do not send tokens to a request-provided return path.
- **Loopback interception:** PKCE prevents an interceptor redeeming the intercepted code without the verifier. It does not prevent a malicious process from occupying the port or a malicious application initiating its own request using the public ID. Exact callbacks, existing listener, visible account confirmation and browser binding are required; local host compromise is a residual. The external-browser/loopback model follows [RFC 8252 sections 7.3 and 8](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3); S256 construction follows [RFC 7636 section 4](https://www.rfc-editor.org/rfc/rfc7636.html#section-4).
- **Redirects:** allowlist before success **and error** redirects; immutable validated request inputs; exact internal login continuation; no reflected raw client names/errors in HTML. Bind issuer and token endpoint in the pending transaction and reject mix-up. No dynamically supplied token server, provider callback or DNS-resolved “loopback”.
- **Website storage remains unchanged:** refresh cookie HttpOnly, access in the existing store; the API client refreshes with credentials and sets the access token in that store. Sources: `ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/core/auth_cookies.py:29-38`, `ai-market-frontend@abe5ec51706cd32361c5de83ba4ba905d050cb5d:store/auth.ts:59-70`, `ai-market-frontend@abe5ec51706cd32361c5de83ba4ba905d050cb5d:api/client.ts:90-107`.
- **AIM Data storage is reused honestly:** `completeLogin` writes access and refresh to localStorage and treats the access token as `apiKey`; `_handle_ai_market_token` persists the access token to the serial store, whose JSON file uses atomic writes and mode 0600. This is not S916 browser storage and is not encrypted-at-rest token storage. Sources: `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:frontend/src/contexts/AuthContext.tsx:67-93`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/auth/api_key_auth.py:337-363`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/services/serial_store.py:106-123`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/services/serial_store.py:183-188`. Do not add verifier, provider credentials or completed-token URLs to those stores. Existing localStorage XSS exposure and customer-host token readability are explicit Gate 1 reservations.
- **Completion semantics:** the connected path does not call `_set_jwt_cookie` or generate a `vz_` key; those belong to local operator login. Sources: `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/routers/auth.py:403-421`, `aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:app/routers/auth.py:468-504`. Reuse means preserve that distinction, not claim OAuth must mint a local admin cookie. Extract only the shared connected completion helper needed by both paths.
- **Secrets and evidence:** Google/GitHub secrets remain in marketplace backend provider exchanges (`ai-market-backend@505465eee5917f4deb6a86469561b6b17f38e725:app/auth/oauth.py:322-346`). No provider tokens, shared client secrets or marketplace signing keys enter image layers, build arguments, bundles, logs, support exports or customer config. Runtime-generated customer install keys remain local as today. Redact state, codes, verifier, auth/cookie headers and token response bodies from both proxy/application logs; callback responses are `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The callback nginx location needs explicit log suppression/redaction because ordinary `/api/` forwarding alone supplies no such policy (`aim-data@9f6030563a02e4a23c15c361a50015d9891d50c2:deploy/nginx.conf:28-40`).
