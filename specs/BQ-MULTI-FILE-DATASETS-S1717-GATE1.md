## 1. Problem

A seller's product is a directory: data blocks, a free sample, a README, a description, sometimes thousands of files. Today every layer models a product as one file:

- AIM Data has two directory-capable ingestion paths and both end in one `DatasetRecord` per file: bulk upload (`aim-data:app/routers/datasets.py:426`, `:512-545`, BQ-108) and directory import (`aim-data:app/routers/imports.py:39-74`, `:87-111` — `POST /imports/scan` and `/imports/start`; `app/services/import_service.py:52-59` `ImportFileEntry.relative_path`, `:146-164` hidden/junk/symlink/unsupported skips, `:176-197` one record per file). The import scanner silently truncates at 10,000 files (`import_service.py:142-145`: `if len(files) >= 10000: truncated = True; return`) — a 21,000-file directory yields a truncated set with no refusal. `DatasetRecord` (`aim-data:app/models/dataset.py:39-64`) carries non-nullable file-specific columns (`original_filename`, `storage_filename`, `file_type` at `:42-44`), `processed_path`, `listing_id`, and `batch_id`/`relative_path` (`:52-54`) that only group notifications. Processing (`aim-data:app/services/processing_service.py:232`) profiles and runs allAI metadata per record. Publishing (`aim-data:app/routers/marketplace_publish.py:403`) publishes one record as one listing and sets `listing_id` on that record (`:393`, `:415`).
- The publish contract already carries N-object scalars: sender allowlist `VersionPublishEmit` (`aim-data:app/routers/marketplace_publish.py:113-116`: `object_count`, `total_size_bytes`, `manifest_hash`), receiver schema `ai-market-backend:app/schemas/vz_publish.py:133-141` (`object_count` is `ge=0`; `manifest_hash` is opaque; the member list is not on the wire). But only the Seller Workspace S3 route uses it: the versions endpoint is S3-scan-only (`marketplace_publish.py:264-293`, `:512-543`), the receiver materializes a `ListingVersion` only with a non-empty `s3_connection.prefix` (`ai-market-backend:app/services/listing_versioning.py:198-199`), `ListingVersion.prefix` is non-null (`ai-market-backend:app/models/marketplace.py:213-240`), the receiver stores the hash and compares it on replay but never recomputes it (`listing_versioning.py:229-246`), and an ordinary local dataset resolves to `NotS3PublishSource` (`aim-data:app/services/s3_publish_source_resolver.py:93-95`). The interop record pins `object_count == 1` for the local route (`specs/SELLER-ROUTE-INTEROP-S1711.md:12`).
- Delivery is one file per order on both routes. Local: `aim-data:app/services/fulfillment_service.py:106-163` resolves one artifact and streams it; backend `TransferSession` is "one transfer session per order fulfillment" with one filename, byte total, chunk count and expected SHA-256 (`ai-market-backend:app/models/transfer_session.py:39-79`); the listener accepts one file description (`app/services/fulfillment_listener_service.py:94-188`), is idempotent on a second complete (`:292-300`), and marks the order `delivered` on the first finalized transfer (`:435-456`). S3: `bind_s3_delivery` refuses `object_count != 1` (`ai-market-backend:app/services/fulfillment_service.py:88-93`, "Object binding rejected"), `_validate_stored_s3_identity` refuses it again (`app/services/order_service.py:1356-1361`, surfaced as `403 DELIVERY_OBJECT_BINDING_REJECTED` at `:1348`), and the design authority is `specs/BQ-MONEY-PATH-DELIVERY-LEG-S1681-GATE1.md:455` ("The purchased `ListingVersion` MUST have `object_count == 1`; any other count is REFUSED on this branch") with the matching test at `:477`. The buyer download unification item already asks how multi-file grants work (`specs/BQ-BUYER-DOWNLOAD-UNIFICATION-S1711-GATE1.md:34`).
- The paid verification scan (`specs/BQ-DATA-VERIFICATION-S1590-GATE1.md`) traverses "every reachable supported object in the registered root" (`:203`) and reports `coverage` with a **closed** skip-reason enum: `permission_denied`, `unsupported_type`, `timeout` (`:131-132`; executable in `ai-market-backend:app/schemas/data_verification.py:466-487` `SkippedObject`/`ReportCoverage` with exact-total validators, and `aim-data:app/schemas/data_verification.py:90-96` for the quote probe). No seller may select exclusions (`:203`) or delete a skip (`:205`). The quote requires `objects_discovered >= 1` (`aim-data:app/schemas/data_verification.py:63-68`). The AIM Data resolver returns one local path or one S3 metadata row (`aim-data:app/services/source_artifact_resolver.py:45`; `data_verification_local_service.py:219-227` probes objects inside one file).
- The free sample is bounded "approved rows" of the one file: `DisclosureSnapshotCreateRequest.sample_decision` is `approved_rows | none` (`ai-market-backend:app/schemas/disclosure_snapshot.py:101-124`; rows at `:64-91`; public summary is row count and columns only, `app/services/disclosure_snapshot_service.py:156-168`). No surface delivers a sample *file*.

Consequences: a real seller cannot list a real dataset without merging it by hand; a 21,000-file directory creates up to 10,000 cards (silently dropping the rest) and 10,000 allAI metadata passes; documentation files become "datasets"; and the seller's question ("must I merge?") is the honest answer today. This is the first wall every serious seller hits, before the verified label even enters the picture.

## 2. Decision (design authority)

**D0. One manifest, four consumers.** Every directory dataset has an immutable, versioned **`DatasetManifest`**: an ordered list of members, each `{index, relative_path, size_bytes, sha256, detected_type, role, is_sample}`, plus `member_count`, `data_member_count`, `total_data_bytes`, and `manifest_hash` = SHA-256 over the JCS (RFC 8785) canonicalization of the member list. Publish (D3), delivery (D5), verification (D6) and the S1711 buyer door all consume this one manifest, pinned to the published version; nothing derives a second identity from the filesystem. A manifest is frozen when a version is published; a re-upload produces a new manifest and (if published) a new version.

**D1. A dataset is a directory.** One `DatasetRecord` represents an uploaded directory tree (a single file is the one-member case). Members live in a new `dataset_members` table (one row per file: the D0 fields plus `status` and `reason`); the file-specific non-nullable columns on `DatasetRecord` (`original_filename`, `storage_filename`, `file_type`) get an explicit directory-mode contract at Gate 2 (directory name, root storage path, `directory`). Each member has a **role** — `data`, `documentation`, `other` — and an independent **`is_sample`** flag. Roles are detected by convention and always editable by the seller before publish (defaults: `README*`, `HOW_TO_USE*`, `*DESCRIPTION*`, `LICENSE*` → `documentation`; unsupported types → `other`, never processed, never delivered unless the seller marks them `data`; everything else → `data`). `is_sample` defaults to true for `data` members under `SAMPLE/`, `sample/` or named `sample*`. Role and sample selection are frozen into the manifest at publish.

**D1a. Migration invariant (AC7).** Every existing `DatasetRecord` becomes a one-member directory whose single member is synthesized from the row's own file columns; existing rows are never merged by `batch_id`; `listing_id` bindings, dataset ids, file paths, statuses and delivery behaviour are unchanged. Directory semantics apply to new uploads only; any retrospective consolidation of old rows is a separate, explicitly approved repair flow, not part of this build.

**D2. Processing is per directory, bounded.** Profiling, PII scan and allAI metadata run once per dataset over a deterministic subset of `data` members. The policy is a set of named fields whose values Gate 2 pins as an appendix: `PROFILE_MAX_MEMBERS` (count), `PROFILE_MAX_MEMBER_BYTES`, `PROFILE_MAX_TOTAL_BYTES`, `PROFILE_TIMEOUT_S`, ordering = ascending `sha256` with `relative_path` tie-break, allAI calls per dataset = 1, and the behaviour when no member fits the cap (terminal `profiling_skipped` with reason, listing still allowed with an explicit "not profiled" summary). The analogous S3 bound (`aim-data:app/services/s3_scan_service.py:24`, `:40-58` `sampled_object_count`, `sample_coverage`) is the model; the dataset page states "profiled on N of M files". Documentation members feed the listing description as seller-supplied context (quoted, never executed). The dataset shows one status; per-member failures are recorded as member status with a fixed reason (`unsupported_type`, `too_large`, `parse_failed`, `timeout`) and never leave the dataset spinning.

**D3. One listing per dataset, N objects, local-route version materialization.** The local route emits `VersionPublish` with `object_count = data_member_count`, `total_size_bytes = total_data_bytes`, `manifest_hash` from D0, and a new route discriminator `source_route = "local"`; the receiver materializes a `ListingVersion` for the local route without an `s3_connection` prefix (`ListingVersion.prefix` becomes nullable and `source_route` is stored; `listing_versioning.py:198-199` is relaxed for `local` only; the S3 route is unchanged). The receiver obtains the member list through a chunked, bounded upload modelled on `seller_approved_source_index` (`ai-market-backend:app/services/seller_approved_source_index.py:28-102`: `MAX_SELECTION_FILES`, `CHUNK_FILES`, `objects[]`), recomputes `manifest_hash` over the received members, and refuses a publish whose count, total size or hash do not match. `manifest_hash` is therefore verifiable, not opaque, on the local route; duplicate/quarantine logic (`listing_versioning.py:109-137`) keys on the recomputed hash. Publishing requires `data_member_count >= 1`; an all-documentation or all-`other` upload is refused before listing. The `object_count == 1` interop pin is retired for the local route. The public listing summary is the aggregate of profiled data members and names the number of distinct schemas found.

**D4. Free sample = chosen data members.** Sample members are `data` members with `is_sample = true`; they are delivered to buyers after purchase like every other data member (D5) *and* before purchase through a new bounded **sample-file route**: at publish, AIM Data uploads the sample members (caps `SAMPLE_MAX_FILES`, `SAMPLE_MAX_TOTAL_BYTES`, Gate 2 values) to ai.market as a disclosure asset bound to the version's manifest hash; `DisclosureSnapshotCreateRequest.sample_decision` gains `member_files` with `approved_sample_members[] = {index, relative_path, size_bytes, sha256}`; the public listing serves them unauthenticated, rate-limited, hash-verified, with no other member reachable. `approved_rows` remains available (and is the default for one-member datasets).

**D5. Delivery is the whole set, under one transfer manifest.** A purchase delivers every `data` member. The Trust Channel local route becomes **one transfer session per order carrying N framed members**: the session opens with a `TransferManifest` = `{version_id, manifest_hash, members[]: {index, relative_path, size_bytes, sha256, content_type?}}` bound to the published `DatasetManifest`; members are streamed sequentially with per-member chunk framing (`member_index` on every chunk), per-member hash verification, and resume at member granularity; the order becomes `delivered` only after every member in the manifest has matched its published hash (`fulfillment_listener_service.py:435-456` changes from first-transfer to all-members completion; `TransferSession` gains member rows). Missing final member, changed path/hash/size, duplicate or replayed chunks and a mid-set failure are refused or resumed, never presented as complete. The S3 route lifts `object_count == 1` on the multi-object branch only (`fulfillment_service.py:88-93`, `order_service.py:1356-1361`) with the object set bound to the version's manifest; single-object listings keep the restrictive binding unchanged. This requires an S1681 Gate 1 amendment of `:455`/`:477` before chunk D. The buyer download door (S1711) consumes the same manifest with `object_count > 1` as its base case; whether the buyer fetches members individually or as an archive assembled at transfer time from unchanged member bytes (transport packaging, not data transformation) is S1711's decision.

**D6. Verification covers the data members, inside the shipped S1590 contract.** For a directory dataset the **registered root** (S1590 `:203`, `:40`) is the frozen data-member set of the published manifest, resolved by the AIM Data resolver as a directory root plus manifest hash (the local analogue of the already-shipped S3 prefix root); `objects[]` enumerates those members exactly as the S3 route enumerates objects under a prefix; the receipt's `artifact_locator_commitment` is over the canonical root path plus `manifest_hash`, and the content hash is `manifest_hash`. Documentation, `other`, and non-data members are **not** in the registered root, so they are never "discovered-and-skipped": the skip-reason enum, `coverage` validators, privacy boundary, payment and publication contracts are untouched, and the seller cannot change scan scope after publish because the root is version-pinned, not role-live. The listing discloses role counts ("N data files scanned; M documentation files not part of the data set") outside the scan report. Gate 2 must cite the S3-prefix resolver path as precedent for the directory root; if the resolver contract turns out to need an S1590 amendment, it is raised as one before chunk E starts, not folded silently.

**D7. The verified label stays voluntary, and says so — as deliverables.** Listing never depends on verification, a card, or a quote (static truth at the pin: `aim-data:frontend/src/pages/DatasetDetail.tsx:1312` gates publish on disclosure/metadata only; the verification panel at `:1323-1327` renders with a possibly-null listing id and at `:1664-1670` only after `preview_ready`; it issues a read-only status GET on render and takes no paid action until clicked; card only at paid start per S1646). Chunk F delivers: the panel heading "Optional: add a verified shape label", visually separated from the publish controls; the first sentence of `data-verification-seller-journey.md` §B stating the whole procedure is optional and seller-initiated (today `:44-49` is a precondition list, not an optionality statement); and an AC6 test asserting the publish request carries no verification field and succeeds with the panel untouched.

**D8. Scale.** 21,000 members must be a normal upload: member registration reuses the import scanner's traversal (`import_service.scan` skip buckets, `relative_path`, `size_bytes`, `extension`) and is streamed and idempotent by (dataset, `relative_path`, `sha256`); the silent 10,000 truncation is removed and replaced by policy caps `DATASET_MAX_MEMBERS` and `DATASET_MAX_BYTES` (Gate 2 values, ≥ 25,000 members so the trigger case fits) that refuse the whole upload with a clear message naming the cap, never a partial set; re-uploading the same directory updates changed members only, and a member that disappears from the source is marked `removed` (never deleted from a published manifest); path collisions on case-insensitive filesystems are refused at registration. The UI shows the directory as one card with a paged member table filterable by role/status.

## 3. Non-goals

No change to pricing, commission, payout, the S1590 manifest, skip-reason enum or privacy boundary, the Seller Workspace S3 publish model (it already is a prefix), the Trust Channel encryption, or the buyer's identity/access rules. No transformation or merging of member bytes anywhere (an archive built at transfer time from unchanged members is packaging, not merging). No cross-dataset bundles. No public per-member browsing beyond the sample members.

## 4. Customer-visible behaviour

1. Upload a folder → one card "Acid Trap Dataset" with member count, total size, one status; above the cap, one refusal naming the cap.
2. Open it → member table with role chips (data / documentation / other) and a sample toggle, per-member status and reason, "Set role" and "Mark as sample" actions; profiling summary "profiled on N of M files"; description drafted from documentation members for the seller to approve.
3. Publish → one listing; buyers see one product with N files, the aggregate summary (with the number of schemas), and the sample files downloadable.
4. Buy → all data members delivered; the order page shows a file list with per-file progress and hashes; the order is complete only when every file matches.
5. Optional: "Add a verified shape label" → the S1590 flow over the data members; the report's coverage section shows N objects; the listing shows the role counts alongside.
6. Existing single-file datasets and listings keep working unchanged (one-member directories).

## 6. Chunks (for Gate 2 to pin)

- **A — AIM Data model and upload:** `dataset_members` table, D0 manifest builder (JCS + SHA-256), directory-mode `DatasetRecord` contract, D1a migration, roles + `is_sample`, streamed idempotent registration reusing the import scanner, caps with refusal, removed-member handling, directory card + member table UI.
- **B — AIM Data processing:** D2 policy fields, per-directory bounded profiling/PII/allAI (one call), documentation as context, member failure states, "profiled on N of M".
- **C — Publish and sample:** local-route `VersionPublish` with `source_route`, chunked member upload and receiver-side hash recomputation, nullable `ListingVersion.prefix`, zero-data refusal, `member_files` sample decision, sample-file route with caps, listing aggregate summary with schema count; interop record update.
- **D — Delivery:** S1681 amendment; `TransferManifest`, N-member framed transfer session, all-members completion, resume/replay/tamper refusals; S3 multi-object binding; order page file list; hand-off to S1711.
- **E — Verification over the set:** resolver directory-root case, connector member enumeration from the pinned manifest, locator commitment over root + `manifest_hash`, role-count disclosure on the listing.
- **F — Copy and runbooks:** D7 heading and separation; `data-verification-seller-journey.md` §B first sentence; `aim-data-seller-publish-journey.md`; INSTALL/README; AC6 test.
Dependency: A → B → C → (D ∥ E) → F, with the S1681 amendment approved before D starts. Each chunk: MP builds, GLM + DeepSeek Gate 3, CC waived; nothing ships to the stable image before C and D are both approved (a listing with N objects must be deliverable).

## 7. Acceptance criteria

- **AC1.** Uploading a directory with 21,000 files in AIM Data yields one dataset, one status, a member table, exactly one allAI call, and profiling that terminates within `PROFILE_TIMEOUT_S` with the sampled count and bytes displayed; a directory above `DATASET_MAX_MEMBERS` is refused whole with the cap named.
- **AC2.** Roles and `is_sample` default by convention and are editable; unsupported members are `other` with a visible reason; no card ever stays in Processing without a member-level reason.
- **AC3.** Publishing produces one local-route listing version with no `s3_connection`, `object_count = data_member_count`, a `manifest_hash` the receiver recomputes and verifies (count/size/path/hash tampering refused), the sample members in the disclosure snapshot and served by the sample-file route; an all-documentation upload is refused; legacy no-version local listings and the S3 route are unchanged.
- **AC4.** A purchase delivers every data member under one `TransferManifest` with per-member hash verification; tests cover resume after a middle-member failure, duplicate/replayed chunks, changed path/hash/size, missing final member and 10,000+ members; the order is `delivered` only when every member matches; a one-member dataset delivers exactly as today.
- **AC5.** A paid verification over the directory produces one accepted report whose `coverage.objects_discovered` equals the data-member count and whose skip reasons are only the S1590 enum; both schemas validate unchanged; a role edit after publish does not change scan scope; the S1590 privacy and payment tests pass unchanged.
- **AC6.** Listing, sample and delivery all complete for a seller who never opens the verification panel; the publish request carries no verification field; the panel is headed "Optional: add a verified shape label"; the runbook's §B first sentence says so.
- **AC7.** Existing single-file datasets/listings (Sergey's June listing, Max's listing 936a08d6) are unaffected before and after upgrade: a copied real-install fixture with published and unpublished records sharing a `batch_id` preserves every dataset id, listing id, file path, status and delivery behaviour.
- **AC-final (Gate 4):** Sergey lists the Acid Trap Dataset as one product from his own install on the stable image, with his chosen sample files, and a buyer test account receives the whole set with every hash matching; evidence recorded without customer data.

## 8. Risks

- Large-set delivery over the Trust Channel is the long pole; D5 pins the transfer manifest now so chunk D and S1711 build on one shape, at the cost of an S1681 amendment before D.
- Aggregate listing summaries could mislead if members have different schemas; the summary names the number of schemas found and the member table shows the per-member schema.
- Role and sample defaults will sometimes be wrong; the seller edits before publish and the frozen manifest is the record.
- The receiver-side member upload for 21,000 members adds a chunked publish step; it reuses the workspace index's chunking and caps, and the publish is atomic on the final hash check.
- The directory-root resolver case is the one place D6 touches S1590-adjacent code; the precedent is the shipped S3 prefix root, and any contract question is raised as an amendment rather than discovered at Gate 3.
