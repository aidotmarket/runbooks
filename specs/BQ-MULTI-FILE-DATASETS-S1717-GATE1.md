## 1. Problem

A seller's product is a directory: data blocks, a free sample, a README, a description, sometimes thousands of files. Today every layer models a product as one file:

- AIM Data has two directory-capable ingestion paths and both end in one `DatasetRecord` per file: bulk upload (`aim-data:app/routers/datasets.py:426`, `:512-545`, BQ-108) and directory import (`aim-data:app/routers/imports.py:39-74`, `:87-111` — `POST /imports/scan` and `/imports/start`; `app/services/import_service.py:52-59` `ImportFileEntry.relative_path`, `:146-164` hidden/junk/symlink/unsupported skips, `:176-197` one record per file). The import scanner (`import_service.py:121-145`) has three silent bounds: `depth > max_depth` returns without setting `truncated` (`:136`, default 5, hard cap 10 at `:127`), a 30-second wall clock (`:138-139`), and 10,000 files (`:143-145`); it also drops unsupported extensions to a count with no path (`:155-162`) and silently passes `PermissionError`. A 21,000-file directory yields a truncated set with no refusal. `DatasetRecord` (`aim-data:app/models/dataset.py:39-64`) carries non-nullable file-specific columns (`original_filename`, `storage_filename`, `file_type` at `:42-44`), optional `processed_path` (`:47`), `listing_id`, and `batch_id`/`relative_path` (`:52-54`) that only group notifications; it has no content hash. Processing (`aim-data:app/services/processing_service.py:232`) profiles and runs allAI metadata per record. Publishing (`aim-data:app/routers/marketplace_publish.py:403`) publishes one record as one listing and sets `listing_id` on that record (`:393`, `:415`).
- The publish contract already carries N-object scalars: sender allowlist `VersionPublishEmit` (`aim-data:app/routers/marketplace_publish.py:113-116`: `object_count`, `total_size_bytes`, `manifest_hash`), receiver schema `ai-market-backend:app/schemas/vz_publish.py:133-141` (`object_count` is `ge=0`; `manifest_hash` is opaque; the member list is not on the wire; the payload docstring says "NO raw data"). But only the Seller Workspace S3 route uses it: the versions endpoint is S3-scan-only (`marketplace_publish.py:264-293`, `:512-543`), the receiver materializes a `ListingVersion` only with a non-empty `s3_connection.prefix` (`ai-market-backend:app/services/listing_versioning.py:198-199`), `ListingVersion.prefix` is non-null with `uq_listing_versions_listing_label` and `uq_listing_versions_listing_prefix` and `ck_listing_versions_status IN ('active','superseded','quarantined')` (`ai-market-backend:app/models/marketplace.py:213-240`), the receiver stores the hash and compares it on replay but never recomputes it (`listing_versioning.py:229-246`; duplicates become a new `quarantined` row via `_decide_quarantine`, `:109-121`, `:237-249`), and an ordinary local dataset resolves to `NotS3PublishSource` (`aim-data:app/services/s3_publish_source_resolver.py:93-95`). The route axis is `listings.source_delivery` JSON (`marketplace.py:162`; `is_workspace_source` checks `authority_kind == "workspace_connection"`, `ai-market-backend:app/services/seller_workspace_delivery.py:27-30`; dispatch at `app/services/fulfillment_service.py:184`). The interop record's device-route row pins `object_count == 1` (`specs/SELLER-ROUTE-INTEROP-S1711.md:12`, `:28`); the AIM Data local route has no row there.
- Delivery is one file per order on the local route. AIM Data resolves one artifact (processed Parquet first, then the original upload: `aim-data:app/services/source_artifact_resolver.py:81-88`) and streams it (`aim-data:app/services/fulfillment_service.py:106-163`; single-artifact 500 MB refusal at `:56`, `:176-185`); backend `TransferSession` is "one transfer session per order fulfillment" with one filename, byte total, chunk count and expected SHA-256 (`ai-market-backend:app/models/transfer_session.py:39-79`, one-hour expiry `:85-87`); the listener accepts one file description (`app/services/fulfillment_listener_service.py:94-188`), refuses `total_bytes > MAX_FILE_SIZE` (500 MB, `:64-65`, `:115-118`), is idempotent on a second complete (`:292-300`), creates one download token per transfer (`:410-433`), and marks the order `delivered` on the first finalized transfer, writing the single `orders.delivery_file_path/hash/size_bytes` (`:435-456`; columns `ai-market-backend:app/models/order.py:171-173`) which the buyer download path reads as a path (`app/services/order_service.py:1245`, `:1285`, `:1296`). The S3 device route is single-object by design authority (`specs/BQ-MONEY-PATH-DELIVERY-LEG-S1681-GATE1.md:455`, G3.4 `:463`; code `fulfillment_service.py:88-93`, `order_service.py:1356-1361`) and the Seller Workspace route already delivers N objects "with all grants withheld until audit commit" (`seller_workspace_delivery.py:1`, over `SellerApprovedSourceIndex`, `MAX_SELECTION_FILES = 50_000`, `app/schemas/seller_source_limits.py`). The buyer download unification item already asks how multi-file grants work (`specs/BQ-BUYER-DOWNLOAD-UNIFICATION-S1711-GATE1.md:34`).
- The paid verification scan (`specs/BQ-DATA-VERIFICATION-S1590-GATE1.md`) traverses "every reachable supported object in the registered root" (`:203`), reports `objects[]` in canonical ascending `object_id` order (signed `traversal_order`, `aim-data:app/services/data_verification/contract.py:113`; validator `ai-market-backend:app/schemas/data_verification.py:685-689`), computes `content_sha256` over the resolved bytes (`aim-data:app/services/data_verification/scanner.py:126-151`) and reports `coverage` with a **closed** skip-reason enum (`:131-132`; `ai-market-backend:app/schemas/data_verification.py:466-487`). Its resolver and receipt are single-artifact (`aim-data:app/services/source_artifact_resolver.py:34-65`; A1 test `:315`), so a directory root is a contract change — decided in the companion amendment.
- The free sample is bounded "approved rows" of the one file (`ai-market-backend:app/schemas/disclosure_snapshot.py:64-91`, `:101-124`; public summary `app/services/disclosure_snapshot_service.py:157-171`). No surface delivers a sample *file*, and no seller bytes are stored on ai.market today.

Consequences: a real seller cannot list a real dataset without merging it by hand; a 21,000-file directory creates up to 10,000 cards (silently dropping the rest) and 10,000 allAI metadata passes; documentation files become "datasets"; and the seller's question ("must I merge?") is the honest answer today. This is the first wall every serious seller hits, before the verified label even enters the picture.

## 2. Decision (design authority)

**D0. One manifest, four consumers.** Every directory dataset has an immutable, versioned **`DatasetManifest`**: an ordered list of members, each `{index, relative_path, size_bytes, sha256, detected_type, role, is_sample}`, plus `member_count`, `data_member_count`, `sample_member_count`, `total_data_bytes`, and `manifest_hash` = SHA-256 over the member list canonicalized with the **existing shared `python-json-sort-compact-v1`** canonicalization (already the signed `canonicalization_version` in both repos) — not a second canonicalization implementation; one golden vector is checked in both repos. `relative_path` is canonical: NFC, forward slashes, no `.`/`..`, no leading slash. `detected_type` is the existing AIM Data file-type value set (`PROCESSABLE_TYPES`) plus `unsupported`. Publish (D3), delivery (D5), verification (D6, companion amendment) and the S1711 buyer door all consume this one manifest, pinned to the published version; the published manifest *is* the immutable per-version snapshot — no surface reads live `dataset_members` after publish. **Retention:** the install keeps every published manifest immutably in its own database (`published_manifests`, keyed by `manifest_hash`, with the member rows it froze), independent of later re-uploads, so a purchased or scanned version can always be resolved locally; ai.market holds the same members from the D3 upload. A manifest is frozen when a version is published; a re-upload produces a new manifest and (if published) a new version.

**D-bytes. One byte-source rule.** A member's bytes are the file at `root_path/relative_path`, where `root_path` is the dataset's member root on the install. For new uploads (single file or directory) that is **the seller's original file as uploaded** — processing produces profiles and previews, never a deliverable; delivery, sample serving and verification all read, hash and stream those same bytes without transformation. Consequence stated plainly: a *new* one-file upload delivers the original file, not today's processed Parquet (today's resolver prefers the Parquet, `source_artifact_resolver.py:81-88`); that is a product decision recorded above for Max. Legacy behaviour is preserved by D1a.

**D1. A dataset is a directory.** One `DatasetRecord` represents an uploaded directory tree (a single file is the one-member case). Members live in a new `dataset_members` table (one row per file: the D0 fields plus `status`, `reason`; current-member identity is **unique by `(dataset_id, relative_path)`**, with `sha256` compared on re-upload to detect change). The file-specific non-nullable columns on `DatasetRecord` get an explicit directory-mode contract at Gate 2 (directory name, `root_path`, `file_type = "directory"`). Each member has a **role** — `data`, `documentation`, `other` — and an independent **`is_sample`** flag. Roles are suggested by convention and always editable before publish (`README*`, `HOW_TO_USE*`, `*DESCRIPTION*`, `LICENSE*` → `documentation`; `detected_type = unsupported` → `other`, never processed, never delivered unless the seller marks it `data`; everything else → `data`). **`is_sample` is set only by the seller** (D4); no convention ever sets it. Role and sample selection are frozen into the manifest at publish.

**D1a. Migration invariant (AC7).** Every existing `DatasetRecord` becomes a one-member directory whose member obeys D-bytes with **one binding**: the migration selects the file the existing resolver selects (`processed_path`, else the standard processed Parquet, else the original upload), sets `root_path` = that file's directory and `relative_path` = its basename, and computes `size_bytes`/`sha256` over it; `role = data`, `is_sample = false` unconditionally, `detected_type = file_type`. So `(root_path, relative_path, sha256)` names exactly the bytes delivery and verification use today, and a later republish, scan and delivery of the migrated dataset all read that same file. When none of the three files exists the member is `status = missing` and no manifest is built until the seller re-uploads. A re-upload of a migrated dataset registers the new original files under D-bytes (every migrated member is expected to compare as changed; that is a new manifest, not an error). The member table shows the migrated member under that basename (for example `<dataset_id>.parquet`) so the seller sees exactly what a republish would sell. If a pinned member file disappears after publish, delivery and verification fail closed; the seller is notified in AIM Data and the repair is to re-upload and publish a new version — the affected order follows the existing undeliverable-order handling, nothing is silently substituted. Existing rows are never merged by `batch_id`; dataset ids, listing ids, file paths, statuses and delivery behaviour are unchanged. **Legacy listings without a `ListingVersion` stay on the existing single-file delivery and verification branches** (no `ListingVersion` is fabricated; the manifest is used only from the next publish onward). Directory semantics apply to new uploads only; any retrospective consolidation of old rows is a separate, explicitly approved repair flow.

**D2. Processing is per directory, bounded.** Profiling, PII scan and allAI metadata run once per dataset over a deterministic subset of `data` members. The policy is a set of named fields whose values Gate 2 pins as an appendix: `PROFILE_MAX_MEMBERS`, `PROFILE_MAX_MEMBER_BYTES`, `PROFILE_MAX_TOTAL_BYTES`, `PROFILE_TIMEOUT_S`, ordering = ascending `sha256` with `relative_path` tie-break, allAI calls per dataset = 1, and the behaviour when no member fits the cap (terminal `profiling_skipped` with reason; listing still allowed with an explicit "not profiled" summary). The analogous S3 bound (`aim-data:app/services/s3_scan_service.py:24`, `:40-58`) is the model; the dataset page states "profiled on N of M files". Documentation members feed the listing description as seller-supplied context (quoted, never executed). The dataset shows one status; per-member failures are recorded as member status with a fixed reason (`unsupported_type`, `too_large`, `parse_failed`, `timeout`) and never leave the dataset spinning.

**D3. One listing per dataset, N objects, local-route version materialization.** The local route emits `VersionPublish` with `object_count = data_member_count`, `total_size_bytes = total_data_bytes` and `manifest_hash` from D0. The route is carried on the existing axis: `listings.source_delivery` gains `authority_kind = "aim_data_local"` for directory publishes (the workspace value is untouched; legacy listings keep `null` and never enter the version path). The receiver materializes a `ListingVersion` for that authority kind without an `s3_connection` prefix: `prefix` becomes nullable with a DB CHECK *`(prefix IS NULL) = (source authority is aim_data_local)`* (stored on the version as `source_kind`; existing versions are backfilled `s3`), `uq_listing_versions_listing_label` is kept, `uq_listing_versions_listing_prefix` becomes a partial unique index `(listing_id, prefix) WHERE prefix IS NOT NULL` (S3/workspace uniqueness unchanged), **no uniqueness on `manifest_hash`** — a re-publish of the same manifest under a new label follows the existing duplicate path and lands as a `quarantined` row exactly as today. `ck_listing_versions_status` gains `pending_members`. The member list reaches the receiver through a chunked, bounded upload modelled on `seller_approved_source_index` (`CHUNK_FILES`, `MAX_SELECTION_FILES`); the version is created `pending_members`, each chunk is validated and stored, and on the final chunk the receiver recomputes `manifest_hash`, `object_count` and `total_size_bytes` over the stored members and either runs the existing quarantine decision and activation atomically or refuses (count/size/path/hash mismatch, duplicate path, non-canonical path). A `pending_members` version never activates, is never delivered, and is garbage-collected after a policy TTL. Publishing requires `data_member_count − sample_member_count ≥ 1`; an all-documentation, all-`other` or all-sample upload is refused before listing. The interop record gains a **new** local-route row when chunk C ships ("`aim_data_local`: `listing_versions` row per signed publish, `prefix NULL`, `object_count == data_member_count`"); its device-route row `:12` and `:28` are untouched. The public listing summary is the aggregate of profiled data members and names the number of distinct schemas found.

**D4. Free sample = seller-chosen data members.** Sample members are `data` members with `is_sample = true`, marked by the seller only; they are delivered to buyers after purchase like every other data member (D5) *and* before purchase through a new bounded **sample-file surface**, owned by chunk C: at publish, AIM Data uploads the sample members to ai.market's listing-asset object store (Gate 2 pins the bucket and the existing storage client) as a disclosure asset bound to the version's `manifest_hash`; `DisclosureSnapshotCreateRequest.sample_decision` gains the literal `member_files` (no list is repeated on the request: the sample members are the `is_sample` rows of the version's stored member list from D3, which is already frozen and hash-verified); bounds `SAMPLE_MAX_FILES`, `SAMPLE_MAX_TOTAL_BYTES` (Gate 2 values) and the D3 paid-set bound apply. Serving: the public listing serves sample members unauthenticated, addressed only by `(version_id, index)` from the approved list, hash-verified before response, always `Content-Type: application/octet-stream` with `Content-Disposition: attachment` (never rendered inline), rate-limited per listing and per client with a per-listing daily byte budget, not enumerable, with no other member reachable. The listing states that sample files are part of the purchased set and free to download. **Lifecycle:** sample URLs serve only while the version is `active` and the listing is published; they stop on supersede, quarantine, listing unpublish/revoke, seller withdrawal or takedown, and the assets are deleted with the version. `approved_rows` remains available and is the default for one-member datasets. S1590's "no raw data leaves the environment" is scoped to the scan conduit; a seller-chosen sample file is the same class of seller-consented public artifact as today's `approved_rows` and does not contradict it.

**D5. Delivery is the whole set, under one transfer manifest (local route only).** A purchase of a local-route directory listing delivers every `data` member. The Trust Channel local route becomes **one transfer session per order carrying N framed members**: the session opens with a `TransferManifest` = `{version_id, manifest_hash, members[]: {index, relative_path, size_bytes, sha256, content_type}}` that must equal the published `DatasetManifest`'s data members; members are streamed sequentially with per-member chunk framing (`member_index` on every chunk), per-member hash verification and resume at member granularity; the order becomes `delivered` only after every member has matched its published hash (`fulfillment_listener_service.py:435-456` changes from first-transfer to all-members completion — the same "withheld until the whole set is committed" rule the workspace route already applies). **Purchased-version binding.** `TransferManifest.version_id` and `orders.delivery_manifest_hash` are taken from `orders.purchased_version_id` (`ai-market-backend:app/models/order.py:164`; resolution `app/services/order_service.py:284-296`) and that version's pinned manifest — never from the currently active version — so a seller superseding the listing between payment and fulfilment cannot change the delivered set. **Order-side records (never overloading shipped columns):** `orders.delivery_file_path/hash/size_bytes` keep their single-file meaning and stay `NULL` for directory orders; a new `orders.delivery_manifest_hash` and a new `order_delivery_members` table (order, index, relative_path, size, sha256, staged path, delivered_at) hold the directory set; `order_service.py:1245` ("Delivery not configured" when `delivery_file_path` is empty) branches on `delivery_manifest_hash` first, so a directory order takes the directory path and a legacy order is byte-identical to today. **Buyer path (interim, shipped by chunk D):** one **order-scoped download grant** per order and purchased version (the existing token model extended with a `manifest_hash` scope; not one token per member), under which the buyer fetches any member by `(order_id, member_index)` from the order endpoint, which returns the member list with per-member addresses. Entitlement is counted **per set, not per member**: `orders.max_downloads`/`downloads_used` (`order.py:174-175`, `order_service.py:428-433`, `:1268-1279`) count grant issuances; the per-order 10-attempts-per-hour log (`app/models/fulfillment_download_token.py:69-81`) applies to grant issuance; member fetches under a valid grant are unlimited in count and bounded by a per-client byte budget (`DOWNLOAD_GRANT_BYTES_PER_HOUR`, Gate 2); the 12-hour grant TTL (`TOKEN_TTL_HOURS`) is renewed by re-issuing the grant, which counts as one download; revocation is one row. On a directory grant the token row's own `download_count`/`max_downloads` (`fulfillment_download_token.py:55-67`) are not consulted (the order-level counters govern) and its `transfer_id` references the N-member session. A directory listing is therefore downloadable member-by-member from the order page on the stable image without waiting for S1711; S1711 later unifies per-file vs archive across routes. **Resource semantics** (values Gate 2): `TRANSFER_MAX_MEMBER_BYTES` (replaces the per-file 500 MB check, applied per member), `TRANSFER_MAX_TOTAL_BYTES` = `DATASET_MAX_BYTES`, `TRANSFER_MANIFEST_MAX_BYTES` (metadata only; member count is bounded by `DATASET_MAX_MEMBERS`, never by this), `TRANSFER_SESSION_TTL_S` renewed on each completed member, resume after expiry by a new session for the same order that acknowledges already-verified members (each resumed member is re-hashed), staging cleanup of orphaned partial members on expiry, and the existing 24-hour finalized-file purge. Missing final member, changed path/hash/size, duplicate or replayed chunks and a mid-set failure are refused or resumed, never presented as complete. **Version carrier and wire change.** S1681 `:208` excludes, verbatim, "Trust Channel protocol, cipher, framing, handshake, ownership or replay-rule changes." This build makes none of those: the change is four additive fields on the `vai.fulfillment.*` **application messages** carried inside the unchanged channel — cloud → device: `purchased_version_id` and `manifest_hash` in the `vai.fulfillment.deliver` parameters (today `{order_id, listing_id, buyer_id, order_number, listing_title, requested_at}`, `ai-market-backend:app/services/fulfillment_service.py:573-585`); device → cloud: a `manifest_hash` on the transfer-open message and `member_index` on the chunk message — not channel framing, ownership or replay rules. The device resolves the member set from its retained published manifest for that hash (D0 retention); a device that does not hold it refuses the delivery naming the version. The listener recomputes `manifest_hash` over the members it receives and compares it to the purchased version's stored members (D3); a mismatch is refused through the existing undeliverable-order path (the order never reaches `delivered`, the seller is notified), never delivered as a different set. The **sender** is AIM Data's device client (`aim-data:app/services/fulfillment_service.py:106-163`, the local-file branch), so chunk D ships an AIM Data release alongside the backend. **Listener mode split and member state machine:** a `vai.fulfillment.metadata` message without `manifest_hash` runs the existing single-file path unchanged (legacy client → new listener: byte-identical). With `manifest_hash`, manifest mode: the metadata scalars (`ai-market-backend:app/schemas/fulfillment.py:21-28`) mean, for the set, `filename` = the dataset directory name, `total_bytes` = `total_data_bytes`, `total_chunks` = the sum of per-member chunk counts, `sha256_hash` = `manifest_hash`; the listener loads the purchased version's stored members (D3) into a new `transfer_session_members` table (index, relative_path, expected size, expected sha256, bytes received, verified_at) and refuses the session if `manifest_hash` differs from the purchased version's. Every `vai.fulfillment.chunk` keeps the existing session-global monotonic `chunk_index` and `byte_offset` (so duplicate/replay detection and ACK/final-chunk logic at `fulfillment_listener_service.py:247-284` are unchanged) and adds `member_index` and `member_byte_offset`; a chunk whose `member_index` is not in the manifest, or whose `member_byte_offset` is not the member's next expected offset, is refused. A member is finalized (`verified_at`) when its received bytes equal its expected size and hash; a hash mismatch refuses the session (never a silent skip). The singular `vai.fulfillment.complete` (`file_size_bytes` = `total_data_bytes`, `chunk_count` = `total_chunks`, `sha256_hash` = `manifest_hash`) is accepted only when every member has `verified_at`; otherwise it is refused and the session stays open for resume. Resume after expiry opens a new session for the same order carrying `manifest_hash` and the list of member indices the device believes verified; the listener re-hashes those members' staged bytes and keeps `verified_at` only where they still match. `transfer_sessions`' single-file columns hold the set-level aggregates above. **Version gate:** the signed publish payload gains an additive `agent_version` field; a directory publish from an AIM Data version below the chunk D release is refused naming the upgrade, so no directory order can ever meet a client that cannot send `member_index`. **The S3 device route and S1681 G3.2 `object_count == 1` are not changed by this build**; the Seller Workspace route already delivers N objects. The buyer download door (S1711) consumes the same manifest with `object_count > 1` as its base case; whether the buyer fetches members individually or as an archive assembled at transfer time from unchanged member bytes (transport packaging, not data transformation) is S1711's decision.

**D6. Verification covers the data members, under the companion S1590 amendment.** For a directory dataset the registered root is the version-pinned data-member set; documentation and `other` members are outside the root and never appear as discovered or skipped; the resolver gains `kind = "local_directory"` with root path plus manifest; the pre-read pass verifies every member against the manifest in manifest order and any mismatch fails closed (`FAILED_VOIDED`, hold voided); `content_sha256` is the path-bound digest of member digests defined in the amendment §1.3(c); the locator commitment is over the canonical root path plus `manifest_hash` (the one CORE S3 sign-off item); the report emits `objects[]` in ascending `object_id` order as today; the skip-reason enum, ordering validator, spec literals, quote minimum, privacy boundary and payment/publication contracts are unchanged. All of this is specified in `specs/BQ-DATA-VERIFICATION-S1590-DIRECTORY-ROOT-AMENDMENT.md`, which is reviewed with this Gate 1 and implemented by chunk E. The listing discloses role counts ("N data files scanned; M documentation files are not part of the data set") outside the scan report.

**D7. The verified label stays voluntary, and says so — as deliverables.** Listing never depends on verification, a card, or a quote (static truth at the pin: `aim-data:frontend/src/pages/DatasetDetail.tsx:1312` gates publish on disclosure/metadata only; the verification panel at `:1323-1327` renders with a possibly-null listing id and at `:1664-1670` only after `preview_ready`; it issues a read-only status GET on render and takes no paid action until clicked; card only at paid start per S1646). Chunk F delivers: the panel heading "Optional: add a verified shape label", visually separated from the publish controls; the first sentence of `data-verification-seller-journey.md` §B stating the whole procedure is optional and seller-initiated (today `:47-49` is a precondition list, not an optionality statement); and an AC6 test asserting the publish request carries no verification field and succeeds with the panel untouched.

**D8. Scale and registration.** 21,000 members must be a normal upload. Registration uses a **new complete, streamed traversal** that reuses only the import scanner's path validation (`validate_import_path`) and its hidden/junk/symlink exclusion policy; it enumerates every other regular file (unsupported extensions and extensionless files become `other` members with their path and size), has no depth cutoff, no wall-clock truncation and no silent file cap; an unreadable entry (`PermissionError` or I/O error) refuses the whole upload naming the entry; the only policy bounds are `DATASET_MAX_MEMBERS` and `DATASET_MAX_BYTES` (Gate 2 values; guidance: ≥ 25,000 members and ≥ 50 GB so the trigger case fits with headroom, set against the listener's staging profile), and reaching either **refuses the whole upload** with a message naming the bound — never a partial member set. Registration is idempotent by `(dataset_id, relative_path)`; re-uploading the same directory compares `sha256` per path and updates changed members only; a member absent from the source on re-upload is marked `removed` (never deleted from a published manifest); two paths equal under case-folding are refused at registration. The UI shows the directory as one card with a paged member table filterable by role/status.

## 3. Non-goals

No change to pricing, commission, payout, the S1590 manifest fields, spec literals, skip-reason enum or privacy boundary, the Seller Workspace S3 publish and delivery model, the S3 device route's single-object binding (S1681 G3.2), `orders.delivery_file_*` semantics, the single-file download-token path, the Trust Channel protocol/cipher/envelope/handshake/replay rules, or the buyer's identity/access rules. No transformation or merging of member bytes anywhere (an archive built at transfer time from unchanged members is packaging, not merging). No cross-dataset bundles. No public per-member browsing beyond the approved sample members.

## 4. Customer-visible behaviour

1. Upload a folder → one card "Acid Trap Dataset" with member count, total size, one status; above a bound or on an unreadable entry, one refusal naming it.
2. Open it → member table with role chips (data / documentation / other) and a sample toggle, per-member status and reason, "Set role" and "Mark as sample" actions; profiling summary "profiled on N of M files"; description drafted from documentation members for the seller to approve.
3. Publish → one listing; buyers see one product with N files, the aggregate summary (with the number of schemas), and the sample files downloadable (stated as part of the purchased set).
4. Buy → all data members delivered; the order page shows a file list with per-file progress, hashes and per-file download; the order is complete only when every file matches.
5. Optional: "Add a verified shape label" → the S1590 flow over the data members; the report's coverage section shows N objects; the listing shows the role counts alongside.
6. Existing single-file datasets and listings keep working unchanged (one-member directories; legacy listings stay on the single-file branch). New single-file uploads deliver the original file (D-bytes).

## 8. Risks

- Large-set delivery over the Trust Channel is the long pole; D5 pins the transfer manifest and resource semantics now so chunk D and S1711 build on one shape; the 21,000-member staging profile is new for the single-instance listener and the `TRANSFER_*` values must be set against it.
- D-bytes changes what a new single-file upload delivers (original file instead of processed Parquet); it is the honest product and is recorded as a decision for Max, and legacy listings are untouched.
- Aggregate listing summaries could mislead if members have different schemas; the summary names the number of schemas found and the member table shows the per-member schema.
- Role defaults will sometimes be wrong; the seller edits before publish and the frozen manifest is the record. Sample exposure is seller-marked only, so no default can make a file public.
- The receiver-side member upload for 21,000 members adds a chunked publish step; it reuses the workspace index's chunking and caps, and activation is atomic on the final hash check.
- The sample-file surface is the first place ai.market stores seller bytes for the local route; it is bounded, index-addressed, hash-verified, attachment-only, lifecycle-bound and limited to what the seller chose to give away.
- The companion S1590 amendment is the one contract change to a shipped, signed path; it is reviewed here rather than discovered at Gate 3, and its single sign-off item is named.
