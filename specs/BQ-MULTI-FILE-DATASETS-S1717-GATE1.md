## 1. Problem

A seller's product is a directory: data blocks, a free sample, a README, a description, sometimes thousands of files. Today every layer models a product as one file:

- AIM Data has two directory-capable ingestion paths and both end in one `DatasetRecord` per file: bulk upload (`aim-data:app/routers/datasets.py:426`, `:512-545`, BQ-108) and directory import (`aim-data:app/routers/imports.py:39-74` — `POST /imports/scan` at `:39`, `/imports/start` at `:53`; `app/services/import_service.py:52-59` `ImportFileEntry.relative_path`, `:146-164` hidden/junk/symlink/unsupported skips, `:176-197` one record per file). The import scanner (`import_service.py:121-145`) has three silent bounds: `depth > max_depth` returns without setting `truncated` (`:136`, default 5, hard cap 10 at `:128`), a 30-second wall clock (`:138-139`), and 10,000 files (`:143-145`); it also drops unsupported extensions to a count with no path (`:155-162`) and silently passes `PermissionError`. A 21,000-file directory yields a truncated set with no refusal. `DatasetRecord` (`aim-data:app/models/dataset.py:39-64`) carries non-nullable file-specific columns (`original_filename`, `storage_filename`, `file_type` at `:42-44`), optional `processed_path` (`:47`), `listing_id`, and `batch_id`/`relative_path` (`:52-54`) that only group notifications; it has no content hash. Processing (`aim-data:app/services/processing_service.py:232`) profiles and runs allAI metadata per record. Publishing (`aim-data:app/routers/marketplace_publish.py:403`) publishes one record as one listing and sets `listing_id` on that record (`:393`, `:415`).
- The publish contract already carries N-object scalars: sender allowlist `VersionPublishEmit` (`aim-data:app/routers/marketplace_publish.py:113-116`: `object_count`, `total_size_bytes`, `manifest_hash`), receiver schema `ai-market-backend:app/schemas/vz_publish.py:133-141` (`object_count` is `ge=0`; `manifest_hash` is opaque; the member list is not on the wire; the payload docstring says "NO raw data"). But only the Seller Workspace S3 route uses it: the versions endpoint is S3-scan-only (`marketplace_publish.py:264-293`, `:512-543`), the receiver materializes a `ListingVersion` only with a non-empty `s3_connection.prefix` (`ai-market-backend:app/services/listing_versioning.py:198-199`), `ListingVersion.prefix` is non-null with `uq_listing_versions_listing_label` and `uq_listing_versions_listing_prefix` and `ck_listing_versions_status IN ('active','superseded','quarantined')` (`ai-market-backend:app/models/marketplace.py:213-240`), the receiver stores the hash and compares it on replay but never recomputes it (`listing_versioning.py:229-246`; duplicates become a new `quarantined` row via `_decide_quarantine`, `:109-121`, `:237-249`), and an ordinary local dataset resolves to `NotS3PublishSource` (`aim-data:app/services/s3_publish_source_resolver.py:93-95`). The route axis is `listings.source_delivery` JSON (`marketplace.py:162`; `is_workspace_source` checks `authority_kind == "workspace_connection"`, `ai-market-backend:app/services/seller_workspace_delivery.py:27-30`; dispatch at `app/services/fulfillment_service.py:184`). The interop record's device-route row pins `object_count == 1` (`specs/SELLER-ROUTE-INTEROP-S1711.md:12`, `:28`); the AIM Data local route has no row there.
- Delivery is one file per order on the local route. AIM Data resolves one artifact (processed Parquet first, then the original upload: `aim-data:app/services/source_artifact_resolver.py:81-88`) and streams it (`aim-data:app/services/fulfillment_service.py:106-163`; single-artifact 500 MB refusal at `:56`, `:176-185`); backend `TransferSession` is "one transfer session per order fulfillment" with one filename, byte total, chunk count and expected SHA-256 (`ai-market-backend:app/models/transfer_session.py:39-79`, one-hour expiry `:85-87`); the listener accepts one file description (`app/services/fulfillment_listener_service.py:94-188`), refuses `total_bytes > MAX_FILE_SIZE` (500 MB, `:64-65`, `:115-118`), is idempotent on a second complete (`:292-300`), creates one download token per transfer (`:410-433`), and marks the order `delivered` on the first finalized transfer, writing the single `orders.delivery_file_path/hash/size_bytes` (`:435-456`; columns `ai-market-backend:app/models/order.py:171-173`) which the buyer download path reads as a path (`app/services/order_service.py:1245`, `:1285`, `:1296`). The S3 device route is single-object by design authority (`specs/BQ-MONEY-PATH-DELIVERY-LEG-S1681-GATE1.md:455`, G3.4 `:463`; code `ai-market-backend:app/services/fulfillment_service.py:88-93`, `app/services/order_service.py:1356-1361`) and the Seller Workspace route already delivers N objects "with all grants withheld until audit commit" (`seller_workspace_delivery.py:1`, over `SellerApprovedSourceIndex`, `MAX_SELECTION_FILES = 50_000`, `app/schemas/seller_source_limits.py`). The buyer download unification item already asks how multi-file grants work (`specs/BQ-BUYER-DOWNLOAD-UNIFICATION-S1711-GATE1.md:34`).
- The paid verification scan (`specs/BQ-DATA-VERIFICATION-S1590-GATE1.md`) traverses "every reachable supported object in the registered root" (`:203`), reports `objects[]` in canonical ascending `object_id` order (signed `traversal_order`, `aim-data:app/services/data_verification/contract.py:113`; validator `ai-market-backend:app/schemas/data_verification.py:685-689`), computes `content_sha256` over the resolved bytes (`aim-data:app/services/data_verification/scanner.py:126-151`) and reports `coverage` with a **closed** skip-reason enum (`:131-132`; `ai-market-backend:app/schemas/data_verification.py:466-487`). Its resolver and receipt are single-artifact (`aim-data:app/services/source_artifact_resolver.py:34-65`; A1 test `:315`), so a directory root is a contract change — decided in the companion amendment.
- The free sample is bounded "approved rows" of the one file (`ai-market-backend:app/schemas/disclosure_snapshot.py:64-91`, `:101-124`; public summary `app/services/disclosure_snapshot_service.py:157-171`). No surface delivers a sample *file*; the only seller bytes ai.market holds for the local route are the post-purchase delivery cache (`fulfillment_listener_service.py:393-397`; the 24-hour purge routine at `:761-788` has no non-test caller at the pin — `git grep` finds only its definition and `tests/test_fulfillment_listener.py`), never a pre-purchase, publicly addressable asset.

Consequences: a real seller cannot list a real dataset without merging it by hand; a 21,000-file directory creates up to 10,000 cards (silently dropping the rest) and 10,000 allAI metadata passes; documentation files become "datasets"; and the seller's question ("must I merge?") is the honest answer today. This is the first wall every serious seller hits, before the verified label even enters the picture.

## 2. Decision (design authority)

**D0. One manifest, four consumers.** Every directory dataset has an immutable, versioned **`DatasetManifest`**: an ordered list of members, each `{index, relative_path, size_bytes, sha256, detected_type, role, is_sample}`, plus `member_count`, `data_member_count`, `sample_member_count`, `total_data_bytes`, and `manifest_hash` = SHA-256 over the member list canonicalized with the **existing shared `python-json-sort-compact-v1`** canonicalization (already the signed `canonicalization_version` in both repos) — not a second canonicalization implementation; one golden vector is checked in both repos. `relative_path` is canonical: NFC, forward slashes, no `.`/`..`, no leading slash. `detected_type` is the existing AIM Data file-type value set (`PROCESSABLE_TYPES`) plus `unsupported`. Publish (D3), delivery (D5), verification (D6, companion amendment) and the S1711 buyer door all consume this one manifest, pinned to the published version; the published manifest *is* the immutable per-version snapshot — no surface reads live `dataset_members` after publish. **Retention:** the install keeps every published manifest immutably in its own database (`published_manifests`, keyed by the composite `(listing_version_id, manifest_hash)` — `manifest_hash` alone is not unique across listings or roots — with the frozen `root_path` and the member rows it froze), independent of later re-uploads, so a purchased or scanned version can always be resolved locally by version plus hash; ai.market holds the same members from the D3 upload. **Capture of the key:** the receiver assigns `version_id` and returns it on the publish response (`ai-market-backend:app/schemas/vz_publish.py:231-245`, `VZPublishVersionResult.version_id`); AIM Data's publish path today drops it (`aim-data:app/routers/marketplace_publish.py:137-140`, `MarketplaceVersionPublishResponse`), so chunk C extends that response model with `version_id` and writes the `published_manifests` row `(version_id, manifest_hash) → {root_path, members}` in the same transaction that records the publish; a publish whose response carries no `version_id` for an `aim_data_local` version is treated as failed and retried, never left unkeyed. A row keyed for a version that later never activates (`pending_members` garbage-collected, D3) is orphan and harmless — nothing ever references it. A manifest is frozen when a version is published; a re-upload produces a new manifest and (if published) a new version.

**D-bytes. One byte-source rule.** A member's bytes are the file at `root_path/relative_path`, where `root_path` is the dataset's member root on the install. For new uploads (single file or directory) that is **the seller's original file as uploaded** — processing produces profiles and previews, never a deliverable; delivery, sample serving and verification all read, hash and stream those same bytes without transformation. Consequence stated plainly: a *new* one-file upload delivers the original file, not today's processed Parquet (today's resolver prefers the Parquet, `source_artifact_resolver.py:81-88`); that is a product decision recorded above for Max. Legacy behaviour is preserved by D1a.

**D1. A dataset is a directory.** One `DatasetRecord` represents an uploaded directory tree (a single file is the one-member case). Members live in a new `dataset_members` table (one row per file: the D0 fields plus `status`, `reason`; current-member identity is **unique by `(dataset_id, relative_path)`**, with `sha256` compared on re-upload to detect change). The file-specific non-nullable columns on `DatasetRecord` get an explicit directory-mode contract at Gate 2 (directory name, `root_path`, `file_type = "directory"`). Each member has a **role** — `data`, `documentation`, `other` — and an independent **`is_sample`** flag. Roles are suggested by convention and always editable before publish (`README*`, `HOW_TO_USE*`, `*DESCRIPTION*`, `LICENSE*` → `documentation`; `detected_type = unsupported` → `other`, never processed, never delivered unless the seller marks it `data`; everything else → `data`). **`is_sample` is set only by the seller** (D4); no convention ever sets it. Role and sample selection are frozen into the manifest at publish.

**D1a. Migration invariant (AC7).** Every existing `DatasetRecord` becomes a one-member directory whose member obeys D-bytes with **one binding**: the migration selects the file the existing resolver selects (`processed_path`, else the standard processed Parquet, else the original upload), sets `root_path` = that file's directory and `relative_path` = its basename, and computes `size_bytes`/`sha256` over it; `role = data`, `is_sample = false` unconditionally, `detected_type = file_type`. So `(root_path, relative_path, sha256)` names exactly the bytes delivery and verification use today, and a later republish, scan and delivery of the migrated dataset all read that same file. When none of the three files exists the member is `status = missing` and no manifest is built until the seller re-uploads. A re-upload of a migrated dataset registers the new original files under D-bytes (every migrated member is expected to compare as changed; that is a new manifest, not an error). The member table shows the migrated member under that basename (for example `<dataset_id>.parquet`) so the seller sees exactly what a republish would sell. If a pinned member file disappears after publish, delivery and verification fail closed; the seller is notified in AIM Data and the repair is to re-upload and publish a new version — the affected order follows the existing undeliverable-order handling, nothing is silently substituted. Existing rows are never merged by `batch_id`; dataset ids, listing ids, file paths, statuses and delivery behaviour are unchanged. **Legacy listings without a `ListingVersion` stay on the existing single-file delivery and verification branches** (no `ListingVersion` is fabricated; the manifest is used only from the next publish onward). Directory semantics apply to new uploads only; any retrospective consolidation of old rows is a separate, explicitly approved repair flow.

**D2. Processing is per directory, bounded.** Profiling, PII scan and allAI metadata run once per dataset over a deterministic subset of `data` members. The policy is a set of named fields whose values Gate 2 pins as an appendix: `PROFILE_MAX_MEMBERS`, `PROFILE_MAX_MEMBER_BYTES`, `PROFILE_MAX_TOTAL_BYTES`, `PROFILE_TIMEOUT_S`, ordering = ascending `sha256` with `relative_path` tie-break, allAI calls per dataset = 1, and the behaviour when no member fits the cap (terminal `profiling_skipped` with reason; listing still allowed with an explicit "not profiled" summary). The analogous S3 bound (`aim-data:app/services/s3_scan_service.py:24`, `:40-58`) is the model; the dataset page states "profiled on N of M files". Documentation members feed the listing description as seller-supplied context (quoted, never executed). The dataset shows one status; per-member failures are recorded as member status with a fixed reason (`unsupported_type`, `too_large`, `parse_failed`, `timeout`) and never leave the dataset spinning.

**D3. One listing per dataset, N objects, local-route version materialization.** The local route emits `VersionPublish` with `object_count = data_member_count`, `total_size_bytes = total_data_bytes` and `manifest_hash` from D0. The route is carried on the existing axis: `listings.source_delivery` gains `authority_kind = "aim_data_local"` for directory publishes (the workspace value is untouched; legacy listings keep `null` and never enter the version path). The receiver materializes a `ListingVersion` for that authority kind without an `s3_connection` prefix: `prefix` becomes nullable with a DB CHECK *`(prefix IS NULL) = (source authority is aim_data_local)`* (stored on the version as `source_kind`; existing versions are backfilled `s3`), `uq_listing_versions_listing_label` is kept, `uq_listing_versions_listing_prefix` becomes a partial unique index `(listing_id, prefix) WHERE prefix IS NOT NULL` (S3/workspace uniqueness unchanged), **no uniqueness on `manifest_hash`** — a re-publish of the same manifest under a new label follows the existing duplicate path and lands as a `quarantined` row exactly as today. `ck_listing_versions_status` gains `pending_members`. The member list reaches the receiver through a chunked, bounded upload modelled on `seller_approved_source_index` (`CHUNK_FILES`, `MAX_SELECTION_FILES`); the version is created `pending_members`, each chunk is validated and stored, and on the final chunk the receiver recomputes `manifest_hash`, `object_count` and `total_size_bytes` over the stored members and either runs the existing quarantine decision and activation atomically or refuses (count/size/path/hash mismatch, duplicate path, non-canonical path). A `pending_members` version never activates, is never delivered, and is garbage-collected after a policy TTL. Publishing requires `data_member_count − sample_member_count ≥ 1`; an all-documentation, all-`other` or all-sample upload is refused before listing. The interop record gains a **new** local-route row when chunk C ships ("`aim_data_local`: `listing_versions` row per signed publish, `prefix NULL`, `object_count == data_member_count`"); its device-route row `:12` and `:28` are untouched. The public listing summary is the aggregate of profiled data members and names the number of distinct schemas found.

**D4. Free sample = seller-chosen data members.** Sample members are `data` members with `is_sample = true`, marked by the seller only; they are delivered to buyers after purchase like every other data member (D5) *and* before purchase through a new bounded **sample-file surface**, owned by chunk C: at publish, AIM Data uploads the sample members to ai.market's listing-asset object store (Gate 2 pins the bucket and the existing storage client) as a disclosure asset bound to the version's `manifest_hash`; `sample_decision` gains the literal `member_files` (no list is repeated on the request: the sample members are the `is_sample` rows of the version's stored member list from D3, which is already frozen and hash-verified). **Enforcement sites (all chunk C):** AIM Data sender `aim-data:app/routers/marketplace_publish.py:93` (`Literal["none","approved_rows"]`) and the branch at `:445`; backend request `ai-market-backend:app/schemas/disclosure_snapshot.py:105`, public summary `:96`, `:136`; database CHECKs `app/models/disclosure_snapshot.py:18-27` (`sample_decision IN (...)` and the `approved_sample` null pairing — `member_files` pairs with `approved_sample IS NULL`) with a migration; the Hugging Face card response `app/schemas/disclosure_snapshot.py:178` (`DisclosureHFCardResponse.sample_decision` literal widened; the card shows the sample-file count) and the HF publish decision `app/services/huggingface_service.py:681-687` (`_has_approved_sample_rows`, callers `:476`, `:549`): for `member_files` the HF repo is published **metadata-only** by design (`rows_published = 0`; sample *files* are served only from the ai.market listing, never mirrored to HF) and the card states that; the rows-sample service `app/services/disclosure_snapshot_service.py:118` (`member_files` answers the rows-sample route with the same 409 `no_approved_sample_rows` as `none` — that route is rows-only) and `:151` (unchanged: `approved_sample` is null); the AIM Data publish control `aim-data:frontend/src/pages/DatasetDetail.tsx:1312` (`sampleDecision === "approved_rows"` gate extended to accept `member_files`); bounds `SAMPLE_MAX_FILES`, `SAMPLE_MAX_TOTAL_BYTES` (Gate 2 values) and the D3 paid-set bound apply. Serving: the public listing serves sample members unauthenticated, addressed only by `(version_id, index)` from the approved list, hash-verified before response, always `Content-Type: application/octet-stream` with `Content-Disposition: attachment` (never rendered inline), rate-limited per listing and per client with a per-listing daily byte budget, not enumerable, with no other member reachable. The listing states that sample files are part of the purchased set and free to download. **Lifecycle:** sample URLs serve only while the version is `active` and the listing is published; they stop on supersede, quarantine, listing unpublish/revoke, seller withdrawal or takedown, and the assets are deleted with the version (including a `pending_members` version that is garbage-collected without activating). `approved_rows` remains available and is the default for one-member datasets. S1590's "no raw data leaves the environment" is scoped to the scan conduit; a seller-chosen sample file is the same class of seller-consented public artifact as today's `approved_rows` and does not contradict it.

**D5. Delivery is the whole set, under one transfer manifest (local route only).** A purchase of a local-route directory listing delivers every `data` member. **Purchased-version binding.** The deliver request and the order carry `orders.purchased_version_id` (`ai-market-backend:app/models/order.py:164`; written at order creation `app/services/order_service.py:221-283`, `api/v1/endpoints/checkout.py:230`; read `:284-296`) and that version's `manifest_hash` (`orders.delivery_manifest_hash`, written at order creation **only when the purchased version's `source_kind` is `aim_data_local`**; device-S3 and workspace orders keep it `NULL` and their shipped paths) — never the currently active version — so a seller superseding the listing between payment and fulfilment cannot change the delivered set. **Wire change (exact).** S1681 `:208` excludes, verbatim, "Trust Channel protocol, cipher, framing, handshake, ownership or replay-rule changes." This build makes none of those: it adds four fields to the `vai.fulfillment.*` **application messages** carried inside the unchanged channel — cloud → device: `purchased_version_id` and `manifest_hash` in the `vai.fulfillment.deliver` parameters (today `{order_id, listing_id, buyer_id, order_number, listing_title, requested_at}`, `ai-market-backend:app/services/fulfillment_service.py:573-585`); device → cloud: `manifest_hash` on `vai.fulfillment.metadata` and `member_index` on `vai.fulfillment.chunk` (`app/schemas/fulfillment.py:21-55`) — plus one key, `verified_member_indices`, in the `data` payload of the existing metadata *response* (`handle_metadata` returns a dict at `fulfillment_listener_service.py:188`, wrapped as `TrustActionResponse.data` at `ai-market-backend:app/api/v1/endpoints/trust_websocket.py:1362-1367`, `app/schemas/trust.py:318`; there is no metadata ACK message — `FulfillmentAckMessage`, `app/schemas/fulfillment.py:124-129`, is chunk-scoped). No new action or message type; nothing else changes on the wire. **Sender:** AIM Data's device client (`aim-data:app/services/fulfillment_service.py:106-163`, local branch) resolves the member set from its retained manifest for `(purchased_version_id, manifest_hash)` (D0 retention); a device that does not hold it refuses the delivery naming the version. Chunk D ships an AIM Data release alongside the backend. **Listener mode is order-derived:** if the order has `delivery_manifest_hash` (equivalently, the purchased version has stored members), the listener requires manifest mode and refuses a metadata message without `manifest_hash`, or with a different one, **before creating a session** (the order stays undelivered, seller notified); if the order has none, the existing single-file path runs unchanged and a `manifest_hash` on metadata is refused. The device therefore cannot select the mode. **Manifest-mode metadata scalars** (`FulfillmentMetadataParams`, `:21-28`): `filename` = the dataset directory name, `content_type` = `application/octet-stream`, `total_bytes` = `total_data_bytes`, `total_chunks` = the sum of per-member chunk counts at `chunk_size`, which in manifest mode is **pinned to 65536** (`FulfillmentMetadataParams.chunk_size`, `:26`, is device-supplied and unbounded today; any other declared value is refused before session creation so the plan scale is not device-chosen), `sha256_hash` = `manifest_hash`, `hash_algorithm` = `sha256` (pinned like `chunk_size`: any other declared value is refused before session creation — today it is defaulted and never consulted, `schemas/fulfillment.py:28`). **One open manifest-mode session per order:** a session is *open* exactly while its status is `receiving`. The pin's terminal transitions all apply: COMPLETE (`:406`), FAILED on `vai.fulfillment.error` (`:514`), on a hash failure at complete (`:381`) or on ACK timeout (`:744-751`), and TIMED_OUT by the idle sweeper (`cleanup_stale_partials`, `:793-841`, `PARTIAL_TIMEOUT_MINUTES` `:69`, statuses at `:811`/`:832`); manifest mode adds TTL expiry (`TRANSFER_SESSION_TTL_S`) and the chunk path keeps refusing any non-`receiving` session (`:223-224`). In manifest mode the idle sweeper marks the session TIMED_OUT but **never unlinks order-directory files** (the shipped sweeper unlinks `<transfer_id>.partial` at `:806`) — only the expiry cleanup removes unverified `.partial` files, and nothing removes verified members before `delivered`. When a new session starts for the order, the abandoned session's `transfer_chunk_receipts` and `transfer_session_members` rows are swept. A metadata message for an order with an open session and the **same** `manifest_hash` is answered idempotently with that session's `transfer_id` and current `verified_member_indices` (the recovery for a lost metadata response); one with a different `manifest_hash`, or a new `transfer_id` while a session is open, is refused (today only a duplicate `transfer_id` is refused, `:120-126`), so two writers never share the order directory. **`vai.fulfillment.error` in manifest mode** aborts the *session* only — the order stays undelivered and resumable — unless the device reports that it holds no manifest for the version, which is permanent and marks the order `delivery_failed` as the shipped handler does (`:482-535`). The listener loads the purchased version's stored members (D3) into a new `transfer_session_members` table (index, relative_path, expected size, expected sha256, frozen start offset, expected chunk count, `bytes_received`, `verified_at`) with a member-level `chunks_received` count (no session-level counter); **layout:** one **order-owned directory** `STAGING_DIR/orders/<order_id>/`, created on the first chunk with its parent fsynced, holds every member for the life of the order — a member is written under the temporary name `<member_index>.partial` and atomically renamed to its final name `<member_index>` in the same directory when verified (the shipped `STAGING_DIR/<transfer_id>.partial` at `:179`, `:252`, `:360` is single-file and per-transfer; the shipped final-directory rename at `:393-397` never syncs a directory), so a resumed session finds the previous session's verified members and no cross-directory migration ever happens. **`TransferManifest`** is not a separate wire object: it is the purchased version's stored member list `{index, relative_path, size_bytes, sha256}` on both sides, identified by `manifest_hash`. **Chunk plan, receipts and arrival semantics:** the chunk plan is frozen from the member list: members in manifest order, each split at `chunk_size` (last chunk short), chunk indices numbered consecutively across members, so every `chunk_index` maps deterministically to one `(member_index, member byte range, length)` known to both sides; start offsets are the cumulative data-member sizes. Every `vai.fulfillment.chunk` keeps the session-global `chunk_index` and `byte_offset` and adds `member_index`; the listener validates all three against the plan and refuses any chunk that disagrees (wrong member for that index, range crossing a boundary, length or offset off-plan). **Receipts (manifest mode only):** a new `transfer_chunk_receipts` relation, unique on `(session_id, chunk_index)`, records `chunk_sha256` on first arrival (`INSERT … ON CONFLICT DO NOTHING`; member index, byte range and length are derivable from the plan, so they are not stored). **Order of operations per chunk:** validate against the plan → verify `chunk_sha256` over the payload → look up the receipt; if a receipt exists, compare its `chunk_sha256` — equal (a resend under the same or a fresh `message_id`) is acknowledged idempotently and **nothing is written**, different is refused and nothing is written; if none exists, write the payload at `byte_offset − start_offset(member_index)` into the member's staging file (the same seek-tolerant write as the single-file path) **and fsync it**, then insert the receipt and advance the member's `bytes_received` and `chunks_received` in one transaction. **Filesystem durability:** a member's `.partial` file is created (or truncated) once, on its first chunk, and the order directory is fsynced after creation before that first receipt may commit (a file fsync alone does not make a new directory entry durable — the shipped path at `fulfillment_listener_service.py:178-182` never syncs the directory); chunks for an order that is already `delivered` are refused. A receipt therefore implies durable bytes at the right range; a crash after the write but before the receipt is repaired by an ordinary retry (same bytes rewritten, receipt inserted once); a crash before the write leaves no receipt. Out-of-order and retried arrivals are counted exactly once and a finalized member can never be overwritten. **Zero-byte member:** one zero-length chunk in the plan, matching the shipped sender (`aim-data:app/services/fulfillment_service.py:191-193`). This is O(1) state per chunk (one indexed insert, one row update); in manifest mode neither `transfer_sessions.chunks_received` nor `message_ids_seen` is rewritten per chunk (both are per-chunk JSONB list rewrites at `transfer_session.py:75`, `:82`, listener `:261-274`; the completion-time read at `:349-358` is likewise not used — quadratic at the target scale of ≥ 50 GB / 64 KiB ≈ 800,000 chunks); `message_ids_seen` is, at the pin, written on metadata (`:173`) and per chunk (`:261-270`) and read only on the chunk path (`:231-233`); `handle_complete` never consults it (its idempotence is the existing-token check, `:340-347`). In manifest mode the chunk path neither appends to nor consults it — chunk idempotence is the receipt relation (equal receipt idempotent under the same or a fresh `message_id`; conflicting reuse, including under the same `message_id`, refused). This replaces the shipped *application-handler* duplicate-chunk rule for directory orders only; it is fulfillment application idempotence, not the Trust Channel envelope replay rule (which lives at the websocket/transcript layer and is untouched), and is recorded under Decisions (0) for Max. The metadata write and the complete-message idempotence are unchanged; the legacy single-file path is byte-identical. `transfer_sessions`' single-file columns hold the set-level aggregates above, except `file_path`, which is **`NULL` for directory orders**: the shipped 24-hour purge selects `file_path IS NOT NULL` and `rmtree`s `file_path.parent` (`:761-791`), which under the new layout would remove *sibling* orders' delivered sets; directory orders are purged by an order-level sweep rooted at `STAGING_DIR/orders/<order_id>/` keyed on the order's `delivered_at` plus the same 24-hour window. **Trigger (chunk D):** the shipped purge/sweeper routines (`cleanup_expired_files` `:761`, `cleanup_stale_partials` `:793`, `cleanup_orphaned_partials` `:844`) have no non-test caller at the pin, so chunk D registers one scheduler job that runs them and the new order-level sweep; until it ships, nothing in the repository bounds delivered staging. The legacy single-file path keeps `chunks_received`, `message_ids_seen`, `file_path` and its purge exactly as shipped. A member is finalized when its receipt count equals its expected chunk count, `bytes_received` equals its expected size, and its staged bytes hash to the expected SHA-256: the listener then atomically renames `<member_index>.partial` → `<member_index>` in the order directory, fsyncs that directory, and only then records `verified_at`. **Reconciliation (idempotent, under the per-order lock), with bounded scope:** (a) *on metadata and complete only* — an order already `delivered` is answered idempotently (existing grant); a chunk for a `delivered` order is refused; (b) *on every message* — by one indexed query, every member whose receipt count equals its expected chunk count and whose `verified_at` is null is hashed from `.partial` (or from its final name if the rename already happened), renamed and fsynced if needed, and `verified_at` recorded — or, on mismatch, reset by the member repair below (for a chunk message this is at most the message's own member plus any member left in that state by a crash); (c) *at metadata (session start) and inside the completion transaction only* — every member with `verified_at` whose final-name file is missing is reset (a full existence sweep is O(verified members) and is never run per chunk, so per-chunk work remains one indexed insert, one row update and one indexed query). This closes every durable post-receipt state — including a crash after the last receipt commit and before finalization, where receipts would otherwise block every resend — so no member can stay receipted-but-unfinalized. **One rule for a member hash mismatch:** the member is reset (repair below), the session stays `receiving`, and the next metadata response lists it as unverified; mismatch never aborts the session and is never a silent skip. **Completion predicate:** every member row has `verified_at`. **Completion transaction:** on the complete message the listener re-hashes every member against the frozen manifest from wherever its bytes are (final name if present, else `.partial`; the set-level counterpart of the shipped whole-file check at `:364-374`; bounded by `TRANSFER_MAX_MEMBER_BYTES` per member), and only then, in one transaction, writes `order_delivery_members`, marks the order `delivered` and issues the grant; the grant serves only files at final names in the order directory. **Immutability applies from `delivered`:** after that commit nothing writes in the order directory (chunks refused, repair impossible); before it, the member repair below may delete and rewrite a member. No file moves at completion, so there is no rename-before-commit window; any member that no longer matches refuses completion. **Repair of a failed member (before `delivered` only):** because existing receipts block every resend for that member, the listener deletes that member's receipts and its file (temporary or final name), resets its `bytes_received`, `chunks_received` and `verified_at`, and reports it as unverified (in the completion refusal and in `verified_member_indices` on the next metadata response), so the device streams that member again in the same session or a new one. A re-sent in-plan chunk with altered bytes is therefore refused at the receipt *and* could never reach the buyer. The singular `vai.fulfillment.complete` (`file_size_bytes` = `total_data_bytes`, `chunk_count` = `total_chunks`, `sha256_hash` = `manifest_hash`) is accepted only when the predicate holds; otherwise it is refused and the session stays open for resume. The order becomes `delivered` only then (`fulfillment_listener_service.py:435-456` changes from first-transfer to all-members completion — the same "withheld until the whole set is committed" rule the workspace route already applies). **Resume:** after expiry the device opens a new session for the same order with the same `manifest_hash`; the listener re-hashes its own staged member files, keeps `verified_at` only where they still match, and returns `verified_member_indices` in the metadata response's `data` payload so the device streams only the rest — no device-supplied claim is trusted. **Staging retention:** verified members' staged files are retained for the order until the grant is issued and then under the existing 24-hour finalized-file purge; on session expiry only *unverified* partial member files are cleaned, so a resume can reuse verified members. **Order-side records (never overloading shipped columns):** `orders.delivery_file_path/hash/size_bytes` keep their single-file meaning and stay `NULL` for directory orders; `orders.delivery_manifest_hash` and a new `order_delivery_members` table (order, index, relative_path, size, sha256, staged path, delivered_at) hold the directory set; `order_service.py:1245` ("Delivery not configured" when `delivery_file_path` is empty) branches on `delivery_manifest_hash` first, so a directory order takes the directory path and a legacy order is byte-identical to today. **Buyer path (interim, shipped by chunk D):** one **order-scoped download grant** per order and purchased version (the existing token model extended with a `manifest_hash` scope; not one token per member), under which the buyer fetches any member by `(order_id, member_index)` from the order endpoint, which returns the member list with per-member addresses. Entitlement is counted **per set, not per member**: `orders.max_downloads`/`downloads_used` (`order.py:174-175`, `order_service.py:428-433`, `:1268-1279`) count grant issuances; the per-order 10-attempts-per-hour log (`app/models/fulfillment_download_token.py:69-81`) applies to grant issuance; member fetches under a valid grant are unlimited in count and bounded by a per-client byte budget (`DOWNLOAD_GRANT_BYTES_PER_HOUR`, Gate 2); the 12-hour grant TTL (`TOKEN_TTL_HOURS`) is renewed by re-issuing the grant, which counts as one download; revocation is one row. On a directory grant the token row's own `download_count`/`max_downloads` (`ai-market-backend:app/models/fulfillment_download_token.py:59-60`) are not consulted (the order-level counters govern) and its `transfer_id` references the N-member session. A directory listing is therefore downloadable member-by-member from the order page on the stable image without waiting for S1711; S1711 later unifies per-file vs archive across routes. **Resource semantics** (values Gate 2): `TRANSFER_MAX_MEMBER_BYTES` (replaces the per-file 500 MB check, applied per member), `TRANSFER_MAX_TOTAL_BYTES` = `DATASET_MAX_BYTES`, `TRANSFER_SESSION_TTL_S` renewed on each completed member, staging cleanup of orphaned partial members on expiry, and the existing 24-hour finalized-file purge. Missing final member, changed path/hash/size, duplicate or replayed chunks and a mid-set failure are refused or resumed, never presented as complete. **Version gate:** the signed publish payload gains **one top-level, optional** `agent_version` field on `VZPublishPayload` (`ai-market-backend:app/schemas/vz_publish.py:144-184`, `extra="forbid"`, so the field is added there; it is *not* added to the nested `VersionPublish` `:133-141` or to `VersionPublishEmit`), injected by AIM Data's canonical `_build_publish_payload` (`aim-data:app/routers/marketplace_publish.py:215-228`) — enforcement sites chunk C/D. It is required and threshold-checked only when the payload publishes an `aim_data_local` version; existing S3/workspace publishes without it remain accepted and byte-identical in behaviour. A directory publish from an AIM Data version below the chunk D release is refused with a named-upgrade error (not a schema 422), so no directory order can ever meet a client that cannot send `member_index`. **The S3 device route and S1681 G3.2 `object_count == 1` are not changed by this build**; the Seller Workspace route already delivers N objects. The buyer download door (S1711) consumes the same member list with `object_count > 1` as its base case; whether the buyer fetches members individually or as an archive assembled at transfer time from unchanged member bytes (transport packaging, not data transformation) is S1711's decision.

**D6. Verification covers the data members, under the companion S1590 amendment.** For a directory dataset the registered root is the version-pinned data-member set; documentation and `other` members are outside the root and never appear as discovered or skipped; the resolver gains `kind = "local_directory"` with root path plus manifest; the pre-read pass verifies every member against the manifest in manifest order and any mismatch fails closed (`FAILED_VOIDED`, hold voided); parity with delivery holds exactly when the scanned `listing_version_id` equals the order's `purchased_version_id`; `content_sha256` is the path-bound digest of member digests defined in the amendment §1.3(c) and member ids use the manifest-independent §1.3(b) binding; the locator commitment is over the canonical root path plus `manifest_hash` (§1.3(a)–(c) — locator, member-id and content-hash preimages — are the CORE S3 sign-off items); the report emits `objects[]` in ascending `object_id` order as today; the skip-reason enum, ordering validator, spec literals, quote minimum, privacy boundary and payment/publication contracts are unchanged. All of this is specified in `specs/BQ-DATA-VERIFICATION-S1590-DIRECTORY-ROOT-AMENDMENT.md`, which is reviewed with this Gate 1 and implemented by chunk E. The listing discloses role counts ("N data files scanned; M documentation files are not part of the data set") outside the scan report.

**D8. Scale and registration.** 21,000 members must be a normal upload. Registration uses a **new complete, streamed traversal** that reuses only the import scanner's path validation (`validate_import_path`) and its hidden/junk/symlink exclusion policy; it enumerates every other regular file (unsupported extensions and extensionless files become `other` members with their path and size), has no depth cutoff, no wall-clock truncation and no silent file cap; an unreadable entry (`PermissionError` or I/O error) refuses the whole upload naming the entry; the only policy bounds are `DATASET_MAX_MEMBERS` and `DATASET_MAX_BYTES` (Gate 2 values; guidance: ≥ 25,000 members and ≥ 50 GB so the trigger case fits with headroom, set against the listener's staging profile), and reaching either **refuses the whole upload** with a message naming the bound — never a partial member set. Registration stats each file before and after hashing it and re-reads (or refuses, naming the entry) a source that changed in between; it is idempotent by `(dataset_id, relative_path)`; re-uploading the same directory compares `sha256` per path and updates changed members only; a member absent from the source on re-upload is marked `removed` (never deleted from a published manifest); two source entries that map to one canonical `relative_path` — equal under case-folding, or distinct byte sequences that normalize to the same NFC string — refuse the whole upload naming the collision, and an entry whose name is not valid UTF-8 refuses the whole upload naming the entry (never a silent drop). The UI shows the directory as one card with a paged member table filterable by role/status.

## 4. Customer-visible behaviour

1. Upload a folder → one card "Acid Trap Dataset" with member count, total size, one status; above a bound or on an unreadable entry, one refusal naming it.
2. Open it → member table with role chips (data / documentation / other) and a sample toggle, per-member status and reason, "Set role" and "Mark as sample" actions; profiling summary "profiled on N of M files"; description drafted from documentation members for the seller to approve.
3. Publish → one listing; buyers see one product with N files, the aggregate summary (with the number of schemas), and the sample files downloadable (stated as part of the purchased set).
4. Buy → all data members delivered; the order page shows a file list with per-file progress, hashes and per-file download; the order is complete only when every file matches.
5. Optional: "Add a verified shape label" → the S1590 flow over the data members; the report's coverage section shows N objects; the listing shows the role counts alongside.
6. Existing single-file datasets and listings keep working unchanged (one-member directories; legacy listings stay on the single-file branch). New single-file uploads deliver the original file (D-bytes).

## 8. Risks

- Large-set delivery over the Trust Channel is the long pole; D5 pins the transfer manifest and resource semantics now so chunk D and S1711 build on one shape; the 21,000-member staging profile is new for the single-instance listener and the `TRANSFER_*` values must be set against it.
- D-bytes changes what a new single-file upload delivers (original file instead of processed Parquet); it is the honest product and is recorded as a decision for Max, and legacy listings are untouched.
- Aggregate listing summaries could mislead if members have different schemas; the summary names the number of schemas found and the member table shows the per-member schema.
- Role defaults will sometimes be wrong; the seller edits before publish and the frozen manifest is the record. Sample exposure is seller-marked only, so no default can make a file public.
- The receiver-side member upload for 21,000 members adds a chunked publish step; it reuses the workspace index's chunking and caps, and activation is atomic on the final hash check.
- The sample-file surface is the first place ai.market stores seller bytes for the local route; it is bounded, index-addressed, hash-verified, attachment-only, lifecycle-bound and limited to what the seller chose to give away.
- The companion S1590 amendment is the one contract change to a shipped, signed path; it is reviewed here rather than discovered at Gate 3, and its single sign-off item is named.
