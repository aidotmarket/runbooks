Publication writes `ListingVersion(object_count=len(objects), total_size_bytes=sum(size), manifest_hash=approval.source_snapshot['input_hash'])` (`app/services/seller_listing_publication.py:132-135`), `prefix='workspace/<approval_id>/'` (`:133`), `authority_kind='workspace_connection'` (`:137`). The parent's D0 requirement — one frozen manifest per version, identified by `manifest_hash` — is therefore **already met** on this route by a different, route-native manifest: `input_hash = sha256(SourceContent.model_dump_json())` (`app/services/seller_listing_approval.py:45`), frozen into `SellerListingApproval.source_snapshot` as the encrypted envelope (`:49-63`). This amendment does **not** replace it with the parent's `python-json-sort-compact-v1` manifest: the workspace manifest is keyed by provider `etag` and `size` per object (`SourceObject`, `app/schemas/seller_listing_source.py:7-12`), not by SHA-256 of bytes, because **ai.market never reads the seller's bytes on this route** — before or after purchase (delivery presigns exact-object GETs, `app/services/seller_workspace_delivery_aws.py:1-3`, `:53-127`; R2 `app/services/seller_workspace_r2.py:175-209`). This amendment keeps that property.
- **Delivery is the whole set.** `app/services/seller_workspace_delivery.py` delivers every object of the approved source (`:151` refuses when `version.object_count != len(source.objects)` or the total size differs; per-object `SellerDownloadFileGrant` rows, `:313`; order events at `:281`, `:317` record `delivery_type = workspace_direct`), resolved through `SellerApprovedSourceIndex` (`app/services/seller_approved_source_index.py`, chunks of `CHUNK_FILES = 64` objects, `:16`, `:81-104`). The buyer already receives the original files unchanged. Nothing here changes.
- **Provider parity.** Publication accepts `provider in {'aws','r2'}` and requires `connection.status == 'verified'` (`app/services/seller_listing_publication.py:102`); R2 objects are validated with `validate_object` and must have `version_id is None` (`:114-117`). ## 2. The gap

`ListingApprovalRequest.sample_decision: Literal['none']` (`app/schemas/seller_listing_approval.py:14`, receipt `:36`) and `CheckConstraint("sample_decision = 'none'", name='ck_listing_approval_sample')` (`app/models/seller_listing_approval.py:12`). The schema comment at `:11-12` says it: "A public sample requires its own bounded, reviewed artifact contract." A workspace seller today — AWS or R2 — can offer **no free sample at all**: `approved_rows` is an AIM Data disclosure-snapshot concept (`app/schemas/disclosure_snapshot.py:96`, `:105`, `:136`, `:178`) that never reached the workspace approval. Every public consumer of the workspace `sample_decision` hard-codes `none`: `app/services/seller_listing_public_presentation.py:58` (`approved_workspace_details` raises `PublicPresentationUnavailable` unless `'none'`; the presentation itself, `approved_public_presentation` `:11-21`, has no gate), `app/services/listing_summary.py:146` (single-listing summary calls `approved_workspace_details`), `:182-190` (emits the fixed fact `("sample_availability", "No sample offered", "SellerListingApproval.sample_decision")` for every workspace block) and `:487` (batch summary drops the workspace block when `sample_decision != "none"`); the Agent API `app/services/agent_service.py:185-205` (`get_dataset_details` returns `approved_workspace_details`), `:277` and `:355` (`get_dataset_evaluation`/`get_dataset_preview` treat any non-`none` decision as "rows sample available" and would synthesize a preview); and the MCP marketplace tools `app/services/mcp_marketplace_tools.py:416-430` (dataset details = `approved_workspace_details`) and `:619-621` (`workspace_preview_unsupported`: "This listing has no public sample."). Plus the Agent synthetic-preview endpoint (`app/api/v1/agent/router.py:472-518` → `app/services/synthetic_data_service.py:72-74`), which refuses every workspace listing today, and the Agent response model `DatasetDetails` (`app/api/v1/agent/router.py:101-128`) through which `get_dataset_details` is serialized. Those are the consumers that read workspace sample state at the pin. The parent's D4 defines the seller-chosen sample-file surface for the local route only ("owned by chunk C: at publish, AIM Data uploads the sample members …"). A seller of 21,000 files on R2 would therefore ship a listing with no way for a buyer to inspect one file before paying — the same customer problem as the trigger, on the route the trigger customer is actually on.

## 3. Decision

**W-D1. `sample_decision = 'member_files'` on the workspace approval; the seller names the sample files by index into the frozen manifest.** `ListingApprovalRequest.sample_decision` widens to `Literal['none','member_files']` (`app/schemas/seller_listing_approval.py:14`; receipt `:36`); the CHECK at `app/models/seller_listing_approval.py:12` widens with a migration; `SellerListingApproval` gains `sample_object_indices: JSON NOT NULL DEFAULT '[]'` — the **indices into the frozen `SourceContent.objects` list** the seller chose, validated at approval against the same `source.content` whose `input_hash` the approval freezes (`app/services/seller_listing_approval.py:37-45`): every index in range, strictly ascending, no duplicates, `len ≤ SAMPLE_MAX_FILES`, `sum(objects[i].size) ≤ SAMPLE_MAX_TOTAL_BYTES`, and **each `objects[i].size ≤ SAMPLE_MAX_FILE_BYTES`**. The three bounds are **one product policy on both routes**: they are defined once by the parent's D4/chunk C (this PR adds the third to the parent, per Max's recorded decision), and chunk G consumes them. `member_files` pairs with a non-empty index list; `none` pairs with an empty one (CHECK). The request carries the indices; `request_hash` (`:27`) therefore binds them, and the existing idempotent-conflict rule (`:29-31`) applies unchanged. **Approval locks the exact staged assets.** Every named index must have a `pending` sample asset row (W-D2) for `(seller_id, connection_id, source_version = row.version, index)` whose recorded `size` equals the manifest entry's `size` and whose `storage_key` object exists (a metadata-only HEAD in ai.market's own store — no seller-bucket access; at most `SAMPLE_MAX_FILES` such calls, deliberately performed inside the owner-locked approval transaction because they are short calls against our own store and the check must be atomic with the lock to `approved`; a missing object fails the approval naming the index); the approval transaction moves those rows `pending → approved` (`approval_id` set on the mutable asset rows after the approval row is flushed — `SellerListingApproval` itself is immutable after INSERT, `app/models/seller_listing_approval.py:33-36`, so `sample_assets` is built before the INSERT) and records on `SellerListingApproval.sample_assets` (JSON) the list `[{index, asset_id, sha256, size, binding}]` taken from the rows — an approval naming an index with no uploaded asset, or a mismatched one, is refused naming the index. every reservation, initial or reuse, gets a new one — it is the generation token that keys the row's objects and every state-conditional update). Two concurrent uploads therefore serialize on the lock and the second is refused before either streams; the row is the reservation. **Transaction boundary:** the reservation transaction commits (row `reserving`, `state_changed_at` = now) and releases the lock before the stream starts; the stream, hashing and promote run outside any DB transaction; completion is a second short transaction under the owner lock that performs the state-conditional `UPDATE … SET state='pending', sha256, md5, binding, storage_key, state_changed_at WHERE id = ? AND state = 'reserving' AND reservation_id = ?` — zero rows updated (the reaper timed it out, or the slot was reused by a newer reservation) means this upload failed and the endpoint deletes the objects it wrote under its own `reservation_id` prefix only. **Chunk G adds this lock to the upload endpoint; it exists today only on the source/review/approval paths.** The endpoint is rate-limited per seller. The upload is then streamed to the listing-asset object store (the parent's D4 store; Gate 2 pins bucket and storage client) under a **staging key** `samples-staging/workspace/<asset_row_id>/<reservation_id>` while computing SHA-256 and MD5, bounded on the wire: the stream is refused (and the staging object deleted) the moment it exceeds the manifest entry's declared `size`; a completed upload whose byte count differs from the declared `size` is refused. On success the object is **promoted by a server-side copy inside ai.market's own store** to the final key `samples/workspace/<asset_row_id>/<reservation_id>/<sha256>` and the staging object deleted; the row then moves `reserving → pending` with `sha256`, `md5`, `binding`, `storage_key` filled. A `reserving` row older than `SAMPLE_UPLOAD_TIMEOUT_S` (Gate 2; guidance: minutes) is a failed upload: sweep (iii) deletes its objects and moves the row to `deleted` (reusable). **Binding to the frozen selection:** `size` must equal `objects[index].size`; when `objects[index].etag` is a plain 32-hex value and the MD5 of the uploaded bytes equals it, the record carries `binding = etag_md5` ("checksum-matched copy" — MD5 equality with the provider ETag, a weak binding: it identifies the bucket object's checksum, it is not a cryptographic proof); otherwise — multipart, SSE-KMS/SSE-C or otherwise opaque ETag, or a plain-hex ETag that does not match — `binding = size_only`, shown publicly as "copy provided by the seller" (a mismatch degrades, it does not refuse: a single-part SSE object can carry a non-MD5 32-hex ETag). This is stated plainly: the workspace manifest has no seller-committed content hash (`SourceObject`, `app/schemas/seller_listing_source.py:7-12`), so the strongest available binding is etag-MD5 where the provider gives one and size otherwise, plus the seller's signed `sample_files_confirmed` statement. The asset row — new table `seller_sample_assets(id, seller_id, connection_id, source_version, index, key_basename, size, sha256, md5, binding, storage_key, state ∈ {reserving, pending, approved, active, unavailable, deleted}, previous_storage_key NULL, approval_id NULL, listing_version_id NULL, created_at, approved_at, activated_at, deleted_at)` with `reservation_id` and a resettable **`state_changed_at`** (set on every transition, including slot reuse; every timed rule — `SAMPLE_UPLOAD_TIMEOUT_S`, `SAMPLE_PENDING_TTL_S`, `SAMPLE_APPROVED_TTL_S` — reads it, never `created_at`) and `UNIQUE (seller_id, connection_id, source_version, index)` — exists from reservation, so every object under `samples-staging/` and `samples/` is named by a row id and has an owner: a crash mid-stream or between promote and the `pending` update leaves a `reserving` row that the timeout turns into `deleted` with its objects removed. **Re-upload rules by state:** `pending` → replaced by the protocol below;  `deleted` → the slot is reused (row back to `reserving`; a `deleted` row is not a tombstone); `reserving` → refused while the upload is live, reusable after `SAMPLE_UPLOAD_TIMEOUT_S`; `approved`, `active`, `unavailable` → refused. **Replacement protocol (crash-safe):** the row's `storage_key` names its single current object. Under the owner lock, CAS `pending → reserving` copying `storage_key` into `previous_storage_key`; stream to the staging key; promote to a new final key (`…/<row_id>/<new reservation_id>/<new sha256>`); CAS `reserving → pending` (predicate includes the new `reservation_id`) setting `storage_key` to the new key and clearing `previous_storage_key`; only then delete the previous object. The promote runs outside any DB transaction; the completion CAS is a short transaction under the owner lock. A crash at any boundary leaves either a `reserving` row (timeout → every object under its prefix deleted, row `deleted`) or a `pending` row whose `storage_key` object exists. **Ownership rule:** while a row is `reserving` and unexpired, *every* object under its prefix belongs to the reservation and sweep (iii) deletes nothing there (the newly promoted object is protected from the moment it is written); once the row is `pending`, `approved` or `active`, exactly one object — `storage_key` — is current and sweep (iii) deletes the rest (for `unavailable`/`deleted` rows sweep (iv) deletes everything, including a `deleted` row's leftovers), so a leftover previous object is reaped and a row never points at a missing object. **`key_basename` = `basename(objects[index].key)`** — the seller's own file name from the frozen manifest, never a segment of the storage key, and the only name ever disclosed (no private prefix or bucket name); a basename that is empty (a key ending in `/`), `.` or `..`, or containing control characters (`0x00–0x1F` including CR/LF, `0x7F`), or longer than 255 UTF-8 bytes (provider keys may be 1024 characters, `app/schemas/seller_listing_source.py:9`; a public file name is not) is refused at upload naming the index. It is not `source_file_name` in the sense of the public schema's forbidden list (`app/schemas/listing_public.py:222-225` — a private source path leaking through metadata): it is the name of a file the seller chose to give away, shown to him at review and confirmation, disclosed already to buyers of the real object (`app/services/seller_workspace_r2.py:209`), and carrying no path. **Authorization:** the endpoint is seller-scoped like every workspace route (`_seller_context`); the `(connection_id, source_version)` must belong to the caller, else 404. 3. The published listing shows "Free sample: N files" with the file names and sizes and a download link per file; the buyer needs no account.

5. Pausing the listing makes the sample links stop at once and re-listing brings them back; disconnecting the connection stops them and removes the files; nothing about the seller's bucket, prefix, keys or account is ever shown.

## 8. Risks

- Sample bytes are seller-supplied public artifacts held in ai.market custody from upload: the upload is bounded server-side (three policy values plus a per-seller pending quota and rate limit), locked at approval, bound to the frozen selection by size and, where the provider exposes it, etag-MD5, hashed, recorded as a row before it can be served, and reaped when unapproved, terminated or orphaned. The seller sees the file names and sizes at confirmation and signs a dedicated statement. Residual: an object with an opaque ETag binds by size only — the seller could upload a same-size different file as its "sample"; the platform makes that residual visible ("copy provided by the seller" versus "checksum-matched copy" — and even the latter is an MD5/ETag equality, not a cryptographic binding to the bucket object), and it remains a misrepresentation by the seller of his own listing, covered by the signed statement and the buyer's whole-set delivery of the real objects, not a platform integrity failure.
- Policy values are shared with the parent's D4: a change to one route's limits changes the other's. This is intended (one product rule) and stated so Gate 2 pins them once; if a value is ever tuned for infrastructure cost rather than product policy, the routes may need to diverge (CC).
