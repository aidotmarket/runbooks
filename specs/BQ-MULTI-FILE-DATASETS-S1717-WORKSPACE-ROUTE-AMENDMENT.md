## 1. What the workspace route already has (no change)

- **One listing = N objects.** A workspace listing version is published from the seller's frozen source selection: `SourceContent.objects` (`app/schemas/seller_listing_source.py:14-19`, `min_length=1, max_length=MAX_SELECTION_FILES`, `MAX_SELECTION_FILES = 50_000`, `app/schemas/seller_source_limits.py:2`, whose docstring records "customer acceptance includes 22,000 files"). Publication writes `ListingVersion(object_count=len(objects), total_size_bytes=sum(size), manifest_hash=approval.source_snapshot['input_hash'])` (`app/services/seller_listing_publication.py:132-135`), `prefix='workspace/<approval_id>/'` (`:133`), `authority_kind='workspace_connection'` (`:137`). The parent's D0 requirement — one frozen manifest per version, identified by `manifest_hash` — is therefore **already met** on this route by a different, route-native manifest: `input_hash = sha256(SourceContent.model_dump_json())` (`app/services/seller_listing_approval.py:45`), frozen into `SellerListingApproval.source_snapshot` as the encrypted envelope (`:49-63`). This amendment does **not** replace it with the parent's `python-json-sort-compact-v1` manifest: the workspace manifest is keyed by provider `etag` and `size` per object (`SourceObject`, `app/schemas/seller_listing_source.py:7-12`), not by SHA-256 of bytes, because **ai.market never reads the seller's bytes on this route** — before or after purchase (delivery presigns exact-object GETs, `app/services/seller_workspace_delivery_aws.py:1-3`, `:53-127`; R2 `app/services/seller_workspace_r2.py:175-209`). This amendment keeps that property.
- **Delivery is the whole set.** `app/services/seller_workspace_delivery.py` delivers every object of the approved source (`:151` refuses when `version.object_count != len(source.objects)` or the total size differs; per-object `SellerDownloadFileGrant` rows, `:313`; order events at `:281`, `:317` record `delivery_type = workspace_direct`), resolved through `SellerApprovedSourceIndex` (`app/services/seller_approved_source_index.py`, chunks of `CHUNK_FILES = 64` objects, `:16`, `:81-104`). The buyer already receives the original files unchanged. Nothing here changes.
- **Provider parity.** Publication accepts `provider in {'aws','r2'}` and requires `connection.status == 'verified'` (`app/services/seller_listing_publication.py:102`); R2 objects are validated with `validate_object` and must have `version_id is None` (`:113-116`). AWS profiling (W3) is not a precondition for publication on either provider.

## 2. The gap

`ListingApprovalRequest.sample_decision: Literal['none']` (`app/schemas/seller_listing_approval.py:14`, receipt `:36`) and `CheckConstraint("sample_decision = 'none'", name='ck_listing_approval_sample')` (`app/models/seller_listing_approval.py:12`). The schema comment at `:11-12` says it: "A public sample requires its own bounded, reviewed artifact contract." A workspace seller today — AWS or R2 — can offer **no free sample at all**: `approved_rows` is an AIM Data disclosure-snapshot concept (`app/schemas/disclosure_snapshot.py:96`, `:105`, `:136`, `:178`) that never reached the workspace approval. Every public consumer of the workspace `sample_decision` hard-codes `none`: `app/services/seller_listing_public_presentation.py:58` (`approved_workspace_details` raises `PublicPresentationUnavailable` unless `'none'`; the presentation itself, `approved_public_presentation` `:11-21`, has no gate), `app/services/listing_summary.py:146` (single-listing summary calls `approved_workspace_details`), `:182-190` (emits the fixed fact `("sample_availability", "No sample offered", "SellerListingApproval.sample_decision")` for every workspace block) and `:487` (batch summary drops the workspace block when `sample_decision != "none"`). The parent's D4 defines the seller-chosen sample-file surface for the local route only ("owned by chunk C: at publish, AIM Data uploads the sample members …"). A seller of 21,000 files on R2 would therefore ship a listing with no way for a buyer to inspect one file before paying — the same customer problem as the trigger, on the route the trigger customer is actually on.

## 3. Decision

**W-D1. `sample_decision = 'member_files'` on the workspace approval; the seller names the sample files by index into the frozen manifest.** `ListingApprovalRequest.sample_decision` widens to `Literal['none','member_files']` (`app/schemas/seller_listing_approval.py:14`; receipt `:36`); the CHECK at `app/models/seller_listing_approval.py:12` widens with a migration; `SellerListingApproval` gains `sample_object_indices: JSON NOT NULL DEFAULT '[]'` — the **indices into the frozen `SourceContent.objects` list** the seller chose, validated at approval against the same `source.content` whose `input_hash` the approval freezes (`app/services/seller_listing_approval.py:37-45`): every index in range, strictly ascending, no duplicates, `len ≤ SAMPLE_MAX_FILES`, `sum(objects[i].size) ≤ SAMPLE_MAX_TOTAL_BYTES`, and **each `objects[i].size ≤ SAMPLE_MAX_FILE_BYTES`**. The three bounds are **one product policy on both routes**: they are defined once by the parent's D4/chunk C (this PR adds the third to the parent, per Max's recorded decision), and chunk G consumes them. `member_files` pairs with a non-empty index list; `none` pairs with an empty one (CHECK). The request carries the indices; `request_hash` (`:27`) therefore binds them, and the existing idempotent-conflict rule (`:29-31`) applies unchanged. **Approval additionally requires that every named index already has an `active`-eligible staged sample asset (W-D2) whose recorded `size` equals the manifest entry's `size`** — an approval naming an index with no uploaded asset, or a mismatched one, is refused naming the index. **Confirmation contract:** `confirmation_version` becomes `Literal['seller-listing-confirmation-v1','seller-listing-confirmation-v2']` (`app/schemas/seller_listing_approval.py:13`, `app/services/seller_listing_confirmations.py:2-7`): v1 is unchanged and remains valid only with `sample_decision = 'none'`; v2 = v1's four statements plus `sample_files_confirmed` ("the files I uploaded as the free sample are copies of files in my selection; anyone may download them free of charge; they are part of the purchased set") and is required for `member_files` (v2 is also accepted for `none`, with the fifth statement then absent). The assertion-building code (`app/services/seller_listing_approval.py:64-65`, `'confirmed':{field:True for field in CONFIRMATION_STATEMENTS}`) and the validators (`app/schemas/seller_listing_approval.py:20-24`) currently treat the statement set as one unconditional block; chunk G changes them to build from the *version's* statement set — a change to the assertion model, not a dictionary entry. The confirmation screen lists the chosen file names (basename only) and sizes beside the statement (the existing `public_disclosure_confirmed` text at `app/services/seller_listing_confirmations.py:6` already says "my sample choice become[s] public on ai.market").

**W-D2. The seller uploads the sample files; ai.market never reads his bucket.** A new seller-authenticated, no-store endpoint under the workspace router (`app/api/v1/endpoints/seller_workspace.py`, same `_seller_context`/idempotency conventions as `:213-232`) accepts **one sample file per request**, addressed by `(connection_id, source_version, index)` — the index into the seller's *current* saved source (`SourceRead.version`, `app/schemas/seller_listing_source.py:40-43`). The upload is streamed to the listing-asset object store (the parent's D4 store; Gate 2 pins bucket and storage client) under a **deterministic private key** `samples/<seller_id>/<connection_id>/<source_version>/<index>/<sha256>` while hashing, and is bounded on the wire: the stream is refused (and the partial object deleted) the moment it exceeds `SAMPLE_MAX_FILE_BYTES` or the manifest entry's declared `size`, whichever is smaller; a completed upload whose byte count differs from the manifest entry's `size` is refused. **Binding to the frozen selection:** `size` must equal `objects[index].size`; when `objects[index].etag` is a plain 32-hex value (a non-multipart S3/R2 upload, whose ETag is the MD5 of the bytes) the MD5 of the uploaded bytes must equal it, recorded as `binding = etag_md5`; otherwise (multipart or otherwise opaque ETag) the record carries `binding = size_only`. This is stated plainly: the workspace manifest has no seller-committed content hash (`SourceObject`, `app/schemas/seller_listing_source.py:7-12`), so the strongest available binding is etag-MD5 where the provider gives one and size otherwise, plus the seller's signed `sample_files_confirmed` statement. The asset row — new table `seller_sample_assets(id, seller_id, connection_id, source_version, index, key_basename, size, sha256, md5, binding, storage_key, state ∈ {pending, active, deleted}, created_at, activated_at, deleted_at, listing_version_id NULL)` with `UNIQUE (seller_id, connection_id, source_version, index)` — is written `pending` **after** the object write succeeds (a crash before the row leaves an object at a deterministic key that the same seller's retry overwrites and the reaper's prefix reconciliation deletes). Re-upload for the same index replaces the pending row and object (the old object deleted, idempotent). One `seller_workspace_audit` row per upload, `purpose = 'listing_approval'`, new operation tokens `sample_asset_uploaded` / `sample_asset_refused` (the operation allowlist `_OPERATIONS`, `app/services/seller_workspace_audit.py:62-100`, and snapshot-field allowlist `:59-61` gain exactly these tokens and the integer fields `index`, `size`); a `listing_publication`-purpose row is **not** written per sample (publication keeps its single `listing_published` row, `app/services/seller_listing_publication.py:149-154`). **`key_basename`** is the object key's final path segment only, so no private prefix or bucket name becomes public. **Why upload rather than read the bucket:** at the pin ai.market holds no byte-reading capability on this route on either provider and the R2 credential is the seller's parent key, which can read his whole bucket (`app/services/seller_workspace_r2.py:4-5`); an upload of files the seller already holds locally keeps that capability out of ai.market entirely, keeps provider I/O out of the publication transaction, and gives immutable, hash-known bytes before approval. **Why not proxy on demand:** every anonymous sample download would be a credentialed read of the seller's bucket (recurring cost and a live credential path on the anonymous surface) and the sample could drift from the manifest.

**W-D3. Activation at publication; compensation, not atomicity, across the object store — stated as such.** `app/services/seller_listing_publication.py` publish, inside its existing DB transaction (`:141-155`) and **with no provider I/O**, re-reads the approval's `sample_object_indices`, requires a `pending` (or already `active` for an idempotent retry) `seller_sample_assets` row for each with `source_version = approval.source_version` and `size` equal to the frozen entry (else `PublicationConflict`, nothing published — the same class as `:151`), and sets those rows `active` with `listing_version_id = version_id` in the same commit as the listing, version, authority and publication rows. Nothing about the object store happens at publication: the objects were written at upload time and are already at their deterministic keys. The publication row stays immutable (`app/models/seller_listing_publication.py:24-27`); the sample list lives on `seller_sample_assets`, never on that row. **Reaper (chunk G, one scheduler job, the same job family as the parent's chunk D sweeps):** (i) `pending` rows older than `SAMPLE_PENDING_TTL_S` (Gate 2; guidance: days) whose `(seller, connection, source_version)` has no approval → object deleted, row `deleted`; (ii) rows whose listing version is no longer `active` or whose listing is unpublished/withdrawn/taken down, or whose connection is `revoked` (`app/services/seller_workspace_connection.py:1239` on `disconnect_connection`, `app/api/v1/endpoints/seller_workspace.py:487`) → object deleted, row `deleted` (serving already refuses, W-D4; the reaper removes the bytes); (iii) prefix reconciliation: any object under `samples/` with no row → deleted. A delete failure leaves the row in its state and is retried on the next run; the row is the durable record that bytes exist in ai.market custody. Serving never consults the object store without an `active` row, so an orphan is never publicly addressable.

**W-D4. Serving reuses the parent's D4 surface verbatim.** The public listing serves sample files addressed only by `(version_id, index)` resolved through an `active` `seller_sample_assets` row, hash-verified against the row's `sha256` before response, `Content-Type: application/octet-stream` + `Content-Disposition: attachment; filename=<key_basename>`, `X-Content-Type-Options: nosniff`, **`Cache-Control: no-store`** (there is no CDN in front of the API at the pin; if one is introduced, termination must invalidate — Gate 2 states the deployment assumption), opaque non-guessable addressing and a per-listing daily byte budget (CC's Gate 1 nits on the parent, carried into Gate 2), rate-limited per listing and per client, not enumerable. **Serving gates, all required:** version `active`; listing `status == 'published'` and `is_listed` (`app/services/seller_listing_management.py:44-45` writes `published`/`unlisted`; withdrawal and takedown are whatever non-published status those flows set — any other status fails the gate); connection `status == 'verified'` (the same condition publication enforces, `app/services/seller_listing_publication.py:102`); asset row `active`. **Public presentation:** `app/services/seller_listing_public_presentation.py:58` and `:71` render `member_files` with the sample list `{index, key_basename, size}` and the statement that sample files are part of the purchased set and free to download; `app/services/listing_summary.py:182-190` makes `sample_availability` value-dependent ("No sample offered" for `none`; "N free sample files" for `member_files`), `:146` and `:487` stop treating `member_files` as unavailable. The rows-sample route keeps answering `member_files` with 409 `no_approved_sample_rows` (parent D4); Hugging Face is out of scope for workspace listings (no HF publish exists on this route today). Supersede/quarantine have no workspace analogue (each publish mints a new listing and version, `seller_listing_publication.py:120-135`); the gates above are the complete termination set for this route.

**W-D5. No roles, no manifest change, no delivery change on this route.** Every workspace object remains a delivered object (there is no `data`/`docs`/`other` role on this route and this amendment adds none — the seller's selection *is* the product); `SourceObject` stays `key/version_id/etag/size`; `manifest_hash` stays `input_hash`; `SellerApprovedSourceIndex` and `app/services/seller_workspace_delivery.py` are untouched; the D5 transfer protocol, D6 verification amendment and D8 registration do not apply here (the seller's files are never traversed or read by ai.market). The parent's D7 (verified label optional) already holds on this route: workspace publication has no verification precondition.

**W-D6. R2 profiling is out of scope** (W3 is AWS-only Lambda, `build:bq-seller-workspace-w3-profiling-s1650`, blocked on its server-authority redesign). A workspace seller lists and samples without profiling on either provider; nothing in this amendment depends on W3.

## 4. Non-goals

No change to the S3 device route or S1681 G3.2; no change to AIM Data's D4 mechanics beyond the shared third bound (this amendment consumes the same serving surface and policy values); no change to pricing, commission, payout, the delivery grant model, `MAX_SELECTION_FILES`, the connection/credential model, or the Trust Channel. **No server-side read of the seller's bucket, ever, on this route.** No on-demand proxying of seller-bucket bytes to anonymous clients. No sample for `version_mode = 'versions'` selections beyond what the frozen `SourceObject.version_id` already pins (R2 refuses `version_id`, `app/services/seller_listing_publication.py:115-116`). No archive/zip of sample files.

## 5. Customer-visible behaviour

1. In the workspace listing review (W4/W5), the seller ticks the files he wants to give away as the free sample and uploads each one (bounded: count, total bytes, per-file bytes — the UI shows the limits, refuses over-limit files by name before upload, and shows which uploads are accepted and bound to the selection).
2. The confirmation screen shows the sample file names and sizes and the extra statement; approval and publication then proceed as today.
3. The published listing shows "Free sample: N files" with the file names and sizes and a download link per file; the buyer needs no account.
4. Purchase delivers the whole selection exactly as today.
5. Unpublishing, pausing, withdrawing or disconnecting the connection makes the sample links stop at once; nothing about the seller's bucket, prefix, keys or account is ever shown.

## 7. Acceptance criteria

- **AC-W1.** An R2 connection with 21,000 objects uploads three sample files, approves under v2 with those three indices, publishes one listing with `object_count = 21000`, `sample_decision = member_files`, three `active` asset rows whose stored objects re-hash to the recorded `sha256` (mutating a stored object → serving refuses with 404 and the row is reaped), recorded `size` equal to the frozen manifest entry and `binding = etag_md5` for the two non-multipart objects and `size_only` for the multipart one; exactly three `sample_asset_uploaded` audit rows plus the existing single `listing_published` row; and the seller's bucket name, prefix, key prefix, account id and credential material appearing nowhere in any public response — asserted by grep over the listing page, the summary endpoints (single and batch), the sample list, every public error body and the sample response headers.
- **AC-W2.** An upload exceeding `SAMPLE_MAX_FILE_BYTES` or the declared `size` is refused mid-stream with the partial object deleted and a `sample_asset_refused` row; a completed upload with a different byte count, or an MD5 differing from a plain-hex etag, is refused; an approval naming an out-of-range, duplicate, over-total or not-uploaded index is refused at approval with the offending index named; a v1 confirmation with `member_files` is refused; a publish whose approval names an index with no matching `pending`/`active` asset for the approval's `source_version` is refused with `PublicationConflict` and creates no listing, no version and no activation.
- **AC-W3.** Sample download without authentication returns the exact bytes with `application/octet-stream`, `attachment`, `nosniff`, `no-store`; enumeration of `(version_id, index)` outside the approved list returns 404 indistinguishable from a non-existent listing; the per-listing daily byte budget and per-client rate limit are enforced; after each of unpublish, pause, withdrawal, takedown, version inactivation and `disconnect_connection` the same URL returns 404 immediately (before the reaper runs) and, after one reaper run, the object is gone and the row is `deleted`; re-listing after pause serves again only when every gate holds.
- **AC-W4.** Fault injection: the process is killed after the object write and before the `pending` row → a retry by the seller overwrites the same key and produces exactly one row and one object; the process is killed after activation's object-free commit → no inconsistency exists by construction; a forced object-delete failure in the reaper leaves the row in its prior state and the next run completes the delete; after `SAMPLE_PENDING_TTL_S` an unapproved pending upload is reaped; an object under `samples/` with no row is reaped.
- **AC-W5.** `sample_decision = none` approvals under v1 and every existing published workspace listing are byte-identical in behaviour before and after the migration, including both `listing_summary` paths (fixture: a copied production-shaped approval + publication row).
- **AC-W6.** An AWS connection passes AC-W1–W4 identically (provider parity), with no profiling job existing for the connection.

## 8. Risks

- Sample bytes are seller-supplied public artifacts held in ai.market custody from upload: the upload is bounded (three policy values), bound to the frozen selection by size and, where the provider exposes it, etag-MD5, hashed, recorded as a row before it can be served, and reaped when unapproved, terminated or orphaned. The seller sees the file names and sizes at confirmation and signs a dedicated statement. Residual: a multipart-uploaded object binds by size only — the seller could upload a same-size different file as its "sample"; this is a misrepresentation by the seller of his own listing, covered by the signed statement and the buyer's whole-set delivery of the real objects, not a platform integrity failure.
- Policy values are shared with the parent's D4: a change to one route's limits changes the other's. This is intended (one product rule) and stated so Gate 2 pins them once; if a value is ever tuned for infrastructure cost rather than product policy, the routes may need to diverge (CC).
