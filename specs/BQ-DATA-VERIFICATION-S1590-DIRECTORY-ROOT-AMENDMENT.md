## 1. What changes and what does not

1.1 The parent Gate 1 resolves the registered source handle "to the exact artifact" (§3 Stage A, `:40`), traverses "every reachable supported object in the registered root" (`:203`), and its A1 test pins "the exact resolved local path or S3 connection/bucket/object key plus content hash before reading" (`:315`). The pinned resolver is single-artifact: `ResolvedArtifact` holds one `local_path` or one `S3ObjectMetadata` and `resolved_object_count()` is 1 for either (`aim-data:app/services/source_artifact_resolver.py:34-51`); the locator preimage is typed and NUL-framed (`local\0<realpath>` / `s3\0<conn>\0<bucket>\0<key>`, `:53-65`); the scanner streams one artifact, computes `content_sha256` over its bytes (`aim-data:app/services/data_verification/scanner.py:126-151`) and passes one stream to the connector (`:173-184`); the connector derives every `object_id` as `HMAC(key, "object\0" + source_binding + "\0" + identity)` with identity `"registered-root"` for an ordinary file and one identity per entry for a ZIP it expands (`aim-data:app/services/data_verification/connectors/eolymp_v1.py:69-85`, `:260-265`, `:291-294`).

1.2 This amendment adds one artifact kind, **`local_directory`**, for directory datasets published under S1717 D0/D3. **Unchanged:** the set and shape of every wire field of the customer-to-cloud manifest (`REPORT_FIELD_CONTRACT`, `contract.py:42-58`); the report ordering (`objects[]` in canonical ascending `object_id` order — signed `traversal_order: "canonical_object_identity_ascending"`, `aim-data:app/services/data_verification/contract.py:113`; ordering and uniqueness validated at `ai-market-backend:app/schemas/data_verification.py:675-690`; `coverage.skipped[]` totals validated at `:479-487`, and this amendment emits `skipped[]` ascending by `object_id` as well so the fingerprint stays deterministic, tied to the parent's A1 §4 byte-identical-payload test); the literals `connector_version: "eolymp-v1"`, `traversal_root: "registered_source_artifact"`, `traversal_scope: "all_reachable_supported_objects"` and `canonicalization_version: "python-json-sort-compact-v1"`; the closed skip-reason enum (`permission_denied`, `unsupported_type`, `timeout`; `ai-market-backend:app/schemas/data_verification.py:466-487`); the coverage-total validators; the prohibition on seller-selected exclusions (`:203`) and on deleting skips (`:205`); the quote, payment, capture, publication and corpus-capture contracts; the privacy boundary (no raw member names, paths, error text or records in cloud-visible fields); and the single-file and S3 kinds, which keep their existing preimages and behaviour byte-for-byte.

1.3 **The CORE S3 items (Max's approval of this amendment records the decision for exactly these three, all confined to the new kind; no field is added, widened or repurposed, and no existing kind's definition changes):**
- (a) `artifact_locator_commitment` preimage for `local_directory`: `b"local_directory\0" + os.fsencode(realpath(root_path)) + b"\0" + manifest_hash_hex.encode()`.
- (b) `objects[].object_id` preimage for a directory member: the parent's `object_commitment(key, source_binding, identity)` with `source_binding` = `b"local_directory_object\0" + os.fsencode(realpath(root_path))` (typed, **manifest-independent**, so ids are stable across versions of the same root) and `identity` = `"member\0" + relative_path + "\0" + member_sha256_hex` (UTF-8, NFC canonical path). The connector's own `"registered-root"` identity is never used for a directory member (§2.4), so member ids are unique, path-and-content-bound, and unchanged by role/sample/order edits.
- (c) `content_sha256` for `local_directory`: a **path-bound** digest of member digests — SHA-256 over the concatenation, in ascending canonical `relative_path` order (key-independent), of `u64-be(len(path_utf8)) || path_utf8 || u64-be(size_bytes) || sha256(member bytes)` for every data member. **Timing, stated once:** the per-member digests in this preimage are the manifest values; the pre-read pass verifies every data member against them, the fact-time read (§2.3) verifies every connector-fed member against them again, and the report is assembled only after both checks pass — so the transmitted `content_sha256` equals the framed digest over exactly the bytes the connector saw for scanned members and the pre-read-verified bytes for skipped members, and any inequality is terminal; it changes if and only if the set of data members' `(path, size, bytes)` triples changes (swapping two members' contents between paths changes it; under SHA-256 collision resistance, as the parent already assumes), and is unaffected by documentation/`other` members, sample flags, manifest order or the commitment key. This is the single definition; S1717 D6 refers to it.
If the panel judges any of (a)–(c) inadmissible under `:110`, that item is the one to change; the fallback for (a) is the root realpath alone with manifest binding carried by the version. Cross-repo golden vectors for (a), (b) and (c) are a chunk E deliverable.

1.4 **Scan-spec change (cloud → customer; not in the §6 customer-to-cloud list, but declared here because `ScanSpecPayload` is `extra="forbid"`, `contract.py:96-99`).** The signed scan spec gains, for `local_directory` sources only, two fields: `listing_version_id` and `manifest_hash`. **`spec_version` stays `"1"`** — the report-visible version is unchanged, so the successful and terminal report models (`ai-market-backend:app/schemas/data_verification.py:626-642`, `:715-721`) and the report/spec equality checks (`app/services/data_verification_service.py:1264-1275`, `:1295-1307`) are untouched and no report-shape decision is needed. Discrimination is by presence: the two fields are present exactly when the registered source is a directory version. The fail-closed basis is the install itself: an install below the chunk E release rejects such a spec as unknown fields (`extra="forbid"` — `FAILED_VOIDED` before any read), and an install at the release refuses when it holds no retained manifest (§2.2). ai.market has no install-version input at spec issue (`ScanSpecIssueRequest`, `ai-market-backend:app/schemas/data_verification.py:169-190`, carries none; `epoch.agent_version` is read only from reports, `data_verification_service.py:1410`), so no server-side version gate is claimed for the spec; single-file and S3 specs are byte-identical to today. The install resolves the root from its **locally retained published manifest** for `(listing_version_id, manifest_hash)` (S1717 D0: every published manifest is kept immutably with its frozen `root_path`, keyed by that composite — `manifest_hash` alone is not unique, since identical member lists can be published under two listings or roots), so a scan over a version published before a re-upload still resolves the version that was sold.

## 2. The directory root

1. **Registered root.** For a listing whose version named in the scan spec (`listing_version_id`, §1.4 — ai.market names the listing's *active* version at spec issue; a superseded version is never scanned) was published from a directory dataset, the registered root is the **version-pinned data-member set**: the members with `role = data` in that version's published `DatasetManifest` (S1717 D0). This is what "all reachable supported objects in the registered root" (`:203`, `traversal_scope`) means for this kind: the root definition changed, the scope literal did not. Members with other roles are not in the root; they are neither traversed nor reported as skipped. The root is frozen by the published version, not by live roles: a role edit after publish does not change the root of any existing version.
2. **Resolution.** `resolve_source_artifact` gains `listing_version_id` and `manifest_hash` arguments (from the spec, §1.4); `ResolvedArtifact` gains `kind = "local_directory"` with `root_path` (the frozen realpath stored with that retained manifest, S1717 D0/D1a), `manifest_hash`, and `members[]` (index, canonical relative path, size, SHA-256, detected type) taken from the retained manifest; `resolved_object_count()` returns `data_member_count`; `canonical_locator_bytes()` returns §1.3(a). Resolution refuses (`ArtifactResolutionError`, scan `FAILED_VOIDED` naming the version) when the install holds no retained manifest for that composite key, or the retained hash differs from the spec's. The pinned resolver today returns `kind="local"` with `local_path=None` for a directory dataset (`source_artifact_resolver.py:164-170`), which is why this branch is required.
3. **Exact binding before reading (the pre-read pass), and byte binding at fact time.** Before any fact is computed, the conduit walks the root members **in manifest index order**, streaming each, and verifies: the realpath of `root_path/relative_path` stays inside `root_path` (no symlink escape), and its size and SHA-256 equal the manifest. Any mismatch, missing member or file outside the root is a **stale-manifest failure**: the scan terminates `FAILED_VOIDED` (parent `:219`, hold voided, nothing publishes) with no partial report. A member is never silently skipped for a manifest mismatch. The pass yields §1.3(c) and the observed member count. **Fact-time binding (no TOCTOU):** members are read twice, not spooled — for each member passed to the connector (§2.4(ii)) the scanner re-opens it, reads it whole into the bounded buffer (`SCAN_MAX_MEMBER_BYTES`), re-verifies realpath/size/SHA-256 of *that buffer* against the manifest and re-checks the file's stat after the read; the connector receives that same buffer, so every reported fact and the member digest that feeds §1.3(c) derive from identical bytes. Any discrepancy between the pre-read pass and the fact-time read (a member mutated in between) is a stale-manifest failure, `FAILED_VOIDED`, no report.
4. **Adapter contract (scanner-side; the connector module is not edited).** The pinned `scan_bytes` has no identity or expansion parameter and expands ZIP payloads unconditionally (`eolymp_v1.py:69-85`, `:272-278`, `:291-293`), so the scanner composes the member result around it: (i) **pre-filter** — before any connector call, a data member whose `detected_type` is `unsupported` or whose bytes satisfy `zipfile.is_zipfile` is recorded under `coverage.skipped[]` with reason `unsupported_type` (discovered and visible, per `:205`), and the connector is never called for it, so no archive is ever expanded; (ii) **call** — for every other data member the scanner calls `scan_bytes` once with that member's bytes, for its facts only (the `source_binding` argument passed in is immaterial because the returned id is discarded); for a non-archive payload it returns exactly one object under the connector's `"registered-root"` identity; if it raises `UnsupportedConnectorShape` for a member the pre-filter let through, that member is recorded `unsupported_type` like (i); (iii) **override** — the scanner replaces that object's `object_id` with the §1.3(b) value, which is the **single normative definition** of a member id (binding `local_directory_object\0<realpath(root)>`, manifest-independent) and is never restated elsewhere, before assembling the report. (iv) **Scan-side member bound** — the pinned scanner buffers one payload whole (`scanner.py:126-151`), so `SCAN_MAX_MEMBER_BYTES` (Gate 2, ≥ `TRANSFER_MAX_MEMBER_BYTES`) bounds **only the fact-time whole-buffer connector read**; the pre-read pass (§2.3) always streams and verifies size and SHA-256 for *every* data member, including one that will be skipped for size, so every digest in §1.3(c) is verified against current bytes. A data member above the bound is recorded `unsupported_type` (the closed enum has no size reason; the seller-facing panel and the listing's role-count line explain such a skip as "exceeds the scan size bound", the wire label stays `unsupported_type`) and never buffered; the quote probe predicts the same skip from the manifest's member sizes (`fixed_reason_skips.unsupported_type`), so quote and report agree. The parent's runtime reasons apply per member (`permission_denied` for a member that becomes unreadable after the pre-read pass, `timeout` per member). Exactly one `objects[]` entry or one `skipped[]` entry results per data member, so `objects_scanned + len(skipped) = objects_discovered` holds by construction.
5. **Reporting.** `objects[]` and `coverage.skipped[]` are emitted in ascending `object_id` order exactly as today — manifest index order is used only for the pre-read pass. `coverage.objects_discovered` is the observed count from the pre-read pass; the conduit fails closed (`FAILED_VOIDED`) if it differs from `data_member_count`, so declared and observed always agree in an accepted report. Aggregate facts are computed over all scanned members exactly as the S3 kind computes them over its objects. The quote probe reports `objects_discovered = data_member_count`, counts container/unsupported data members under `fixed_reason_skips.unsupported_type`, and derives `size_class` from `total_data_bytes`.
6. **Fulfilment parity, exactly scoped.** Fulfilment resolves `orders.purchased_version_id`; verification resolves the listing's active version at spec issue (§2.1). Parity — the delivered set and the scanned set being the same members with the same hashes — therefore holds **exactly when `scan.listing_version_id == order.purchased_version_id`** (equivalently equal `manifest_hash`), which is every order placed while that version is active. After a supersede, an order pinned to V1 is fulfilled from V1 while a new scan covers V2; the V2 report never corroborates the V1 delivery, the public badge names the version it covers, and the parent A1 `:315` parity test is amended to assert equality of `(listing_version_id, manifest_hash)` between the two resolutions rather than a categorical claim.

## 3. Acceptance additions (to the parent's A1 list)

- A1 §6 is amended to read: "…pins the exact resolved local path, S3 connection/bucket/object key, **or canonical directory root plus `manifest_hash`**, plus content hash before reading."
- A directory fixture whose manifest index order differs from ascending `object_id` order produces a report accepted by the unchanged `contract.py` and backend validators, with unique ascending member ids, `objects_discovered` equal to the data-member count, skip reasons only from the parent enum and coverage totals consistent; documentation and `other` members appear nowhere in the report; schema digests are unchanged.
- A fixture with two tabular data members and one data member whose bytes are a ZIP produces one accepted report whose two `objects[]` ids equal the §1.3(b) value, one `skipped[]` entry (`unsupported_type`), no expanded entries, and `objects_scanned + len(skipped) = objects_discovered`; a member above `SCAN_MAX_MEMBER_BYTES` is a visible `unsupported_type` skip, is never buffered whole, and still contributes its pre-read-verified digest to `content_sha256`; the same member with same-size different bytes after publish terminates `FAILED_VOIDED` before facts or charge.
- Identical member lists published under two listings/roots retain two snapshots and resolve independently; an old version scanned after a byte-identical re-upload at a new root resolves the old root; a version/hash mismatch refuses closed. Successful and terminal directory reports pass the unchanged `spec_version: "1"` validators.
- A directory listing whose dataset was re-uploaded after publish produces an accepted scan over the published version's retained manifest; a directory spec sent to an install below the chunk E release, or naming a version the install does not hold, fails closed with no charge.
- The same member paths and bytes scanned under two different commitment keys yield identical `content_sha256` and different `object_id`s; changing one data member's bytes changes that member's `object_id`, its hash and `content_sha256`. Invariance, stated exactly: a new published manifest that changes only non-data members, sample flags or member order leaves `content_sha256` **and every member `object_id`** unchanged and changes only `manifest_hash` and the (a) locator commitment; a role change that moves a member into or out of the data set changes `content_sha256` (and adds/removes that member's id); swapping two members' contents between paths changes `content_sha256` and both ids; moving the root directory changes every id and the locator but not `content_sha256`. Report-to-report correlation across versions of one root is by member `object_id`.
- Golden vectors for §1.3(a)–(c) reproduce byte-for-byte in both repositories.
- Changing a member's bytes, removing a member, or replacing a member with a symlink outside the root after publish causes `FAILED_VOIDED` before any fact is computed and no charge; mutating a member *between* the pre-read pass and its fact-time read also causes `FAILED_VOIDED` with no accepted report, and a normal fixture shows facts and `content_sha256` derived from the same bytes.
- A role edit after publish does not change `objects_discovered` for the published version.
- Parity fixtures: a same-version order and scan resolve identical roots and hashes; a V1-order/V2-scan fixture resolves distinct `(listing_version_id, manifest_hash)` bindings and nothing asserts or displays that the V2 report covers the V1 delivery.
- No cloud-visible receipt or report field contains a member path or name (existing privacy tests extended with the directory fixture).
- Single-file and S3 fixtures pass unchanged, byte-for-byte.
