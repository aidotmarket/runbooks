## 1. What changes and what does not

1.1 The parent Gate 1 resolves the registered source handle "to the exact artifact" (§3 Stage A, `:40`), traverses "every reachable supported object in the registered root" (`:203`), and its A1 test pins "the exact resolved local path or S3 connection/bucket/object key plus content hash before reading" (`:315`). The pinned resolver is single-artifact: `ResolvedArtifact` holds one `local_path` or one `S3ObjectMetadata` and `resolved_object_count()` is 1 for either (`aim-data:app/services/source_artifact_resolver.py:34-51`); the locator preimage is typed and NUL-framed (`local\0<realpath>` / `s3\0<conn>\0<bucket>\0<key>`, `:53-65`); the scanner streams one artifact, computes `content_sha256` over its bytes (`aim-data:app/services/data_verification/scanner.py:126-151`) and passes one stream to the connector (`:173-184`); the connector derives every `object_id` as `HMAC(key, "object\0" + source_binding + "\0" + identity)` with identity `"registered-root"` for an ordinary file and one identity per entry for a ZIP it expands (`aim-data:app/services/data_verification/connectors/eolymp_v1.py:69-85`, `:260-265`, `:291-294`).

1.2 This amendment adds one artifact kind, **`local_directory`**, for directory datasets published under S1717 D0/D3. **Unchanged:** the set and shape of every wire field of the customer-to-cloud manifest; the report and skip ordering (`objects[]` and `coverage.skipped[]` in canonical ascending `object_id` order — signed `traversal_order: "canonical_object_identity_ascending"`, `aim-data:app/services/data_verification/contract.py:113`; validator `ai-market-backend:app/schemas/data_verification.py:685-689`); the literals `connector_version: "eolymp-v1"`, `traversal_root: "registered_source_artifact"`, `traversal_scope: "all_reachable_supported_objects"` and `canonicalization_version: "python-json-sort-compact-v1"`; the closed skip-reason enum (`permission_denied`, `unsupported_type`, `timeout`; `ai-market-backend:app/schemas/data_verification.py:466-487`); the coverage-total validators; the prohibition on seller-selected exclusions (`:203`) and on deleting skips (`:205`); the quote, payment, capture, publication and corpus-capture contracts; the privacy boundary (no raw member names, paths, error text or records in cloud-visible fields); and the single-file and S3 kinds, which keep their existing preimages and behaviour byte-for-byte.

1.3 **The CORE S3 items (Max's approval of this amendment records the decision for exactly these three, all confined to the new kind; no field is added, widened or repurposed, and no existing kind's definition changes):**
- (a) `artifact_locator_commitment` preimage for `local_directory`: `b"local_directory\0" + os.fsencode(realpath(root_path)) + b"\0" + manifest_hash_hex.encode()`.
- (b) `objects[].object_id` preimage for a directory member: the parent's `object_commitment(key, source_binding, identity)` with `source_binding` = the (a) preimage bytes and `identity` = `"member\0" + relative_path + "\0" + member_sha256_hex` (UTF-8, NFC canonical path). The scanner passes this member-specific binding and identity; the connector's own `"registered-root"` identity is never used for a directory member, so member ids are unique and path-and-content-stable.
- (c) `content_sha256` for `local_directory`: a digest of member digests — SHA-256 over the concatenation, in ascending `(member_sha256_hex, relative_path)` order (key-independent), of `u64-be(size_bytes) || sha256(member bytes)` for every data member. It is computed from the pre-read pass without re-reading bytes; it changes if and only if some data member's bytes or size change (under SHA-256 collision resistance, as the parent already assumes), and is unaffected by documentation/`other` members, roles, sample flags, member order or the commitment key.
If the panel judges any of (a)–(c) inadmissible under `:110`, that item is the one to change; the fallback for (a) is the root realpath alone with manifest binding carried by the version. Cross-repo golden vectors for (a), (b) and (c) are a chunk E deliverable.

## 2. The directory root

1. **Registered root.** For a listing whose purchased or active version was published from a directory dataset, the registered root is the **version-pinned data-member set**: the members with `role = data` in that version's published `DatasetManifest` (S1717 D0). This is what "all reachable supported objects in the registered root" (`:203`, `traversal_scope`) means for this kind: the root definition changed, the scope literal did not. Members with other roles are not in the root; they are neither traversed nor reported as skipped. The root is frozen by the published version, not by live roles: a role edit after publish does not change the root of any existing version.
2. **Resolution.** `ResolvedArtifact` gains `kind = "local_directory"` with `root_path` (canonical realpath of the version's member root, S1717 D1/D1a), `manifest_hash`, and `members[]` (index, canonical relative path, size, SHA-256, detected type) taken from the pinned manifest; `resolved_object_count()` returns `data_member_count`; `canonical_locator_bytes()` returns §1.3(a). Resolution refuses (`ArtifactResolutionError`) when the version has no local-route manifest.
3. **Exact binding before reading (the pre-read pass).** Before any fact is computed, the conduit walks the root members **in manifest index order**, streaming each once, and verifies: the realpath of `root_path/relative_path` stays inside `root_path` (no symlink escape), and its size and SHA-256 equal the manifest. Any mismatch, missing member or file outside the root is a **stale-manifest failure**: the scan terminates `FAILED_VOIDED` (parent `:219`, hold voided, nothing publishes) with no partial report. A member is never silently skipped for a manifest mismatch. The pass also yields §1.3(c) and the observed member count.
4. **Adapter contract (scanner ↔ unchanged connector).** Fact traversal calls the connector once per data member with the member's bytes, the member-specific `source_binding` and identity of §1.3(b), and archive expansion disabled: a data member whose bytes are a ZIP/container, or whose `detected_type` is `unsupported`, is **not** expanded or parsed; it is reported under `coverage.skipped[]` with reason `unsupported_type` (it stays discovered and visible, per `:205`). The parent's runtime reasons apply per member (`permission_denied` for a member that becomes unreadable after the pre-read pass, `timeout` per member). Exactly one `objects[]` entry or one `skipped[]` entry results per data member, so `objects_scanned + len(skipped) = objects_discovered` holds by construction.
5. **Reporting.** `objects[]` and `coverage.skipped[]` are emitted in ascending `object_id` order exactly as today — manifest index order is used only for the pre-read pass. `coverage.objects_discovered` is the observed count from the pre-read pass; the conduit fails closed (`FAILED_VOIDED`) if it differs from `data_member_count`, so declared and observed always agree in an accepted report. Aggregate facts are computed over all scanned members exactly as the S3 kind computes them over its objects. The quote probe reports `objects_discovered = data_member_count`, counts container/unsupported data members under `fixed_reason_skips.unsupported_type`, and derives `size_class` from `total_data_bytes`.
6. **Fulfilment parity.** Fulfilment and verification resolve the same version-pinned root and manifest (parent A1 `:315`, amended below), so a buyer's delivered set and the scanned set are the same members with the same hashes (S1717 D-bytes, D5 purchased-version binding).

## 3. Acceptance additions (to the parent's A1 list)

- A1 §6 is amended to read: "…pins the exact resolved local path, S3 connection/bucket/object key, **or canonical directory root plus `manifest_hash`**, plus content hash before reading."
- A directory fixture whose manifest index order differs from ascending `object_id` order produces a report accepted by the unchanged `contract.py` and backend validators, with unique ascending member ids, `objects_discovered` equal to the data-member count, skip reasons only from the parent enum and coverage totals consistent; documentation and `other` members appear nowhere in the report; schema digests are unchanged.
- A fixture with two tabular data members and one data member whose bytes are a ZIP produces one accepted report with two `objects[]` entries and one `skipped[]` entry (`unsupported_type`); the ZIP is never expanded.
- The same member paths and bytes scanned under two different commitment keys yield identical `content_sha256` and different `object_id`s; changing one member's bytes changes that member's `object_id`, its hash and `content_sha256`; documentation/role/sample changes and member reordering change neither `content_sha256` nor the member ids (the locator commitment changes with `manifest_hash`).
- Golden vectors for §1.3(a)–(c) reproduce byte-for-byte in both repositories.
- Changing a member's bytes, removing a member, or replacing a member with a symlink outside the root after publish causes `FAILED_VOIDED` before any fact is computed and no charge.
- A role edit after publish does not change `objects_discovered` for the published version.
- No cloud-visible receipt or report field contains a member path or name (existing privacy tests extended with the directory fixture).
- Single-file and S3 fixtures pass unchanged, byte-for-byte.
