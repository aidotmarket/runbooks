## 1. What changes and what does not

1.1 The parent Gate 1 resolves the registered source handle "to the exact artifact" (§3 Stage A, `:40`), traverses "every reachable supported object in the registered root" (`:203`), and its A1 test pins "the exact resolved local path or S3 connection/bucket/object key plus content hash before reading" (`:315`). The pinned resolver is single-artifact: `ResolvedArtifact` holds one `local_path` or one `S3ObjectMetadata` and `resolved_object_count()` is 1 for either (`aim-data:app/services/source_artifact_resolver.py:34-51`); the locator commitment is an HMAC over that one path or key (`:53-65`); the scanner streams one artifact, computes `content_sha256` over its bytes (`aim-data:app/services/data_verification/scanner.py:126-151`) and passes one stream to the connector (`:173-184`).

1.2 This amendment adds one artifact kind, **`local_directory`**, for directory datasets published under S1717 D0/D3. **Unchanged:** every wire field of the customer-to-cloud manifest and its meaning — in particular `content_sha256` stays "SHA-256 of the complete resolved bytes" (parent `:124`) and `objects[]`/`coverage.skipped[]` stay in canonical ascending `object_id` order (signed `traversal_order: "canonical_object_identity_ascending"`, `aim-data:app/services/data_verification/contract.py:113`; validator `ai-market-backend:app/schemas/data_verification.py:685-689`; connector sort `aim-data:app/services/data_verification/connectors/eolymp_v1.py:388-389`); the literals `connector_version: "eolymp-v1"`, `traversal_root: "registered_source_artifact"`, `traversal_scope: "all_reachable_supported_objects"` and `canonicalization_version: "python-json-sort-compact-v1"`; the closed skip-reason enum (`permission_denied`, `unsupported_type`, `timeout`; `ai-market-backend:app/schemas/data_verification.py:466-487`); the coverage-total validators; the prohibition on seller-selected exclusions (`:203`) and on deleting skips (`:205`); the quote, payment, capture, publication and corpus-capture contracts; the privacy boundary (no raw member names, paths, error text or records in cloud-visible fields); and the single-file and S3 kinds.

1.3 **The one item requiring the CORE S3 decision:** the preimage of `artifact_locator_commitment` for the new kind is the canonical directory root realpath **plus `manifest_hash`** (§2.4). No field is added, widened, made more precise or repurposed; the commitment's shape, key and privacy posture are unchanged. Max's approval of this amendment records the decision that defining a preimage for a new artifact kind is admissible under parent `:110`. If the panel judges otherwise, this line is the one to change and the amendment falls back to the root realpath alone (with manifest binding carried by the version instead).

## 2. The directory root

1. **Registered root.** For a listing whose active version was published from a directory dataset, the registered root is the **version-pinned data-member set**: the members with `role = data` in the published `DatasetManifest` (S1717 D0). This is what "all reachable supported objects in the registered root" (`:203`, `traversal_scope`) means for this kind: the root definition changed, the scope literal did not. Members with other roles are not in the root; they are neither traversed nor reported as skipped. The root is frozen by the published version, not by live roles: a role edit after publish does not change the root of any existing version.
2. **Resolution.** `ResolvedArtifact` gains `kind = "local_directory"` with `root_path` (canonical realpath of the published version's member root, S1717 D1/D1a), `manifest_hash`, and `members[]` (index, canonical relative path, size, SHA-256) taken from the pinned manifest; `resolved_object_count()` returns `data_member_count`. Resolution refuses (`ArtifactResolutionError`) when the listing's active version has no local-route manifest.
3. **Exact binding before reading (the pre-read pass).** Before any fact is computed, the conduit walks the root members **in manifest index order** and verifies each: the realpath of `root_path/relative_path` stays inside `root_path` (no symlink escape), and its size and SHA-256 equal the manifest. Any mismatch, missing member or file outside the root is a **stale-manifest failure**: the scan terminates `FAILED_VOIDED` (parent `:219`, hold voided, nothing publishes) with no partial report. A member is never silently skipped for a manifest mismatch; the skip enum is reserved for the parent's three runtime reasons, which still apply per member during fact traversal (for example a member that becomes unreadable after the pre-read pass is `permission_denied`).
4. **Commitments and content hash.** `artifact_locator_commitment` = HMAC (same customer-held key as the parent) over the canonical `root_path` plus `manifest_hash` (§1.3). `content_sha256` = SHA-256 over a **length-framed concatenation of the data members' bytes** (`u64-be(size) || bytes` per member, members in ascending `object_id` order), computed during the pre-read pass; it therefore changes if and only if some data member's bytes change, and is unaffected by documentation/`other` members, roles or sample flags. `objects[].object_id` = the customer-held-keyed HMAC over the member's canonical relative path plus SHA-256, so member comparison across runs is stable while no path reaches ai.market.
5. **Traversal and reporting order.** Fact traversal runs one connector stream per member (the connector is unchanged; the scanner iterates members), and the report emits `objects[]` and `coverage.skipped[]` **in ascending `object_id` order** exactly as today — manifest index order is used only for the pre-read pass in §2.3, never for the wire. `coverage.objects_discovered` is the observed member count from the pre-read pass; the conduit fails closed (`FAILED_VOIDED`) if it differs from `data_member_count`, so declared and observed always agree in an accepted report. Aggregate facts are computed over all scanned members exactly as the S3 kind computes them over its objects. The quote probe reports `objects_discovered = data_member_count` and `size_class` from `total_data_bytes`.
6. **Fulfilment parity.** Fulfilment and verification resolve the same version-pinned root and manifest (parent A1 `:315`, amended below), so a buyer's delivered set and the scanned set are the same members with the same hashes (S1717 D-bytes).

## 3. Acceptance additions (to the parent's A1 list)

- A1 §6 is amended to read: "…pins the exact resolved local path, S3 connection/bucket/object key, **or canonical directory root plus `manifest_hash`**, plus content hash before reading."
- A directory fixture whose manifest index order differs from ascending `object_id` order produces a report accepted by the unchanged `contract.py` and backend validators, with `objects_discovered` equal to the data-member count, skip reasons only from the parent enum and coverage totals consistent; documentation and `other` members appear nowhere in the report; schema digests are unchanged.
- Two directory versions with identical data-member paths and bytes but changed documentation/role/sample metadata have identical `content_sha256` and different locator commitments; changing one data-member byte changes that member's `object_id`, the per-member hash and `content_sha256`.
- Changing a member's bytes, removing a member, or replacing a member with a symlink outside the root after publish causes `FAILED_VOIDED` before any fact is computed and no charge.
- A role edit after publish does not change `objects_discovered` for the published version.
- No cloud-visible receipt or report field contains a member path or name (existing privacy tests extended with the directory fixture).
- Single-file and S3 fixtures pass unchanged.
