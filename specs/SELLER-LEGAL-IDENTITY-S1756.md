The current sole-trader resolver looks for a platform `billing_entities` row through `listings.stripe_connect_account_id`, or transient typed/old terms data (`legal_identity.py:115-191`); a Workspace listing does not set that Connect column (`seller_listing_publication.py:139-149`). The frontend **already sends** `license_selection` (`api/sellerListingPublication.ts:27`) and **already renders** `SellerLicenseSelection` in the licence step (`components/seller-workspace/WorkspaceData.tsx:61`), saved through `SavedWorkspaceData.tsx:17-22,65-75`. Add identity status and fields inside that step. `SellerPublication.tsx:32-36` currently treats every 409 as stale review/files; fix that error mapping.

## 2. Stripe-first capture

Select the seller's Connect account deterministically **before any Stripe call**. Resolve the seller's party and its `PartyIdentity(provider='stripe_connect')` bridge through `get_stripe_connect_identity(user_id, db)` (`app/domains/crm/core/stripe_connect_identity.py:148-161`). Its `scalar_one_or_none()` can raise `MultipleResultsFound`: catch that as `LEGAL_IDENTITY_CONFLICT`, never a 500. If bridge and `users.stripe_account_id` both exist, they must agree. If the bridge is absent but the legacy ID exists, use `get_stripe_connect_identity_by_account_id`'s global `(provider='stripe_connect', external_id)` lookup (`stripe_connect_identity.py:164-173`): only an absent result or a result for **this seller's party** permits that legacy ID. A result for another party conflicts. Every ambiguous case returns a safe, non-disclosing 409 `LEGAL_IDENTITY_CONFLICT`, with no Stripe call or acceptance. Record the selected account ID and bridge/legacy lookup provenance in the protected identity event. Require the retrieved Stripe Account `id` to equal the selected ID. Do not use `seller_profiles`, `billing_entities`, display names, email, tax IDs, or Person records as legal-name authority.

Retrieve through the existing async Stripe wrapper with an explicit bounded timeout, **before** any DB row/listing lock or acceptance transaction. The pinned onboarding creates Standard accounts and an Account Link (`stripe_connect_service.py:77-104`; `stripe_connect.py:124-185`). Stripe's [Account object](https://docs.stripe.com/api/accounts/object) says `company` and `individual` return only a subset after an Account Link or Account Session is created when Stripe collects requirements; its [Accounts API](https://docs.stripe.com/api/accounts) says **some properties can no longer be updated** at that point. Treat `company.name` for `business_type=company` or joined `individual.first_name` and `last_name` for `business_type=individual`, together with `account.country`, as usable only when actually returned and valid. Do not infer a company name from an individual's `company` object. Unknown type or incomplete/redacted fields mean `required`; exceptions, timeout, malformed response, wrong account, or unavailable key mean `IDENTITY_SERVICE_UNAVAILABLE` (503) when no stored identity can be used. Verify Standard test-account visibility during build.

## 3. Persisted seller identity and concurrency

Add `seller_legal_identities`: `user_id` unique/primary FK, legal name (1–255 visible characters after NFC/trim; reject controls), uppercase jurisdiction from a pinned ISO 3166-1 alpha-2 list, source `stripe_connect|seller_typed`, selected Connect account ID nullable, `version` monotonic, and capture/update timestamps. Pin the list to the ISO Online Browsing Platform's current ISO 3166-1 alpha-2 assigned codes at build time as a reviewed, versioned application fixture; use the same fixture for API and UI validation and document updates. Add append-only `seller_legal_identity_events` with seller ID, actor, request ID, source, account ID **and bridge/legacy lookup provenance**, previous/new values and versions, reason, timestamp. Current row plus events are restricted personal data: owner-scoped authenticated GET returns only current name/country/source/version; support reads use a separately authorized support/audit role and audited seller-ID lookup, never a broad listing/export endpoint. No names in generic logs, URLs, analytics, or client error details.

Add a dedicated `resolve_seller_legal_identity(db, seller_id, expected_version?)` that reads this persisted row for seller acceptance. Leave `resolve_legal_identity`, buyer/order calls (`order_service.py:1015`), organization billing/reconciliation/backfill, and existing buyer records unchanged. There is no live Stripe call in this resolver. It rejects absent rows, selected-account changes, or expected-version mismatch; it never falls back to old terms or transient typed values. Acceptance copies the row's name/jurisdiction and stores `identity_id` plus `version` in the same transaction. Publication checks that the acceptance's stored version equals the current identity version before binding; a mismatch refuses publication. Historical signed records stay frozen.

`GET /api/v1/seller-workspace/legal-identity` reads stored state only, plus a local selected-account-ID-change check; it never calls Stripe or writes. A changed or ambiguous account ID conflicts even during an outage. With no linked account and no row, return `required`. New `POST /api/v1/seller-workspace/legal-identity/refresh` performs deterministic account selection, then bounded Stripe-first retrieval and capture/persist. A complete Stripe value differing from a stored row under `legal_identity._comparison` (`legal_identity.py:85-87`) conflicts; an incomplete Stripe response leaves a stored row usable. A Stripe outage leaves a stored row usable **if its selected account ID still matches**; without a row return 503, not a typed prompt. `PUT` accepts typed `{legal_name,jurisdiction,expected_version}` only when the seller has **no resolvable Connect account** or a fresh, bounded, pre-lock Stripe check returned an incomplete identity for the selected account. Otherwise reject it; Stripe-sourced rows are never seller-editable. Complete Stripe data wins first capture; differing typed input conflicts. A seller may replace their own `seller_typed` row by PUT while no seller licence acceptance references that identity version: require the expected version, bump it by one, and append a correction event. Matching repeat PUT is idempotent. Once an acceptance binds that version, only the reviewed support path may replace it. The server rechecks selected account, version, source, and acceptance binding under lock before committing a Stripe/typed candidate and one event; if they changed during the network call, conflict and retry from a fresh GET. Serialize first capture and relink by locking the seller `users` row before reading/upserting the unique identity row; hold that lock only for the short DB write, and retry a unique-insert race once. No network call occurs under the lock.

GET and refresh return `{status:"known"|"required",source,legal_name,jurisdiction,version}` (null identity fields when required), `Cache-Control: private, no-store`; conflict is 409, unavailable is 503. Apply the same seller-session ACL and rate limits to GET and refresh; derive seller ID from that session only, with no target-user parameter or internal-key shortcut. Rate-limit PUT to 10 writes per seller per hour, validate on the server, and preserve a request ID for idempotency/audit. Client errors contain only code, safe message, and fixed `/seller-workspace/support/legal-identity` destination. Never serialize the existing `LegalIdentityConflict.detail` with its `sources` array for this seller path.

## 4. Acceptance paths and UI

Every production `_seller_identity`/seller-side `resolve_legal_identity` caller at the backend pin is accounted for: `seller_license_service.py:42-59,114` (shared acceptance), `app/gateway_v2/surfaces/publish.py:267-277` (gateway preflight), and `legal_terms.py:226,304` (user and admin terms). Production callers of shared `record_seller_license_acceptance` are `seller_listing_publication.py:163` (Workspace), `listing_management_service.py:136` (direct listing publish), and `aim_gateway_listing.py:112` (AIM gateway). All sole-trader branches must read the persisted row and reject missing/conflicting versions, while organization branches retain their existing resolver. No seller acceptance path may create an identity from supplied terms fields.

For **seller-scope acceptance** by an individual on `POST /legal/terms/accept` or `/admin/accept`, compare supplied `business_legal_name`/`jurisdiction` with the already-persisted sole-trader row and write only the matching resolved snapshot; reject absent/mismatched identity. Discriminate by acceptance context and the authenticated/target user's seller capability via `assert_user_capability(user, db, "seller", ...)` as in `stripe_connect.py:135`, not role alone or `scope=individual` alone. At the pinned code, **both routes can be on a buyer individual path**: `/accept` takes any authenticated user via `get_user_or_internal_key` (`legal_terms.py:212-226`), while `/admin/accept` takes an admin/internal caller and a target `accepted_by_user_id` (`legal_terms.py:289-304`); each currently maps every individual request to `sole_trader` when licences are enabled. Preserve buyer individual/order and organization terms behavior. `record_terms_acceptance` calls `activate_inherited_listings` (`terms_acceptance_service.py:230-244`), which currently can use request values when `derived_identity` is absent; require the persisted sole-trader identity there before creating a derivative `seller_license_acceptances` row (`inherited_listing_license_service.py`). Gate seller terms/derived acceptance in one DB transaction; a refusal leaves neither acceptance nor derivative listing binding. Gateway, direct listing, AIM gateway, and Workspace publish use the same persisted-only contract. Their callers must obtain/refresh status before acceptance; none calls Stripe inside a publish/listing lock.

In the existing `SellerLicenseSelection` step, call POST refresh on entry, then GET; GET again after successful PUT. `known` displays “Legal name on the licence: <name> (<country>)”, labelled “from your Stripe account” or “saved by you” according to source, with no redundant save. A stored identity stays `known` during a Stripe outage; the response may flag a retryable refresh warning. `required` shows legal name/country alongside, but distinct from, signer name/title; save before licence acceptance. Carry the returned identity version with the saved licence selection into approval and publish so the server can reject a version mismatch rather than silently bind a changed identity. Block licence save/publish while identity is required, conflicting, or unavailable without a saved row. In `SellerPublication`, branch on `response.data.detail.code`: map `SELLER_LEGAL_IDENTITY_REQUIRED` to the licence step and `LEGAL_IDENTITY_CONFLICT` to support; map 503 to retry. Only an actual review/source/hash conflict sets `stale=true`. Never display raw Stripe details in error copy.

### Reviewed support correction procedure

The support destination opens a restricted case, not a self-service edit. An authorized support operator records the seller's authenticated request, current row/version/event ID, bridge and legacy account IDs, Stripe account ownership evidence, and the legal document or seller attestation in a restricted case store. A second authorized reviewer approves the exact replacement and reason. A dedicated support service checks that approval, current account linkage, and expected version under the seller-row lock, writes version `+1` and an append-only correction event with both actor IDs and case reference, then returns only a safe status to the seller. Reject stale approval/version; do not amend old signed acceptances. Support/audit access to the restricted case and identity event is role-gated and itself audited. No hand SQL or ordinary PUT correction.

## 5. Rollout and proof

One additive migration creates the row/event tables, constraints and indexes; no bulk backfill from old terms or billing data. `LISTING_LICENSES_ENABLED` is **already true globally in production** and sole-trader publish is broken, so there is no seller cohort or new flag enablement. Deploy backend and frontend together. Verify with `max@kisa.cat` through the real Workspace, then `sergey@eolymp.com`, then the real tester `code@sentineldata.com.ua`; record exact deployed SHAs, selected account provenance, identity version/event IDs, one frozen licence acceptance, and publish outcome without logging legal names. Rollback is revert deploy; retain identity rows, events and signed acceptances. Do not roll back the migration after data exists.

Build tests cover these five account-selection cases before any Stripe call: (1) duplicate `stripe_connect` rows for the seller's party (`MultipleResultsFound`); (2) bridge and legacy ID disagree; (3) no bridge, legacy ID has no global bridge; (4) no bridge, legacy ID maps to this seller's party; (5) no bridge, legacy ID maps to another party. Also cover bridge/legacy agreement. Assert every ambiguous case returns safe 409 with no Stripe call or acceptance. Cover read-only GET versus mutating POST refresh, same ACL/rate limits for both, Stripe complete/incomplete/error/timeout, no account, PUT allowed with no resolvable account or incomplete Stripe identity and rejected with complete identity, pre-acceptance `seller_typed` replacement/version bump/one event, post-binding PUT refusal, Stripe-sourced PUT refusal, persisted use during outage, account relink, first-capture concurrency, idempotent PUT/event count, publication version equality, support correction, auth/ACL, seller path inventory above, unchanged buyer/order/organization behavior, and frontend status/error mapping. A Stripe test-mode account must prove actual Standard field visibility; a full-field fixture alone does not. This spec is not Gate 4 production proof.
