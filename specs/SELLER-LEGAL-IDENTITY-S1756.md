# Seller legal identity for sole traders — S1756 Gate 1 + Gate 2

**Status:** Proposed design and build contract; review required before build. **Owner decision:** Max, Event `a93e2c1a`: “Stripe first, ask if missing.” **Scope:** backend and Seller Workspace frontend. No implementation is authorized by this document alone.

## 1. Problem and pinned evidence

The S1756 rolled-back production rehearsal found that `max@kisa.cat` and `sergey@eolymp.com` (sole traders with `users.stripe_account_id` and payouts enabled) cannot publish with `LISTING_LICENSES_ENABLED=true`: HTTP 409 `SELLER_LEGAL_IDENTITY_REQUIRED`. The code path is `SellerListingPublicationService.publish` → `record_seller_license_acceptance` → `_seller_identity` → `resolve_legal_identity` (`backend@20eb5d7295 app/services/seller_listing_publication.py:159-166`; `app/services/seller_license_service.py:42-59,104-115`). The acceptance freezes the resolved legal name and jurisdiction (`app/services/seller_license_service.py:116-130`).

The present billing source joins `billing_entities` to `listings.stripe_connect_account_id` (`app/services/legal_identity.py:115-142`); `billing_entities` is the platform finance model (`app/models/finance.py:31-57`). The Workspace-created listing does not set that Connect column (`app/services/seller_listing_publication.py:139-149`; column at `app/models/marketplace.py:120`). The typed source reads call arguments, then organization reconciliation or latest terms data; there is no dedicated durable sole-trader identity (`app/services/legal_identity.py:145-191`). Publish passes no typed values (`app/services/seller_license_service.py:49-55`). The frontend maps **every** publish 409 to stale files/listing copy (`frontend@c24135ec components/seller-workspace/SellerPublication.tsx:32-36`).

This contract addresses that failure without changing the organization path. Existing terms acceptance passes typed legal values, and the buyer order constructor calls the same resolver; both must use the sole-trader policy consistently (`backend app/api/v1/endpoints/legal_terms.py:223-240`; `app/services/order_service.py:998-1019`). Existing frontend `WorkspaceData` is the “Choose what to sell” surface, but its pinned UI currently contains file selection, not a licence identity form (`frontend components/seller-workspace/WorkspaceData.tsx:41-54`); build the licence-step integration explicitly rather than assuming it exists.

## 2. Stripe reality and design decision

The active creation path calls `stripe.Account.create(type="standard")`, stores the ID on `users.stripe_account_id`, and uses Stripe-hosted onboarding (`backend app/services/stripe_connect_service.py:77-104`; `app/api/v1/endpoints/stripe_connect.py:124-162`; `app/models/user.py:84`). Use `stripe.Account.retrieve(account_id)` through the existing async wrapper (`app/core/stripe_async.py:1-11,45-62`), with that user's account ID only. Do not use `billing_entities`, `business_profile.name`, a display name, signer name, email, tax ID, or a Person lookup as legal-name authority.

Stripe's [Account object](https://docs.stripe.com/api/accounts/object) includes `country`, `company`, and `individual`, but says that Standard/Express accounts with Stripe-collected requirements expose only a subset of company/individual details after Account Link or Account Session creation. Stripe's [Standard onboarding guide](https://docs.stripe.com/connect/enable-payment-acceptance-guide) says account information cannot be read or written after the Standard Account Link is created. Thus `company.name` and especially `individual.first_name`/`individual.last_name` are **opportunistic**, not guaranteed readable in this integration. The normal path for an already onboarded individual may be seller typing. Never claim the platform can always fetch an individual's legal name. `account.country` is readable per the Account object; it alone is insufficient. Confirm field visibility against a test Standard account at build time; do not fetch live personal names for spec review.

For `business_type=company`, use `company.name` plus `account.country` only when both are returned and valid. For `business_type=individual`, use joined nonempty `individual.first_name` and `individual.last_name` plus `account.country` only when all are returned and valid. Do not substitute `company.name` for an individual, nor use a representative's name for a company. For other/unknown business types or missing/redacted fields, report `required`; the typed flow is available. A successful Account response with redacted fields is missing data; a Stripe exception, timeout, bad response, wrong account, or unavailable key is `IDENTITY_SERVICE_UNAVAILABLE` (503, retriable), never `required`.

## 3. Durable data and resolution contract

Add `seller_legal_identities` with `user_id UUID PRIMARY KEY REFERENCES users(id)`, `legal_name VARCHAR(255) NOT NULL`, `jurisdiction CHAR(2) NOT NULL` (valid ISO 3166-1 alpha-2, uppercase), `source` constrained to `stripe_connect|seller_typed`, `stripe_account_id VARCHAR(100) NULL`, `captured_at TIMESTAMPTZ NOT NULL`, `updated_at TIMESTAMPTZ NOT NULL`, and a monotonic version. Add an append-only `seller_legal_identity_events` table with event ID, `user_id`, actor, source, account ID, previous/new name and country, reason, request ID, and timestamp; restrict reads to authorized support/audit roles. The row is current state; the events preserve changes. Do not put legal names in generic audit payloads, logs, URLs, analytics, or client error detail. A Stripe-sourced row requires the account ID. A typed row records the linked account ID when present to detect relinking.

Sole-trader resolver, used by seller licence acceptance, individual terms acceptance, inherited-listing acceptance, and buyer/order identity records:

1. Lock/read the current row for `user_id`; read `users.stripe_account_id` in the same transaction. An account-ID change against a stored row is a conflict, not a silent rebinding. If an account ID exists, retrieve that exact account with a bounded timeout. A Stripe failure yields 503 even if a stored row exists, so a stale cache never silently bypasses reconciliation. If no account ID exists, use a stored typed row if present; otherwise `required`.
2. If Stripe yields a complete legal name and country, compare it with the stored row using existing `legal_identity._comparison` semantics (NFC/trim on intake, whitespace collapse and casefold for name, uppercase ISO code for country; `app/services/legal_identity.py:59-87`). If no row, insert source `stripe_connect` and an audit event. If equal, retain the stored row and original source. If different, raise `LEGAL_IDENTITY_CONFLICT`; do not overwrite or issue an acceptance.
3. If Stripe succeeds but returns no complete usable identity, use the stored row if present. Otherwise raise `LegalIdentityRequired`; only then offer typed capture. A missing name is not evidence that a previously captured name changed. A changed available country **is** a conflict. Partial Stripe names are never merged with typed fields.
4. Typed input enters only through the validated persistence service (including existing terms/API flows), after the same Stripe check proves no complete Stripe identity is available. A matching repeat PUT is idempotent and creates no new event. A different typed value, a Stripe-visible identity, or a changed account ID returns `LEGAL_IDENTITY_CONFLICT`; the ordinary PUT never edits an existing legal identity. A typed row later contradicted by a complete Stripe identity conflicts at the next read/acceptance. No caller may use transient typed values to bypass this service.

Keep `resolve_legal_identity(party_type="organization")`, its billing/organization reconciliation, and organization backfill unchanged (`app/services/legal_identity.py:194-236`). Branch before `_billing_source` for sole traders; do not make platform billing entities a seller identity source. Identity capture and licence/terms record creation must commit atomically where in one request; refusal must roll back any provisional listing, acceptance, or identity event. Preserve historical signed records as frozen snapshots; reconciliation changes only future records. Existing inherited listings remain pending until a real current-identity terms acceptance as required by the licence contract.

**Reconciliation:** `LEGAL_IDENTITY_CONFLICT` returns a safe message and a fixed seller support/settings destination, not competing names. The seller can inspect their saved value in their authenticated status screen and request correction; authorized support verifies Stripe/account ownership and the legal document, records reason and actor, then performs a reviewed version-checked correction with an append-only event. Never auto-prefer either source or let the typed PUT resolve conflict. Existing organization reconciliation URL remains as is.

## 4. API and UI contract

Add seller-authenticated, feature-gated `GET /api/v1/seller-workspace/legal-identity` and `PUT /api/v1/seller-workspace/legal-identity`. Derive `user_id` solely from the authenticated seller session; no target user ID parameter, internal key shortcut, cross-user lookup, or organization-member delegation. GET resolves/reconciles and returns `{status:"known"|"required",source,legal_name,jurisdiction}` (null fields when required); conflict is 409 and service failure is 503. Set `Cache-Control: private, no-store`. PUT accepts only `{legal_name,jurisdiction}`; Unicode NFC/trim, 1–255 visible characters, no control characters, country in the supported ISO list. Return the same known shape. Use a seller-scoped rate limit (e.g. 10 writes/hour) and request ID for idempotency/audit; same normalized value returns existing row, while changed value returns conflict. Server validation and rate limit apply independent of UI. Existing terms/agent routes must not allow an alternative unpersisted sole-trader identity write.

In Seller Workspace’s licence step under “Choose what to sell,” request status once on entry and refresh after a successful PUT. `known` displays **“Legal name on the licence: <name> (<country>) — from your Stripe account”** for `stripe_connect`; for `seller_typed`, label it as saved by the seller. `required` shows Legal name and Country fields next to signer fields and saves them once before licence acceptance. Keep legal name distinct from signer name/title. If unchanged, show “Saved” and do not ask to save again. If missing, say: “Your legal name and country are not saved. Save them to accept the licence and publish.” Disable or explain licence save/publish until identity is known, and expose retry for 503. A conflict explains that publish is blocked pending reconciliation and links to the fixed destination. Do not show a successful acceptance/publish state before server confirmation. The pinned frontend currently sends publication without `license_selection` (`frontend api/sellerListingPublication.ts:24-29`), while the flagged backend compares it and records acceptance (`backend app/services/seller_listing_publication.py:130-166`); the build must wire the existing licence selection/signer contract end to end, not add only identity fields.

`SellerPublication` must branch on `response.data.detail.code` before treating 409 as stale (`frontend components/seller-workspace/SellerPublication.tsx:32-36`): `SELLER_LEGAL_IDENTITY_REQUIRED` → “Your legal name and country are not saved; return to the licence step”; `LEGAL_IDENTITY_CONFLICT` → reconciliation message/link; `IDENTITY_SERVICE_UNAVAILABLE` (503) → “We could not check your legal identity right now; try again.” Only actual approval/source/hash conflict uses the existing “listing or files changed” copy and `stale=true`. Keep retries idempotent and display no raw Stripe or personal details from error payloads.

## 5. Migration, rollout, verification

One additive migration creates current and event tables, constraints, indexes, and access policy. **No bulk backfill is needed for existing rows:** first resolution lazily captures visible Stripe data, or the seller types once. Do not infer identity from old terms, display names, or platform billing rows. Existing signed acceptance/order snapshots are not rewritten. Migration rollback is allowed only before any identity rows/events or new acceptances exist; otherwise disable behavior and retain legal records.

Ship backend migration and API first with `LISTING_LICENSES_ENABLED=false` behavior unchanged; deploy frontend behind the same licence capability; then enable in a controlled seller cohort after Stripe test-account visibility and error-path checks. Watch counts of required/conflict/unavailable by opaque user ID, latency, and publish outcomes, without names. Flag off hides new licence flow and restores pre-flag behavior while preserving captured rows, audit, and signed records. An outage must not turn into a typed prompt or bypass existing acceptance gates.

**Build files:** backend `app/services/legal_identity.py`, a small sole-trader persistence/Stripe adapter, `app/models/*` plus Alembic migration/registry, seller-workspace identity endpoints and schemas, seller licence/terms/inherited acceptance error mapping, and tests; frontend `WorkspaceData` licence-step component/API, `SellerPublication`, and tests. Keep organization code and existing legal instruments unchanged.

**Tests:** unit cases for normalization/ISO validation, Standard company/individual/missing/redacted fields, stored equal/different Stripe and typed values, account relink, no-account typed flow, idempotent PUT and audit cardinality, rate limit, auth isolation, wrong account, exception and timeout → 503; organization path parity. Integration tests use a Stripe Account retrieval stub for company, individual, missing fields, error, and timeout; verify seller licence, terms, inherited-listing activation, and buyer/order record snapshots use the same sole-trader resolver, transaction rollback on refusal, flag-off parity, and unchanged historical snapshots. Frontend tests cover known/required/conflict/unavailable displays, save-once behavior, real refusal mapping, and publication retry identity. Test Standard account field visibility in Stripe test mode before rollout; a fixture with full individual fields alone is insufficient.

**Production acceptance, after reviewed build and controlled enablement:** with the exact deployed SHAs, migration and flag recorded, `max@kisa.cat` publishes the S1756 rehearsal listing through the real Seller Workspace and produces one frozen seller licence acceptance; `sergey@eolymp.com` identity status resolves to known, by Stripe if readable or by one saved typed entry if missing. Record consent-safe UI/API evidence and audit IDs, not raw legal names in logs. These checks are future Gate 4 proof, not evidence supplied by this spec.

## 6. Out of scope and risks

Out of scope: organization identity changes; legal identity verification/KYC, tax or payout eligibility; changing licence text or past signed records; Stripe account updates; public disclosure of names; bulk import from prior terms; production data edits during spec review. Risks: Standard-account field redaction makes typed capture common; account relinking or changed Stripe fields creates support reconciliation load; live Stripe latency/outage blocks publish; legal-name exposure in client logs/support tools; rollout mismatch between backend flag and frontend licence step. Mitigate with explicit missing/error distinction, bounded timeout, private responses, redacted telemetry, atomic writes, version checks, and controlled enablement.
