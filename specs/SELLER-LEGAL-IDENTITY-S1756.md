Add identity status and fields inside that step. `SellerPublication.tsx:32-36` currently treats every 409 as stale review/files; fix that error mapping.

## 2. Stripe-first capture

Resolve the seller's Connect account through `get_stripe_connect_identity(user_id, db)` and `PartyIdentity(provider='stripe_connect').external_id` (`app/domains/crm/core/stripe_connect_identity.py`), as `app/api/v1/endpoints/stripe_connect.py:143-157` does. Use `users.stripe_account_id` only when the bridge is absent. If both exist and differ, return `LEGAL_IDENTITY_CONFLICT`; never pick one silently. Record the retrieved account ID and bridge/legacy lookup provenance in the protected identity event. Require the retrieved Stripe Account `id` to equal the selected ID. Do not use `seller_profiles`, `billing_entities`, display names, email, tax IDs, or Person records as legal-name authority.

Retrieve through the existing async Stripe wrapper with an explicit bounded timeout, **before** any DB row/listing lock or acceptance transaction. The pinned onboarding creates Standard accounts and an Account Link (`stripe_connect_service.py:77-104`; `stripe_connect.py:124-185`). Stripe's [Account object](https://docs.stripe.com/api/accounts/object) says `company` and `individual` return only a subset after an Account Link or Account Session is created when Stripe collects requirements; its [Accounts API](https://docs.stripe.com/api/accounts) says **some properties can no longer be updated** at that point. Treat `company.name` for `business_type=company` or joined `individual.first_name` and `last_name` for `business_type=individual`, together with `account.country`, as usable only when actually returned and valid. Do not infer a company name from an individual's `company` object. Unknown type or incomplete/redacted fields mean `required`; exceptions, timeout, malformed response, wrong account, or unavailable key mean `IDENTITY_SERVICE_UNAVAILABLE` (503) when no stored identity can be used. Verify Standard test-account visibility during build.

## 3. Persisted seller identity and concurrency

Add `seller_legal_identities`: `user_id` unique/primary FK, legal name (1–255 visible characters after NFC/trim; reject controls), uppercase jurisdiction from a pinned ISO 3166-1 alpha-2 list, source `stripe_connect|seller_typed`, selected Connect account ID nullable, `version` monotonic, and capture/update timestamps. Pin the list to the ISO Online Browsing Platform's current ISO 3166-1 alpha-2 assigned codes at build time as a reviewed, versioned application fixture; use the same fixture for API and UI validation and document updates. Add append-only `seller_legal_identity_events` with seller ID, actor, request ID, source, account ID **and bridge/legacy lookup provenance**, previous/new values and versions, reason, timestamp. Current row plus events are restricted personal data: owner-scoped authenticated GET returns only current name/country/source/version; support reads use a separately authorized support/audit role and audited seller-ID lookup, never a broad listing/export endpoint. No names in generic logs, URLs, analytics, or client error details.

Add a dedicated `resolve_seller_legal_identity(db, seller_id, expected_version?)` that reads this persisted row for seller acceptance. Leave `resolve_legal_identity`, buyer/order calls (`order_service.py:1015`), organization billing/reconciliation/backfill, and existing buyer records unchanged. There is no live Stripe call in this resolver. It rejects absent rows, selected-account changes, or expected-version mismatch; it never falls back to old terms or transient typed values. Acceptance copies the row's name/jurisdiction and binds its version (new FK/version column or immutable event reference) in the same transaction. Historical signed records stay frozen.

`GET /api/v1/seller-workspace/legal-identity` is the workspace-entry refresh: resolve the bridge/legacy account, call Stripe first if an ID exists, then persist a complete Stripe identity or return the stored row. A complete Stripe value differing from a stored row under `legal_identity._comparison` (`legal_identity.py:59-87`) conflicts; an incomplete Stripe response leaves a stored row usable. A Stripe outage leaves a stored row usable **if its selected account ID still matches**; without a row return 503, not a typed prompt. A changed account ID is a conflict even during outage. With no linked account and no row, return `required`. `PUT` accepts only typed `{legal_name,jurisdiction,expected_version}` after a fresh, bounded, pre-lock Stripe check proves the selected account lacks a complete identity; it cannot overwrite an existing different row. Matching repeat PUT is idempotent. Complete Stripe data wins first capture; differing typed input conflicts. The server rechecks selected account and version under lock before committing the Stripe/typed candidate and one event; if they changed during the network call, conflict and retry from a fresh GET. Serialize first capture and relink by locking the seller `users` row before reading/upserting the unique identity row; hold that lock only for the short DB write, and retry a unique-insert race once. No network call occurs under the lock. A supported correction is the only way to replace a conflicting row.

GET returns `{status:"known"|"required",source,legal_name,jurisdiction,version}` (null identity fields when required), `Cache-Control: private, no-store`; conflict is 409, unavailable is 503. Derive seller ID from seller session only; no target-user parameter or internal-key shortcut. Rate-limit PUT to 10 writes per seller per hour, validate on the server, and preserve a request ID for idempotency/audit. Client errors contain only code, safe message, and fixed `/seller-workspace/support/legal-identity` destination. Never serialize the existing `LegalIdentityConflict.detail` with its `sources` array for this seller path.

## 4. Acceptance paths and UI

Every production `_seller_identity`/seller-side `resolve_legal_identity` caller at the backend pin is accounted for: `seller_license_service.py:42-59,114` (shared acceptance), `gateway_v2/surfaces/publish.py:267-277` (gateway preflight), and `legal_terms.py:226,304` (user and admin terms). Production callers of shared `record_seller_license_acceptance` are `seller_listing_publication.py:163` (Workspace), `listing_management_service.py:136` (direct listing publish), and `aim_gateway_listing.py:112` (AIM gateway). All sole-trader branches must read the persisted row and reject missing/conflicting versions, while organization branches retain their existing resolver. No seller acceptance path may create an identity from supplied terms fields.

For seller actors taking individual `POST /legal/terms/accept` or `/admin/accept`, compare supplied `business_legal_name`/`jurisdiction` with the already-persisted sole-trader row and write only the matching resolved snapshot; reject absent/mismatched identity. Select this branch by the authenticated/target user's seller role or capability, not by `scope=individual` alone. `record_terms_acceptance` calls `activate_inherited_listings` (`terms_acceptance_service.py:230-244`), which currently can use request values when `derived_identity` is absent; require the persisted sole-trader identity there before creating a derivative `seller_license_acceptances` row (`inherited_listing_license_service.py`). Keep buyer individual/order and organization terms behavior unchanged. Gate seller terms/derived acceptance in one DB transaction; a refusal leaves neither acceptance nor derivative listing binding. Gateway, direct listing, AIM gateway, and Workspace publish use the same persisted-only contract. Their callers must obtain/refresh status before acceptance; none calls Stripe inside a publish/listing lock.

In the existing `SellerLicenseSelection` step, GET on workspace entry and after successful PUT. `known` displays “Legal name on the licence: <name> (<country>)”, labelled “from your Stripe account” or “saved by you” according to source, with no redundant save. A stored identity stays `known` during a Stripe outage; the response may flag a retryable refresh warning. `required` shows legal name/country alongside, but distinct from, signer name/title; save before licence acceptance. Carry the returned identity version with the saved licence selection into approval and publish so the server can reject a version mismatch rather than silently bind a changed identity. Block licence save/publish while identity is required, conflicting, or unavailable without a saved row. In `SellerPublication`, map `SELLER_LEGAL_IDENTITY_REQUIRED` to the licence step, `LEGAL_IDENTITY_CONFLICT` to support, and 503 to retry; only an actual review/source/hash conflict sets `stale=true`. Never display raw Stripe details in error copy.

### Reviewed support correction procedure

The support destination opens a restricted case, not a self-service edit. An authorized support operator records the seller's authenticated request, current row/version/event ID, bridge and legacy account IDs, Stripe account ownership evidence, and the legal document or seller attestation in a restricted case store. A second authorized reviewer approves the exact replacement and reason. A dedicated support service checks that approval, current account linkage, and expected version under the seller-row lock, writes version `+1` and an append-only correction event with both actor IDs and case reference, then returns only a safe status to the seller. Reject stale approval/version; do not amend old signed acceptances. Support/audit access to the restricted case and identity event is role-gated and itself audited. No hand SQL or ordinary PUT correction.
