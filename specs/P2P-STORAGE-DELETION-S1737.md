# Delete ai.market's seller-data storage and relay code (S1737)

**Authority:** Max, 2026-09-22, S1737: "simplify code whenever possible to not be additive" (Event Ledger `109db5e8`), then, on the proposal to delete rather than guard: "Then do it" (`87fb454b`). Rule: `runbooks/data-delivery-p2p.md`. Rescoped S1739: Max decided (Event Ledger `e7e104d5`; CORE v9.19, `45675b19`/`58dae0d1`) that a seller-chosen public sample is hosted by ai.market, so all sample code stays; and (S1737 handoff, `d26bc740`) that the deletion ships as one release, code and schema together, with no maintenance-window ceremony. Risk class: customer data and delivery, so unanimous Council (GLM, DeepSeek, Gemini) on this spec and on the build.

**Base:** ai-market-backend `main` after licence chunks E and D merge (agreed merge order, Mars peer 5851); rebase and re-cite at dispatch. Citations below are at `0d0d718d` (CORE v9.19; main is now `d5d2e391`, CORE.md only on top) unless marked. MP builds on `build/p2p-storage-deletion-s1737`.

## Principle

Delete every module whose purpose is to receive, buffer, stage, store, presign, proxy or relay seller bytes through ai.market, plus everything that exists only to serve those modules. Where a surviving caller branches into removed code, delete the branch so the flag-off behaviour becomes the only behaviour. No replacement abstractions, shims or new flags. The one exception is code that a surviving live path needs; it is named below.

## Keep

- The manifest contract for the future peer-to-peer design (Mars, peer message 5843): `listing_version_members`, `manifest_hash`, manifest intake and validation in `vz_publish` / `vz_publish_service.py`, `listing_summary.py`, `listing_versioning.py`, and `MULTI_FILE_DATASETS_ENABLED`, which afterwards gates local manifest publishing and the kept local sample route and sample serving (`vz_samples.py`, `multi_file_guard.py`, `public_sample_service.py`); it stays off. No new flag. The per-file grant/consume semantics and buyer-side hash check are the contract to rebuild peer to peer; their bucket-bound implementation goes.
- The live legacy delivery path (`fulfillment_listener_service.py` stream-to-disk, `delivery_service.py` `_queue_delivery_request`). It is how AIM Data orders deliver today; it goes under T-2026-000839 once a peer-to-peer replacement exists.
- Seller Workspace delivery from the seller's own bucket (`order_service` `assume_seller_role`, `seller_workspace_delivery`, `seller_workspace_r2.py`).
- The seller-chosen public sample, end to end: `listing_asset_store.py` sample functions, `public_sample_service.py`, `vz_samples.py`, the sample routes in `public.py`, the samples router include in `vz_publish.py`, sample validation in `vz_publish_service.finalize_local_version`, the `listing_sample_assets`, `seller_sample_assets` and `listing_asset_tombstones` tables and models, `WORKSPACE_SAMPLE_FILES_ENABLED`, and `require_listing_license_snapshot` on the sample route (licence Gate 2 §6 stands).
- Every #451 licence gate on a surviving door.

## One release

Code and schema ship together in one build and one deploy (Max, S1737 handoff `d26bc740`: no orders, one customer, do not protect traffic that does not exist). One Alembic migration drops the six delivery tables in foreign-key order (`transfer_part_receipts` before `transfer_session_members`; children before parents), the shared columns with `uq_transfer_manifest_receiving_order`, `ck_transfer_completion_state` and the `fulfillment_download_tokens.purchased_version_id` FK, and the `aim_nodes` relay columns; the models go in the same commit, so `alembic check` is clean. The migration sets `lock_timeout = '5s'` so a lock wait fails the deploy instead of stalling live tables (`orders`, `transfer_sessions`, `fulfillment_download_tokens`, `aim_nodes`, `users`, `listing_versions`); on failure it is simply redeployed. No service stop and no maintenance window. The downgrade recreates the empty tables, the null columns, and that index, check constraint and FK.

Production state read by Vulcan 2026-09-22 (procedure step 3 in `runbooks/data-delivery-p2p.md` prints the table and relay counts; the shared-column reads were separate `psql` counts): all nine storage tables 0 rows (six are dropped here; the three sample tables stay); `aim_nodes` 2 rows, 0 relay; `aim_sessions` 0 rows; `orders.delivery_manifest_hash`, `transfer_sessions.manifest_hash`/`staging_generation`, `fulfillment_download_tokens.manifest_hash`/`purchased_version_id` all null; `transfer_sessions.completion_state` all `none`.

Pass at the candidate SHA: no import of a removed module, no reference to a removed qualified name, no removed route in `app.routes`, no removed field on `Settings`; no reference to the removed models or to the shared-column and relay ORM attributes; zero `git grep` hits in `app` and `scripts` for the delivery-only column names in any form (`delivery_manifest_hash`, `staging_generation`, `completion_state`, `completion_lease_until`, `order_delivery_manifest_hash`); for the two names that also exist on kept tables, zero hits that refer to the dropped columns (`fulfillment_download_tokens.purchased_version_id`, and `manifest_hash` on `transfer_sessions` and `fulfillment_download_tokens`), with the script printing every surviving `purchased_version_id` and `manifest_hash` hit attributed to its kept owner (known kept: `orders.purchased_version_id` and its readers, `workspace_test_authority.purchased_version_id`, `agent_proposal.manifest_hash`, `dataset_manifest.manifest_hash`, and the `listing_versions`/`listing_sample_assets`/`listing_version_members` contract); for symbols removed from kept files (`listing_asset_store.py` above, the `orders.py` routes, the model attributes) the script takes the list above as input rather than parsing deleted files; `tests/test_listing_license_route_inventory.py` no longer lists the deleted `orders/{order_id}/members*` routes; `alembic check` clean; the migration upgrades and downgrades on a disposable database.
