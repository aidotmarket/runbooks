## 1. Decision and problem

S1656's `./bin/verify --from-clean-seed` proves listing publication, paid verification and Stripe setup/capture (AC1–AC12). Its acceptance summary gates seventeen browser criteria and a verification PaymentIntent, but no buyer order, device delivery, downloaded bytes or seller transfer (`environment:bin/verify:739-775`). The browser journey finishes the paid verification and gates those criteria (`environment:browser/s1590-money-path.spec.ts:1097-1129`). Verification payment is the seller buying verification, not buyer-01 buying the dataset.

The task brief records that no seller device has ever delivered a purchased dataset in this environment or production. Bundle `20260908T215737Z` is the supplied historical device/session proof reference, not delivery proof and not a fresh run of the v1.23.2 candidate. This authoring task did not rerun or certify that bundle. Every new acceptance run must independently establish the active seller device and then prove its response to the purchased order.

The new connected journey is: buyer-01 purchases seller-01's S3 fixture listing; the signed payment webhook requests fulfilment; the device at port 18081 answers over Trust Channel; the order reaches delivered; buyer-01 obtains and redeems a download token, GETs the presigned object directly, compares the bytes, and confirms receipt; a real test-mode Connect transfer must be recorded. Online, offline/reconnect and duplicate-delivery cases become mandatory inputs to the nightly result.

## 4. Purchase and download decisions

**Decision D2 — Canonical Stripe test data-order checkout.** Keep `ENABLE_CANONICAL_TX=true`, `STRIPE_TEST_MODE=true`, `DEMO_FULFILLMENT=false`. Drive buyer-01's authenticated `POST /api/v1/checkout/create` from the browser journey, then complete its returned real hosted Stripe checkout. Using the public purchase API from the signed-in browser context avoids pretending the owner-only synthetic listing page is buyer-visible (S1656 A2 item 3). Bind the exact buyer/seller/listing/Order/Transaction/Session/PaymentIntent, charge 2500 cents USD as the fixture listing price, and retrieve Stripe truth. Do not use `cs_e2e_mock_*`, `pi_e2e_mock_*`, paid verification, free purchase or direct status writes. Keep the S1590 paid-verification payment separate and unchanged.

The test webhook endpoint must subscribe to `checkout.session.completed` and `payment_intent.succeeded`; prove both signed provider deliveries in either order, and duplicate delivery through Stripe's own resend mechanism. Checkout completion is the fulfilment-driving branch; PaymentIntent success is backup payment confirmation. No `mode=setup`, transfer-created or bank-payout event substitutes for purchase completion. The existing setup event subscription remains for S1656. **Council question D2:** Is this canonical purchase surface sufficient despite synthetic listing visibility, with the existing narrow webhook exception and no additional suppression bypass?

**Decision D3 — Token issue, token redemption, direct presigned GET, exact bytes.** A 200 from `/orders/{id}/download`, a delivered label, a URL string or equal reported hashes alone is insufficient. The backend returns a usable signed token from authenticated `POST /api/v1/orders/{order_id}/download` and redeems it at proposed `POST /api/v1/orders/{order_id}/download/redeem` (body token, owning buyer authentication, `Cache-Control: no-store`, 303 Location to the unmodified device-issued S3 URL). Never append the JWT to the S3 query or proxy bytes.

**Durable single-object record (Chunk A):** populate `orders.delivery_file_path` with the exact S3 object key. Under the existing `orders.delivery_config` JSON, record the backend-derived `s3_bucket`, `s3_object_key` (equal to `delivery_file_path`), `s3_prefix`, `listing_version_id` (the purchased immutable version), `s3_version_id` (when versioned; otherwise null with an immutable run-owned key that must never be overwritten), `s3_presigned_url`, `presign_expires_at` (UTC), and `credential_generation`. Preserve `delivery_file_hash`, `delivery_file_size_bytes` and the first `delivered_at`. Bucket/key/version are parsed from the authenticated seller device's presigned URL and bound fail-closed to the listing's server-validated `raw_metadata.s3_connection.bucket` and the purchased `ListingVersion.prefix` with `object_count == 1` (Amendment G3.2 defines the exact rule; the former "explicit single-object manifest" source does not exist at base and is superseded). Ownership is never inferred from an arbitrary URL: the URL must arrive on the owning seller's Trust Channel response for this order and must pass the G3.2 binding. Store expiry as the earlier of the device's reported expiry and the URL's signed expiry; reject missing, malformed or elapsed expiry. The pinned response already contains URL, expiry and size (`aim:app/services/fulfillment_service.py:314-322`, `aim:app/services/fulfillment_service.py:352-372`), but its backend storage uses `gatekeeper_url` and omits the file path (`backend:app/services/fulfillment_service.py:216-241`). These named fields are the proposed repair, not existing fields silently assumed present.

**Validation order:** after authenticating the session and validating JWT signature, audience/type and buyer/order binding, lock the durable order and validate **owner → order status → revocation → access window → remaining downloads → stored presign expiry** before any redirect. Retain the linked Transaction closed-status refusal within access-window validation (`backend:app/services/order_service.py:345-381`). Validate purchased version, bucket/key/prefix and credential generation before releasing the URL. Issuance uses the same order, without a JWT input. A new issuance reserves one download atomically; persist its hashed JTI, download number, generation and redemption state in `delivery_config.download_issuances`. Redemption validates the reserved entitlement, including the last permitted download, rather than incorrectly treating that reservation as an exhausted new request. Redeeming the same valid issuance is idempotent and never increments again; invalid/unauthorized probes consume nothing. This preserves the pinned issuance-time counter semantics (`backend:app/services/order_service.py:1195-1215`) while closing concurrent issue/redeem races.

## Amendment G15 (design amendment, S1711): refund-and-release for a paid checkpoint whose proof failed

**Trigger.** Run 12 at `de88c35d` pins / environment `031d67e6` (2026-09-10 18:02Z) produced the first real Trust-Channel delivery: order `b6dec71a` paid (`pi_3UECIjRx8FzPjYyV0CG1K6yZ`, USD 25.00 test mode, captured), delivered by seller-01's device, `transactions.status = delivered`, no Transfer, no payout. The `purchasing` checkpoint is correctly refused by `--abandon-unpaid` (G14.10–12) because money is in flight. Without a sanctioned path the environment is locked for the 48 h hold and beyond, and settling a run whose proof failed would make a non-proof into a Transfer. Approved by Max on 2026-09-11 ("your proposed plan is fine"): refund the test payment and release the checkpoint, never settle it.

**G15.1 — Decision.** Add `python3 bin/check-settlement --abandon-refunded <run_id> <environment_sha40> <order_uuid>` to the environment. It refunds the buyer in full at the provider, lets the product's own `charge.refunded` webhook path (`backend:app/api/v1/endpoints/webhooks.py:1696–1784`, unchanged) mark the **order** refunded and revoke access — note that this path updates `transactions.status` only for `buyer_type = agent` (`:1771–1784`), so for this human purchase the transaction legitimately stays `delivered`; the design does not require, and does not claim, a transaction status change — proves the product state, and only then releases the checkpoint. Option B — hand-editing the database or waiting out the hold and settling — is rejected: the first bypasses every guard, the second pays a seller for an unproven delivery.

**G15.2 — Contract.** Exclusive lock (`locked()`); refuses unless `checkpoint.state == purchasing`, `run`/`source.environment` match the named target, the environment sha is an ancestor of HEAD and the spec pins exist (as G14.10); exactly one order named and it must be the only order in the snapshot; no `settlement-check.json` or `purchase-confirmation.json` receipt.

Two admissible entry states for the named order, read from `delivery_snapshot()` (extended per G15.3): **(A) not yet refunded** — `status in ("paid","delivered")`, `transaction_status in ("paid","delivered","fulfilling")`, `payment_intent_id` present, `transfer_id` null, `settled_at` and `payout_triggered_at` null, `revoked false`; **(B) already refunded by a previous attempt of this command** — `status == refunded`, `revoked true`, a full-refund `order_events` row present, `transfer_id`/`settled_at`/`payout_triggered_at` null. Any other state refuses. State (B) exists so that a timeout after the irreversible provider refund is recoverable; it is the idempotent re-run path and must be first-class, not a side note.

Provider step inside the backend container with the settlement block's asserts (`ENVIRONMENT test`, `STRIPE_TEST_MODE`, `sk_test_`, no RAILWAY/PRODUCTION, `compare_digest` on the key), reading `t.tx_number` and `t.id` for the order in-container exactly as the settlement block does (`bin/check-settlement:1001–1010`): retrieve the PaymentIntent and require `livemode false`, `status succeeded`, `amount_received == 2500`, `currency usd`, `metadata.order_id == <order>` (the human hosted-checkout PaymentIntent carries only `order_id` and `order_number`, `backend:app/api/v1/endpoints/checkout.py:350–355`; `transaction_id` exists only on the agent path, `transaction_service.py:281–285`, so it is never asserted — the transaction is bound by the in-container `t.id`/`t.tx_number` read for the order and the `transfer_group` check instead); retrieve `latest_charge` and require `charge.disputed is false` (no dispute, LOW-3) and `charge.livemode false`; require `stripe.Transfer.list(transfer_group=<tx_number>)` empty.
