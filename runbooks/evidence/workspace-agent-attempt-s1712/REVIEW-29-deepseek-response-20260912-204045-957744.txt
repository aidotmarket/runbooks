### SIMPLER
One concrete simplification preserving every invariant: replace the new closed `expected_binding` value type plus its new keyword on both `mark_paid` and the helper with an extension of the already-validated `checkout_data` dict that the sync caller computes today (packet `:4028` already passes `checkout_data["order_id"]`/`["payment_intent_id"]`). This removes one new public type, two public signature changes, and the associated missing/extra-field rejection code, while keeping the invariant that only validator-produced facts cross the async boundary. It does **not** remove the two unique constraints or the recovery mode (those are required by Q3/Q2). Recorded as advisory; there is no evidence of scope violation.

### BETTER
A materially better approach for the acknowledged cross-table gap (Q3/Q1): make exclusivity database-enforceable across tables by introducing a single claim row — e.g. a `payment_intent_claims` table keyed `UNIQUE(stripe_payment_intent_id)` with FK-like `(order_id, transaction_id)` columns and a CHECK binding the pair — so a PI cannot simultaneously bind an Order in one path and a Transaction in another even if a future writer bypasses the helper. Compare failure modes: the current design fails open only for writers that skip the validated helper (a small, inventoried set today); the claim-table design closes that hole but requires backfilling existing bound rows and a second forward migration, and its rollback is a drop-migration rather than a no-op. Cost: one extra table + backfill vs. two indexes. Recorded as advisory; the residual risk is explicitly bounded and documented, so this is not a scope-violation mandate.
