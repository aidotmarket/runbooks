## 4. Answers to the eight owner questions (re-anchored to the 588-line file)

**Q1 — Atomic dual-PI persist without crossing sync/async sessions with locks held; expected facts revalidated within the owning locked op; exact callers, synthetic path, direct method.**
**Yes, by design.** The design correctly identifies that the browser seam's paid transition runs in an **independent async session** — `webhooks._handle_checkout_completed` reads Order/Transaction without money-row locks, then calls an independent async `OrderService` session (`spec:560`). It therefore mandates: do **not** sync-bind PI or take Order/Transaction locks before that boundary; instead carry an **immutable `expected_binding`** (order_id, transaction_id, stored + signed Session id, signed PI, signed amount/currency, buyer/seller/listing, platform_fee_cents, seller_amount_cents) into the async `mark_paid`, which owns Order→Transaction locks, binds both dedicated PIs, and commits together under existing `auto_commit=True` (`spec:560,:584`). Facts are **re-compared under locks** (`spec:526,:586`), not reconstructed from caller IDs; previously-observed PI may remain NULL or advance only to the **same** signed PI (`spec:586`). The synthetic inline branch (`marked_paid_inline=True`) owns event→Order→Transaction in one sync transaction (`spec:562`); the legacy mock (`auto_commit=False`) has the helper neither commit nor discard caller writes (`spec:562,:588`); `TransactionService.handle_payment`'s `tx_id` is "not PI authority" — it builds direct-mode facts from locked state and refuses both-NULL (`spec:588`). Crash-after-async-commit-before-event-completion is a required test (`spec:560`). Coherent and consistent with the verified source (retained). **Not blocking.**

**Q2 — Original-ID signed capture recovery without reopening dedup, accepting conflicting identity, premature money authority, overwriting non-NULL PI, or reviving refunded/revoked/disputed/settled; PI-first ordering and backup handler's prior money-state creation.**
**Yes, by design.** `signed_capture_recovery` is tightly gated (`spec:533`): already-paid/pending_delivery + matching Order PI + linked Transaction paid/fulfilling with NULL PI + original capture failed **before** finance + no W registration + no Payment/refund/payout/captured authority + no revocation/dispute/reconciliation; requires matching stored Session, fresh provider metadata for both IDs, exact amount/currency/platform, original persisted signed payload; completes Transaction PI then captures in one transaction with **no status/paid_at rewrite**. Non-NULL PI may only advance to the *same* signed PI (`spec:526,:586`). The completed-checkout dedup is not reopened (`spec:537,:564,:566`). The backup `_handle_payment_succeeded` branch is explicitly **forbidden from creating an OrderMoneyState** and must fail retryably on a missing pair (`spec:516,:579`); a pre-existing empty OrderMoneyState forces refusal (`spec:533`) — directly closing the "prior money-state creation" concern. Commit-uncertainty is reconciled by original-ID replay + stored finance, never a second provider purchase (`spec:537`). **Not blocking.**

**Q3 — Two native nullable uniques enforce same-table exclusivity while preserving multiple unpaid NULLs; strict cross-table reverse-pair validation retained; ordering, preflight, collision, rollback, PG17 ancestry, bounds, forward-only.**
**Yes, by design.** Both constraints are nullable with **no `NULLS NOT DISTINCT`** (`spec:505`), so Postgres keeps multiple NULLs for unpaid rows. Cross-table identity is explicitly *not* claimed from uniqueness — "the existing exact reverse-pair and money-field validation remains mandatory" (`spec:501`), and a raw cross-table mismatch "is not prevented by uniqueness alone, and continues to be refused by strict pair validation" (`spec:541`). Preflight inspects non-NULL duplicates and **aborts, never chooses winners**; missing objects created, exact existing = no-op, same-name mismatch aborts; verifies attnums/`contype=u`/validated/nondeferrable/index unique-valid-ready-immediate/actual nullability; ACCESS EXCLUSIVE in Order→Transaction order, `lock_timeout 250ms`, `statement_timeout 2000ms`, 5-second body deadline, rollback of both on failure; PG17 fresh/full ancestry + repeat body + collision/rollback mandatory; retained forward-only downgrade refusal (`spec:505,:507`). The `down_revision` chain is internally consistent (`spec:32,:86,:505`) and was verified head-correct at `backend@817f7331` (retained). **Not blocking** (subject to L1's premise note). Note the amendment's single-column PI uniques compose with — and are strictly tighter than — the retained contract's 5-column `uq_s1712_order_discovery`/`fk_s1712_registered_order_discovery` composite (`spec:338,:443`); no conflict.

**Q4 — Same-PI different-Order races, different-event same-pair races, cancellation, unique-conflict, uncertain-commit bounded/safe; agent branches, provider idempotency/spend, no provider I/O under new money locks.**
**Yes, by design.** Global lock key event→Order→Transaction→money authority→Payment→sorted Refund→agent (`spec:541`, consistent with retained `:40`); the loser of a same-table PI race must roll back and cannot retain a one-sided binding; a raw cross-table mismatch is still refused by pair validation (`spec:541`). SQLSTATE `23505` on the named constraints = retryable binding conflict; `55P03/40P01/57014` + commit-uncertainty explicitly **not** success (`spec:543`); uncertain commit reconciled by original-ID replay + stored finance, never a second provider purchase (`spec:537`). No new lock or provider I/O before agent external creation; uniqueness is checked only when persisting the returned PI (`spec:545`). `create_agent_checkout`'s two branches already set both dedicated PIs with the same returned provider PI in one transaction (retained proof), so uniqueness is automatically satisfied without redesigning agent idempotency/spend (`spec:519`). The design also **harmonizes lock order**: `_repair_canonical_payment` is re-ordered from Transaction-first to Order-first to avoid a new deadlock against Order-first `mark_paid` (`spec:564`) — a real hazard the design anticipates. Capture provider preflight ≤10s/20s occurs outside event/money locks (`spec:545`). **Not blocking.**

**Q7 — Test-lifecycle isolation runs real notification behavior against the case DB, awaits only owned work, disposes every owned pool even after failure; next-template-clone regression; distinguish fixture fault from product PI omission; no monkeypatch/session-killing/suppressed assertions.**
**Yes, by design, honestly hedged.** The diagnosis (`spec:573-575`): `notification_service` imports a module-bound `AsyncSessionLocal` on the initial template DB; the case fixture swaps env but not the factory → notification FK error → subsequent template clones fail — explicitly labeled "a strong inference, not identification of the transient backend PID or a reproduced final fix.
