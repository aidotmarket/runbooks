## 2. Findings (highest severity first)

**No HIGH or MEDIUM findings.**

### L1 — LOW (non-blocking) — The two same-table PI UNIQUE constraints depend on an unstated one-PaymentIntent↔one-Order/Transaction premise
- **Location:** `runbooks@e3b8b088 specs/SELLER-WORKSPACE-ACTIVATION-S1712-GATE2.md:166` ("uq_s1714_order_payment_intent UNIQUE(stripe_payment_intent_id) … uq_s1714_transaction_payment_intent UNIQUE(stripe_payment_intent_id)").
- **Observed:** The design installs single-column UNIQUE constraints on `orders.stripe_payment_intent_id` and `transactions.stripe_payment_intent_id` but never states the invariant they require — that a given Stripe PaymentIntent maps to at most one Order (and one Transaction). If any legitimate flow ever attached one PI to multiple orders, the constraint would be wrong.
- **Expected:** The premise stated, and the migration's duplicate-preflight framed as verifying it.
- **Evidence (static):** I independently corroborated the invariant at `backend@817f7331`: `app/models/finance.py:294` already declares `Payment.stripe_payment_intent_id … unique=True`; `alembic/versions/20260912_001_order_money_protocol.py` shows `order_money_states` keyed `PRIMARY KEY (order_id)` and `s1681_refund_test_authorities` with both `UNIQUE (payment_intent_id)` and `PRIMARY KEY (order_id)`. The money subsystem already treats PI as 1:1 with Order. The agent producer writes the **same** `:pi_id` to both `orders` (`transaction_service.py:379,438`) and `transactions` (`:392,449`) — two *separate* single-column uniques do not collide because the tables differ.
- **Impact:** None on money-safety and none on this design verdict — the design is fail-safe: it mandates a pre-DDL non-NULL duplicate scan that **aborts and never chooses winners** (`spec:168`). Worst case is a migration that refuses to apply, caught before release.
- **Smallest required outcome:** In the next build, have the duplicate-preflight explicitly assert "zero legitimate non-NULL PI duplicates in each table" and record the premise. No design change required.
- **Verification criterion:** Migration preflight output shows the per-table non-NULL duplicate count = 0 on the frozen source before constraint creation.

## 4. Answers to the eight owner questions

**Q1 — Atomic dual-PI persist without crossing sync/async sessions with locks held; expected facts revalidated within the owning locked op; exact callers, synthetic path, direct method.**
**Yes, by design.** The design correctly identifies that the browser seam's paid transition runs in an **independent async session** (`webhooks.py:683`, `OrderService(async_db)`), so it mandates: do **not** bind PI or take Order/Transaction locks in the synchronous caller before that boundary; instead carry an **immutable `expected_binding`** (order_id, transaction_id, stored + signed Session id, signed PI, amount/currency, buyer/seller/listing, platform_fee_cents, seller_amount_cents) into the async `mark_paid`, which owns Order→Transaction locks, binds both dedicated PIs, and commits together under existing `auto_commit=True` (`spec:245-249`). Facts are **re-compared under locks** (`spec:246-247`), not reconstructed from caller IDs. The synthetic inline branch (`marked_paid_inline=True`, `webhooks.py:1411`) owns event→Order→Transaction in one sync transaction; the legacy mock (`checkout.py:246`, `auto_commit=False`) has the helper neither commit nor discard caller writes; `TransactionService.handle_payment` builds direct-mode facts from locked state and refuses both-NULL. This is coherent and matches the verified source. **Not blocking.**

**Q2 — Original-ID signed capture recovery without reopening dedup, accepting conflicting identity, premature money authority, overwriting non-NULL PI, or reviving refunded/revoked/disputed/settled; PI-first ordering and backup handler's prior money-state creation.**
**Yes, by design.** `signed_capture_recovery` is tightly gated (`spec:194`): already-paid/pending_delivery + matching Order PI + linked Transaction paid/fulfilling with NULL PI + original capture failed **before** finance + no W registration + no Payment/refund/payout/captured authority + no revocation/dispute/reconciliation; requires matching stored Session, fresh provider metadata for both IDs, exact amount/currency/platform, original persisted signed payload; completes Transaction PI then captures in one transaction with **no status/paid_at rewrite**. Non-NULL PI may only advance to the *same* signed PI, never a different one (`spec:247`). The completed-checkout dedup is not reopened (`spec:198,227`). The backup `_handle_payment_succeeded` branch is explicitly **forbidden from creating an OrderMoneyState** to enable NULL recovery (`spec:240`), and a pre-existing empty OrderMoneyState forces refusal (`spec:194`) — directly closing the "prior money-state creation" concern. **Not blocking.**

**Q3 — Two native nullable uniques enforce same-table exclusivity while preserving multiple unpaid NULLs; strict cross-table reverse-pair validation retained; ordering, preflight, collision, rollback, PG17 ancestry, bounds, forward-only.**
**Yes, by design.** Both constraints are nullable with **no `NULLS NOT DISTINCT`** (`spec:166`), so Postgres keeps multiple NULLs for unpaid rows. Cross-table identity is explicitly *not* claimed from uniqueness — "the existing exact reverse-pair and money-field validation remains mandatory" (`spec:162,202`). Preflight scans non-NULL duplicates and **aborts, never chooses winners**; missing objects created, exact existing = no-op, same-name mismatch aborts; catalog attnums/contype/validity/nondeferrability verified; ACCESS EXCLUSIVE in Order→Transaction order, `lock_timeout 250ms`, `statement_timeout 2000ms`, 5s body deadline, rollback of both on failure; PG17 fresh/full ancestry + repeat-body + collision/rollback mandatory; forward-only downgrade refusal (`spec:166-168`). Verified anchors: `down_revision` head is correct (`backend@817f7331 20260912_002:7-8`, nothing lists `s1712_workspace_authority_v1` as a down_revision → it is head); no pre-existing UNIQUE on the two columns. Consistent with the prior-approved R5/R4 migration patterns. **Not blocking** (subject to L1's premise note).

**Q4 — Same-PI different-Order races, different-event same-pair races, cancellation, unique-conflict, uncertain-commit bounded/safe; agent branches, provider idempotency/spend, no provider I/O under new money locks.**
**Yes, by design.** Global lock key event→Order→Transaction→money authority→Payment→sorted Refund→agent (`spec:202`); the loser of a same-table PI race must roll back and cannot retain a one-sided binding; a raw cross-table mismatch is still refused by pair validation. SQLSTATE `23505` on the named constraints = retryable binding conflict; `55P03/40P01/57014` + commit-uncertainty explicitly **not** success (`spec:204`); commit-uncertainty reconciled by original-ID replay + stored finance, never a second provider purchase (`spec:198`). No new lock or provider I/O is introduced before agent external creation; uniqueness is checked only when persisting the returned PI (`spec:206`). Agent dual-write verified (`transaction_service.py:379/392,438/449` — same `:pi_id`), so uniqueness is automatically satisfied without redesigning agent idempotency/spend. The design also **harmonizes lock order**: `_repair_canonical_payment` currently opens Transaction-first (`webhooks.py:1272`) and is re-ordered to Order-first (`spec:225`) to avoid a new deadlock against the Order-first `mark_paid` — a real hazard the design anticipates. **Not blocking.**

**Q5 — Full Workspace authority/discovery/registration/closure contract intact (mutable Transaction drift, parent composite FK, publication enforcement, three refund-event statuses, one-sided identity inclusion, final READ COMMITTED observation, immutable terminal representative)?**
**Yes — preserved by construction.** The spec delta is additive only (owner-attested "all prior 477 lines retained unchanged," and the diff shows only two additive hunks with zero deletions). The retained contract is byte-identical to the previously-AWN'd 55690c7a (a4-successor), whose authority/discovery/closure invariants I and the prior panels verified against `backend@e621c760`. The status header affirms "This full successor retains every 55690c7 obligation below" (`spec:134`). Nothing in the amendment touches the authority window, composite discovery FK, publication guard, or closure/terminal logic. **Not blocking.**

The runbooks reiterate "rerun qualification on one frozen source" and "1988/1990… both renamed cases require explicit reconciliation." Appropriately specified as future work. **Not blocking.**

**Q7 — Test-lifecycle isolation runs real notification behavior against the case DB, awaits only owned work, disposes every owned pool even after failure; next-template-clone regression; distinguish fixture fault from product PI omission; no monkeypatch/session-killing/suppressed assertions.**

Preserve that uncertainty." The correction (`spec:238`): bind the notification factory to the per-case DB, keep real notification/post-commit/handlers, track only this fixture's coroutines, await ≤5s, dispose every owned pool in `finally` on success **and** error, on timeout cancel/await only tracked tasks (do **not** enumerate/kill unrelated tasks or disable notifications/money), wrap admin-engine/CREATE DATABASE/yield in one try/finally, drop only the successfully-created clone, and assert a forced-failure-then-next-clone regression with zero retained template sessions. It explicitly separates this fixture fault from the real product PI omission (`spec:240`). Directly answers Q7. **Not blocking.**

**Yes — all open and un-waived.** The status header, amendment, and both runbook continuations state the amendment "is not an accepted contract, implementation instruction… or release approval," that backend `817f7331` is "partial/unqualified," and that "all original environment integration, combined review, protected runtime phases, real scheduled execution, production cutover and enabled AWS S3/Cloudflare R2 release proofs remain open until independently verified." ### SIMPLER
**None found** that preserves every requirement. The amendment explicitly weighs and rejects the one obvious simplification — a single application **advisory lock** instead of two native uniques — on sound grounds (`spec:162`): an advisory lock forces every existing and future writer (legacy + agent + raw SQL) to share one hashing/key convention before money locks; a missed writer silently evades the guarantee, and inserting it beneath existing locks risks lock-order inversion. Native uniqueness arbitrates all DB clients without a new lock tier and preserves multiple unpaid NULLs. I tried to remove (a) the second (Transaction) unique — but the demonstrated defect is precisely a one-sided Transaction NULL, so both are load-bearing; (b) the `expected_binding` value — but without it the async session would have to reconstruct trusted event facts from caller IDs across the boundary, the exact anti-pattern the design forbids; (c) the fixture-isolation section — but it addresses a distinct, source-evidenced failure (the 44 setup errors) orthogonal to the PI omission. Each removal reopens a specific requirement. Advisory only.

### BETTER
**None materially better.** The alternatives are worse on failure-mode or cost: a **cross-table PI foreign key / CHECK** would try to enforce Order↔Transaction PI equality declaratively, but the design correctly declines it ("No cross-table PI FK is claimed," `spec:166`) because PI can be legitimately NULL on one side mid-flow and the real invariant is the existing reverse-pair validation, not column equality — an FK here would either block legal intermediate states or require deferral gymnastics. A **backfill/UPDATE migration** to repair the stuck MP248 row would be faster than replay-based recovery but violates the money-safety rule against operator backfill and loses the signed-provenance guarantee; the chosen original-ID replay through `signed_capture_recovery` preserves authenticated facts with clean rollback. `CREATE UNIQUE INDEX CONCURRENTLY` would reduce cutover lock time but forfeits transactional rollback of the paired additions; the design's transactional maintenance-window change is the safer, now-explicitly-named tradeoff. Rollback for the whole amendment is a separately-reviewed forward-only down migration — appropriate for money-table DDL.
