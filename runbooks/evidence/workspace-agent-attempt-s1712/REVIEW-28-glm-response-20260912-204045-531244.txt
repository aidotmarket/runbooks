## 4. Answers to the eight numbered questions

1. **Yes, as a design.** The final design moves PI binding into the lock-owning operation. Normal `_handle_checkout_completed` passes a closed `expected_binding` into independent async `OrderService.mark_paid`; that session owns Order→Transaction locks and commits binding plus paid transition together. The synthetic branch uses its existing synchronous owner. `TransactionService.handle_payment` must derive authority from persisted locked Order state, never from `tx_id` alone. Expected Session, transaction, actor/listing, amount, fee, currency, and PI facts are revalidated after locking. Evidence: specification lines 513-520, 556-567, and 582-588; embedded base source confirms the current unlocked validation/async-session boundary and current `mark_paid` lock order.

2. **Yes, as a design.** Recovery is PI-first: resolve an existing Order by stored PI, read authoritative PI/Charge outside money locks, then lock event→Order→Transaction and run the narrow recovery before strict capture processing. It does not reopen completed-checkout dedup; refuses conflicting PI, asymmetric history, retained registration, Payment/refund/payout/authority, revocation, dispute, reconciliation, or settled/refunded states; preserves status and paid history; and binds Transaction PI plus capture atomically. The normal backup path is explicitly forbidden from creating `OrderMoneyState` to make recovery possible. Evidence: specification lines 513-520, 523-535, 539-545, and 573-580.

3. **Yes, as a design.** Two nullable, nondeferrable native unique constraints enforce per-table non-NULL PI exclusivity for every database writer while allowing multiple unpaid NULLs. Duplicate preflight aborts rather than choosing a winner; named-object collision and repeat behavior are fail-closed; DDL is bounded, ordered, transactional, and rollback-safe; PG17 full/repeat ancestry, catalog facts, bounds, collision, rollback, and forward-only refusal are mandatory. Strict reverse-pair validation remains responsible for cross-table coherence. Evidence: specification lines 503-510 and 539-545.

4. **Yes, as a design.** Same-PI different-Order and different-Transaction writers are arbitrated by the native constraints; the loser rolls back and cannot retain a one-sided binding. Same-pair different-event work serializes on Order→Transaction after each event lock. Agent provider creation receives no new binding/event/money lock beforehand; uniqueness applies when the returned PI is persisted. Cancellation, duplicate collision, timeout, deadlock, unique conflict, and uncertain commit are explicitly refusal/reconciliation states, not success. Provider reads remain outside event/money locks. None found.

Alternatives I attempted to remove:

- Replacing the migration and two native constraints with a shared helper/advisory lock would remove one migration and the ACCESS EXCLUSIVE cutover step, but it fails unknown/raw/future database writers and adds a new lock tier.
- A recovery-only Transaction PI backfill would remove several normal producer changes, but leaves every future public checkout exposed to the same defect.
- Fixing only the notification test would remove the 44 setup errors’ immediate symptom, but does not address the real product PI omission.

### BETTER

None found.

A cross-table PI FK or exclusion-style constraint was considered as a “stronger” alternative. It is materially worse here: unpaid rows require NULLs in both tables, a cross-table constraint would broaden schema coupling and locking, and it still would not remove the need for exact producer/recovery semantics and strict money validation. The selected pair of per-table native uniqueness plus strict locked reverse-pair validation has smaller scope, database-wide collision enforcement, and a straightforward rollback/reconciliation path.
