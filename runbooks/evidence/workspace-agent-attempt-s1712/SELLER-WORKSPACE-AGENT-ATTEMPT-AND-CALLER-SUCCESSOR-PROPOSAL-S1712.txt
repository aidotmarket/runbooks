# Agent payment-attempt safety and complete caller compatibility — successor proposal

Proposed for joint owner disposition and fresh full review. This is a semantic amendment to frozen e3b8b088, not an accepted low-nit implementation interpretation. It responds to Mars4704 and independently verified caller/source evidence4705–4706. Do not mutate the still-reviewed candidate, dispatch MP, add exceptions or claim implementation from this proposal.

## Why the existing instruction cannot finish the work

At817f TransactionService.create_agent_checkout creates a new uncommitted Order before confirmed provider creation; its requires_action branch cancels the returned PI before native uniqueness can reject a reused identity. A rollback loses that Order but cannot undo provider spend. A later call can generate a different Order with the same provider idempotency key. The generic failure helper unconditionally decrements reserved spend. app/services/mcp_tools.py commits the initial transaction and spend reservation before checkout, so that reservation survives the failed checkout transaction. There is no identified existing collision reconciliation or once-only release operation. A draft saying preserve lifecycle and use existing reconciliation therefore leaves a known implementation hole.

The minimal selected successor uses an internal durable attempt inside the existing transactions.metadata JSONB and persists the original Order/request before the one provider creation. This deliberately supersedes the amendment's preserve-agent-external-call-lifecycle sentence; it does not introduce a claim table, new schema column, advisory lock, new endpoint or new provider purchase. All current actor/terms/published-listing/payout checks and exact money/ownership validation remain. This is a meaningful design change requiring full review, not a mere file-membership permission.

## Durable identity and state

Reserve the internal metadata key canonical_agent_attempt_v1. Preserve every unrelated metadata key. The value is a closed versioned record with: version=1; immutable attempt_id UUID; transaction_id, original_order_id, api_key_id, org/actor/listing identity; original provider idempotency key api_key_id:transaction_id; exact amount/currency/fee/seller amount; original customer/payment-method identifiers and provider account/test context; original provider request metadata; state; bounded observed provider PI/status and evidence timestamps when available; spend_release_state=held|released; and a once-only release evidence identity. Never store credentials, signed secrets, card data or complete provider payloads. Store identifiers needed for exact request equality in the same access-controlled internal data as the existing transaction; redact them from public response/logs. All identity/request fields become immutable once prepared. Record shape/version errors refuse instead of discarding or replacing the attempt.

States: prepared_unknown, response_observed, bound_pending, cancellation_unknown, cancelled_reconciled, conflict_reconciliation. These are internal attempt states, not new public TransactionStatus values. An unknown/unresolved attempt keeps the Transaction initiated and its committed spend held; it must not become paid, agent_payment_pending or agent_payment_failed merely because a provider call raised. A proven normal bound checkout moves to existing agent_payment_pending; a proven owned cancelled/no-charge attempt can move to existing agent_payment_failed exactly once with the spend release transaction. An attempt never resets to absent/prepared with a new Order or key.

The prepare commit precedes all provider creation; prepared_unknown means the call may or may not have happened. This conservative ambiguity is intentional. No timeout, lease expiry, process restart or absence of a PI in local rows makes replaying creation safe. The original caller gets a one-shot in-memory dispatch entitlement only after that commit is known successful. An uncertain prepare commit means no provider call by that caller; subsequent requests reconcile/refuse the retained attempt. No external write is retried automatically by reconstructing a new request.

## Prepare transaction and lock order

First discover the Transaction/possible existing Order and attempt without using that observation as final authority. If an attempt or linked Order exists, follow the existing-identity branch below; do not create another Order. For a genuinely unlinked candidate, create the candidate Order with the existing OrderService and auto_commit=False, then acquire/revalidate the exact Transaction before claiming it. The candidate Order is this transaction's newly inserted row; this does not acquire an existing Order underneath a Transaction lock. Recheck initiated status, original API key/organization/actor/listing/money tuple, empty attempt, NULL Tx.order_id and exact reverse cardinality. A concurrently committed different claim refuses and rolls back this candidate Order, creation event and queued notification. Foreign-key KEY SHARE interactions or competing claim deadlocks are bounded refusals, not provider work; retain a forced concurrent-prepare proof.

Link Transaction.order_id to that candidate, store the immutable attempt with held spend, and commit the Order+link+attempt together before the provider call. No key/spend mutation is needed in preparation because initiate_purchase already committed the reservation. Preserve original normal Order creation notification behavior: only the winning committed Order may schedule a notification. Do not acquire a second/different existing Order after the Transaction; rollback and rediscover if the observed relationship changed. Each DB phase uses250ms lock wait/2s statement/decreasing5s body bounds. Provider I/O holds none of these Order/Transaction/money/key locks.

For an existing identity, lock the observed Order first then exact Transaction, validate the reverse pair and immutable attempt. If the observed Order changed, rollback and refuse/retry discovery outside locks; never chase it under the Transaction. A legacy linked agent pair without this attempt cannot be adopted by fabricating request facts. Preserve existing fully coherent completed/cached behavior where independently proven; otherwise require explicit separate reconciliation rather than new provider creation.

## Provider response, binding and cancellation

The original winning caller uses the persisted request byte-equivalent facts and unchanged api_key_id:tx_id key for the single existing PaymentIntent.create call. The response is not authority by PI ID alone: validate immutable transaction/order/key/agent metadata, amount/currency, customer and account/test context against the durable request. A response may be observed even when identity is contradictory; store only bounded diagnostic facts and mark conflict_reconciliation, never assign its PI as authority or cancel/refund it.

For a matching response, start a fresh bounded Order→Transaction transaction, revalidate the exact durable attempt and all row facts, and atomically write both PI columns with the native constraints. A non-NULL value can only equal the returned PI; no overwrite. Record response identity and the appropriate attempt state in the same transaction. Any native collision rolls back both PI writes and is followed by a separate bounded attempt-state update to conflict_reconciliation, leaving the original Order+attempt and held reservation durable. If the diagnostic update fails, prepared_unknown remains a safe refusal; do not report successful persistence of the diagnostic. No success, fulfillment, cancellation, refund or spend release follows a conflicting/missing/uncertain binding commit.

For the normal accepted provider status, only a known-successful coherent binding commit can set/return bound_pending plus existing agent_payment_pending. Preserve the existing provider-status admission rules; explicitly test all observed statuses rather than assuming every non-requires_action response succeeded. Cached responses are permitted only after attempt/state/pair validation, not by the old early pi-id check alone.

For requires_action, persist the matching pair and cancellation_unknown before invoking the existing cancellation, without marking successful purchase or releasing spend. Commit known-successful first, release locks, and call cancellation only for that validated original PI. If either commit or cancellation outcome is unknown, retain cancellation_unknown and held spend. Native uniqueness must therefore arbitrate BEFORE cancellation; a returned foreign/reused PI is never cancelled as a loser-cleanup action. There is no cancellation retry from an uncertain state; read-only reconciliation determines what happened. This ordering is part of the new reviewed lifecycle.

## Original-identity reconciliation and once-only spend release

Implement a bounded internal TransactionService reconciliation method for the existing attempt, callable by subsequent checkout requests before cached/status shortcuts. It performs no provider create/cancel/refund/confirm and does not create a new Order. For a known observed PI, read only the authoritative provider object outside DB locks and compare exact request/ownership/context. With no trustworthy PI or contradictory identity, return a durable reconciliation-required refusal and held spend; neither metadata search absence nor elapsed time proves no charge. The support runbook names this exact state and evidence needed, without pretending a provider-unknown state can always be automatically resolved.

After the read, lock Order→Transaction→existing money authority→Payment→sorted Refund→agent key as applicable, recompare attempt and provider/local facts, and classify:

- Existing identical committed bound pair: idempotent result only after strict original binding/history checks. Never issue another purchase or paid event.
- Original owned provider PI definitively cancelled with no captured/received amount or other retained liability, and no local Payment/capture/refund/payout/settlement/revocation/dispute/reconciliation authority: eligible for once-only reserved-spend release.
- Captured, processing, requires-action-but-not-cancelled, contradictory, foreign, missing, stale or unverified provider state; any unresolved finance/commit: preserve held reservation and refuse. A collision with a foreign winning PI does not prove this original attempt has no liability.

Release is one atomic database transition, not the generic _mark_agent_checkout_failed helper: under the exact Transaction and agent-key locks require spend_release_state=held, original key/organization ownership and sufficient aggregate reserved spend (at least this exact amount). Decrement exactly this original amount without GREATEST masking underflow; set spend_release_state=released with exact evidence identity, attempt=cancelled_reconciled and existing failed/cancelled public states in the same transaction. Log the existing transaction/audit event once in that transaction. If already released with matching immutable evidence, return the retained outcome without another decrement; conflicting evidence refuses. A cancelled local Order update that fires existing status triggers must occur before downstream money/key locks: acquire/order and perform compatible Order changes in the accepted order or stage the full transaction so no trigger acquires an upstream lock beneath the key. Prove the actual trigger path; do not infer it from application SQL order.

Known-safe ordinary failures before any provider dispatch may continue their separately verified prior behavior. After the durable attempt is prepared, generic exception handling must never route to the unconditional spend-release helper. Retry checkout checks the durable attempt before its old cached-PI/initiated shortcuts and cannot fall back into Order creation. Retain failed/unknown attempts indefinitely for reconciliation. No cleanup/expiry path may discard attempt history or release its reservation on age alone; the existing stale cleanup must explicitly refuse unresolved attempt states if they can enter its selection. A complete implementation must enumerate those callers and prove this guard, using accepted targets or a precisely reviewed scope addition if necessary.
