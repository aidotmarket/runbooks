## 4. ANSWERS TO THE 12 OWNER QUESTIONS

**Q1 — Atomic dual-PI persistence without crossing sync/async sessions under locks; facts revalidated in the owning locked op.** Satisfied in design. The non-creating, non-committing `bind_initial_order_payment_intent_sync(…, mode)` (`:562`) is called by a caller owning one bounded transaction; the 12-field `expected_binding` (D6, `:658–676`) is constructed once from validated signed facts and **re-validated field-by-field against locked rows by the lock owner**. Both PI columns are written atomically with native constraints (`:156`, `:847`). Provider I/O holds no Order/Transaction/money locks (`:148`). No cross-session-under-lock pattern is authorized. Callers/synthetic path/direct method are all addressed (D4, `:596`, D6 pi_e2e_mock allowance).

**Q2 — Original-ID signed capture recovers completed-checkout/failed-capture history without unsafe effects.** Satisfied. `signed_capture_recovery` (`:571`) requires matching stored Session, fresh provider metadata for both IDs, exact money/scope, and refuses if any empty `OrderMoneyState` pre-exists. PI-first ordering and the **backup handler's prior money-state creation** are explicitly governed: the backup `_handle_payment_succeeded` branch "must not create an OrderMoneyState to make NULL binding recovery possible" and its `lock_order_money_sync` is permitted only on an already-coherent binding (`:617`) — consistent with the verified creating behavior of that helper (817f `order_money_service.py:149-153`). Non-NULL PI is never overwritten (`:805`); refunded/revoked/disputed/settled history is preserved (`:821`, `:827`).

**Q3 — Two native nullable uniques enforce same-table exclusivity for every writer, preserve multiple unpaid NULLs, retain cross-table reverse-pair validation.** Satisfied in design. D5 (`:635`) binds both migration bodies to 250ms/2000ms/5s, Order→Transaction lock order, and an explicit money-readiness projection **extension** (`uq_s1714_order_payment_intent`, `uq_s1714_transaction_payment_intent`) with "normal NULL-distinct semantics" — preserving multiple unpaid NULLs. D2 (`:628`) mandates a read-only duplicate census before each constraint application and a transactional migration that independently rejects duplicates; **any duplicate stops without choosing a winner** and routes to a separately-reviewed reconciliation. Reverse-pair cardinality is retained (`:562`). PG17 ancestry is a stated proof obligation (D8 `:117`); I verified `001→002` is linear at 817f and `003` is the proposed child (not yet built) — consistent with the design, not a contradiction.

**Q4 — Races, cancellation, unique-conflict and uncertain-commit bounded and safe; no provider I/O under new money locks.** Satisfied — this is the strongest part of the design. Native uniqueness **arbitrates before cancellation**; a returned foreign/reused PI is never cancelled as loser-cleanup (`:160`, `:865`). Uncertain commit ⇒ `prepared_unknown`/`cancellation_unknown`, held spend, **no replay** (`:142`, `:160`). Same-PI-different-Order and different-event-same-pair are refusals with no partial binding. Provider I/O is explicitly outside all Order/Transaction/money/key locks (`:148`, `:164`, `:825`). Original provider idempotency key is unchanged and reused (`:154`; 817f `:354`).

**Q5 — Full Workspace authority/discovery/registration/closure contract intact.** Intact — the retained contract is byte-identical to e3b8b088 (mutable Transaction drift + composite FK `:376`; publication enforcement `:138`; READ COMMITTED closure `:416`; immutable terminal representative retained). ## SIMPLER

**None found that preserves every invariant.** The apparent simplification — reuse the existing rollback-only reconciliation and the unconditional spend decrement instead of a durable attempt record — is exactly what the design proves cannot be safe: at 817f the requires_action branch cancels the returned PI **before** native uniqueness can arbitrate (`transaction_service.py:373-374`), the failure helper decrements unconditionally (`:1176`), the reservation is pre-committed by `mcp_tools` (`:665,673`), and the webhook decrements with a bare `GREATEST` and no marker (`webhooks.py:1532`). Removing the durable attempt reintroduces the double-spend/foreign-PI-cancel hole. The one genuinely removable element I tried — storing the attempt in a new table/column — is already removed: the design deliberately reuses the existing `transactions.metadata` JSONB (verified `transaction.py:184`) and adds no table, column, endpoint, advisory lock, or new provider call. What remains (12-field `expected_binding`, 7-state machine, 8-row status table, 14-key provider-evidence input) is essentialy irreducible given the crash/uncertainty and money-exclusivity requirements; the `completed`-keeps-`held` invariant already collapses the capture/release accounting to a single decrement point.

## BETTER

**None materially better for a payments-integrity design.** The candidate architecture already reflects the best-practice payment idempotency pattern: persist intent before the external side-effect, treat provider I/O as outside-transaction, arbitrate uniqueness before any cancel, and bias every uncertainty toward *hold-and-refuse* rather than auto-release. The one alternative worth naming is a **provider-webhook-first / reconciler-driven** model (never call `PaymentIntent.create` inline; enqueue and let a single reconciler own all binding). Its failure modes are worse here: it widens the window where the caller has no synchronous result, and it still needs the same durable-attempt record and once-only release marker — so it adds latency and a queue without removing any invariant, and rollback would require re-plumbing the synchronous agent checkout contract. The chosen design's rollback story is cleaner (it is design-only; nothing is applied until the frozen implementation passes fresh full review, migration census, and all release gates). The only concrete improvement is the LOW‑1 enumeration completeness, already captured as a finding.
