### SIMPLER

**Keep `OrderService.mark_paid`’s public signature unchanged and carry the validated binding on the owning session instead of as a new kwarg.** The design already contains a non-creating, non-committing initial-binding helper; let the sync validator and the webhook attach the closed 12-field value to the async session’s `.info` (or an equivalent request-scoped immutable object) that the lock owner already possesses, and have the helper read it under the Order→Transaction locks. This preserves every stated invariant — facts are constructed once at the validated boundary and never reconstructed from caller IDs, and are re-compared under locks — while removing the need to touch `order_id`/`stripe_payment_intent_id` callers. Quantified removal: 1 public method signature change, the `tests/integration/test_webhook_canonical_payment.py:153` double rewrite, the `tests/test_notification_events.py` / `tests/test_s1097_order_fulfillment_scoping.py` fixture adjustments, and the two frozen `test_webhook_audit.py:287/661` expectations — i.e. ~4 test-file edits and the entire “zero-unmigrated-caller” migration surface for this method collapse to 1 helper input already inside the 27-target scope. Tradeoff to accept explicitly: implicit per-session data flow is less auditable than an explicit argument, which is the reason the design chose the kwarg. Recorded as **advisory** (no evidence of scope violation or material risk).

### BETTER

**Make the durable agent attempt a first-class immutable row rather than a key inside `transactions.metadata` JSONB.** A small `agent_payment_attempts` table (unique on the provider idempotency key, `NOT NULL` immutable identity columns, a `CHECK`/trigger on the closed state set, and a unique release marker) would make the invariants the contract currently enforces only in application code — immutability of identity/request fields, one attempt per original identity, one-shot release — enforced by the database, and would turn the support/reconciliation path into a typed query rather than a JSON parse. Failure modes versus the current design: it adds DDL under the same 5 s whole-body deadline and quiescence rules (new migration, forward-only, harder rollback), and it is a larger design surface than the “no claim table, no new schema column” choice the owner made after Mars4675 — so it trades migration risk for DB-enforced correctness. Rollback: author-only forward migration plus a write-through JSONB projection (never a destructive downgrade). Cost: one more target in the 27 and one more reviewed migration. Recorded as **advisory**; the current JSONB design is defensible because no existing writer was found that replaces `transactions.metadata` wholesale (only `jsonb_set` partial writes), so the “retain attempts indefinitely” invariant is not silently destroyed by current code.
