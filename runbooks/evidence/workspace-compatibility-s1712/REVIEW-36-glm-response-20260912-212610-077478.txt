## Answers to all 12 active owner questions

   The async `OrderService.mark_paid` owner establishes Order→Transaction locks and commits both PI columns plus the paid transition in one transaction (`specs:598-604,620-626`). `expected_binding` is closed, immutable, and revalidated under locks (`specs:655-676`). 2. **Original-ID failed-capture recovery — Yes, as a design.**  
   Recovery is restricted to the original failed `payment_intent.succeeded` ID, matching stored PI/Session, authoritative provider facts, exact ownership, and absence of authority/history conflicts (`specs:549-575`). Completed checkout dedup is not reopened. The backup handler may not create `OrderMoneyState` merely to make recovery possible (`specs:617`).

   Two nullable, nondeferrable, per-table unique constraints enforce non-NULL PI exclusivity while retaining multiple NULLs (`specs:541-547`). Strict reverse-pair and money validation remains mandatory; no cross-table FK is claimed.

## SIMPLER

**None found** that preserves every requirement.

Alternatives I attempted to remove:

- Replacing the two native PI constraints with an application advisory lock would remove one migration, both indexes, and the cutover DDL step, but it fails unknown raw/future/legacy writers and adds a new lock tier beneath established money locks.
- A recovery-only Transaction PI backfill would remove normal producer changes but leaves every future public checkout exposed to the demonstrated one-sided binding defect.
- Omitting the notification isolation matrix would remove fixture-only work but would mask a real lifecycle failure without fixing the product PI omission.
- Replacing the durable agent protocol with the existing rollback-only branch would remove schema/state work but cannot bound provider spend after uncertain creation or rollback.
- Removing the mandatory crash/race/provider-status tests would reduce qualification cost but would remove the core once-only and no-second-purchase invariants.

## BETTER

**Advisory only:** a first-class `agent_payment_attempts` table keyed by immutable `attempt_id` and unique `transaction_id`, with explicit revision/state/spend-release columns and immutable request columns, would be materially stronger than JSONB metadata for long-term durability.

- **Failure-mode comparison:** It would make whole-object `transactions.metadata` replacement unable to erase the attempt authority and would give the database a direct uniqueness/ownership anchor. The selected JSONB design avoids that risk only through service discipline and the metadata-writer inventory proposed in NIT 1.
- **Cost:** One additional migration/table and service query/join; the current 28-field record still must be validated. It would also expand the stated 27-target implementation scope.
- **Rollback:** Like the selected forward-only design, removal would require a separately reviewed migration; a table is harder to retire than metadata but easier to audit.
- **Disposition:** Advisory. The current design can preserve every invariant by adding the explicit metadata-writer gate; no demonstrated current failure mandates the schema expansion.
