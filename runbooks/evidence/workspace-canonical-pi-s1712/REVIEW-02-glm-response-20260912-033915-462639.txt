## Answers to the numbered questions

### Q1 — Are packaged identity binding and TEST-only provider/refund admission sufficiently strict without weakening public guards?

**Yes, at design scope.**

The contract binds identity to the packaged account-pool entries, exact role/secret-name pairs, database IDs, synthetic classification, and reserved fixture email, while explicitly rejecting request IDs, runtime registration, provider metadata, or email patterns as authority. The verified account-pool model already prevents values in secret-name fields.

The provider contract is also appropriately mode-aware: test-key form plus authenticated retrieval and exact ownership marker establish the Account’s test provenance; event, charge, PaymentIntent, and refund objects must still explicitly report `livemode=false` where their schemas do so. Requiring an invented Account `livemode` field would be wrong; the official Account schema omits it.

Gate2 must still make the following executable:

- one-to-one persisted joins across user/party/order/transaction/PaymentIntent/charge/Payment/refund;
- exact seller02/buyer01 ownership and both synthetic flags;
- no agent key, device authority, connected-account context, or fallback IDs;
- one exact full refund with positive integer amount/currency agreement;
- explicit event/object mode and production-marker refusal;
- no broad synthetic-suppression bypass;
- public synthetic Connect and 2FA guards byte-for-byte in intent and behavior.

Blocking criterion: any live, foreign, duplicate, or ambiguous actor/event/provider identity that can be admitted, or any weakening of a public guard, rejects Gate2.

### Q2 — Does the shared-lock/inner-guard protocol preserve run25 and fail closed on every error?

**Yes, if implemented exactly as specified.**

The existing wrapper validates the command parent, lock token, owner ancestry, and held lock. Because `workspace-fixture` is outside its guarded-name set, entering through `S1681_LOCK_ENTERED` alone would indeed be insufficient. Requiring an unchanged inner `check-settlement --guard seed` and treating every nonzero result—both exit 1 and exit 2—as pre-mutation refusal closes that gap.

The run25 receipt independently shows the current checkpoint would make the guard return exit 2. Read-only status must not create a token, write audit state, or claim a mutation-safe snapshot.

Gate2 tests must prove:

1. lock acquisition;
2. successful inner guard;
3. only then first audit/provider/database/secret write;
4. exit 1 and exit 2 both produce zero mutations;
5. crash between lock and successful guard leaves no audit phase or mutation;
6. malformed audit, foreign lock, missing owner, wrong ancestor/token, and timeout all fail closed;
7. normal seed/reset refuse active or inconsistent Workspace audit before S3 cleanup or container destruction;
8. pure status creates no token or audit write.

Blocking criterion: any pre-guard write or any nonzero guard path that continues rejects Gate2/Gate3.

### Q3 — Are before-state custody, idempotent creation, recovery, and deactivation sufficient?

**Yes as a Gate1 contract; Gate2 must freeze the exact serialization and discriminators.**

The design now requires a private, atomic, versioned audit; fixed identities and pins; operation identity before provider creation; stable provider idempotency; exact owned-resource reconciliation; retained restorable seller02 before-state; protected-state comparison; refusal on corrupt/incomplete audit; and non-destructive cleanup unless every new Workspace order is proven terminal and unable to settle.

The revised enumerated seller02 restoration fields and the requirement that the audit retain only a ciphertext digest/version discriminator, never plaintext TOTP, materially improve the prior draft. Reconciliation by unique ownership marker after idempotency-key retention expires is also the correct durable mechanism.

Gate2 must still define and test:

- exact audit JSON schema/version and phase transitions;
- exact provider marker, idempotency key/payload, and account enumeration query;
- exact TOTP secret UUID/version and DB ownership discriminator;
- snapshot serialization and timestamp handling;
- interrupted create/retrieve/delete behavior;
- duplicate or contradictory marked-account refusal;
- exact `stripe_connect` row equality before deletion;
- partial recovery resuming only the same validated operation;
- refusal, not repair, of incomplete preexisting marked accounts;
- deactivation refusal on uncertain provider outcome, unresolved refund, or changed identity/ciphertext;
- protected seller01/buyer01/device/trust/serial before/after equality.

Blocking criterion: any path that loses restorable state, reassigns a foreign provider identity, retries an uncertain provider operation as a fresh create, or deletes/duplicates an unowned resource rejects Gate2/Gate3.

### Q5 — Is there a simpler or better design preserving signed refund proof, protected state, and the production objective?

See the SIMPLER and BETTER assessments below. No simpler design removes normal signed proof, protected-state custody, provider reconciliation, or the production objective without violating an invariant.

## SIMPLER

**Advisory simplification:** collapse `seed/workspace-host.py` into a module used exclusively by `bin/workspace-fixture`, while retaining the fixed backend-container mode and private `docker exec -i` stdin boundary.

- **Removes:** one new environment allowlist file and one host-to-host process hop.
- **Preserves:** lock/guard ordering, test-key/provider validation, private custody, bounded stdin schema, backend encryption, canary testing, audit/recovery, and deactivation proofs.
- **Why advisory only:** the separate host helper also gives useful custody/container orchestration separation and is already explicitly specified. There is no evidence of a scope violation or material risk requiring this change.

Structural alternatives I tried to remove and rejected:

- Reusing `seed/host-seed.py` would pull in S3, serial, and device state.
- Folding activation into normal `bin/seed` would violate default-seed baseline behavior.
- Replacing restorable before-state with hashes alone would make recovery impossible.
- Using Compose environment injection would move the TOTP value toward container configuration despite the safer stdin design.
- Avoiding the `webhooks.py` seam entirely would forfeit normal signed refund proof.

## BETTER

**Materially better approach:** have Mars’s accepted Gate2 product candidate expose one narrow, versioned processor/schema readiness and admission seam, defaulting to suppression, with the Workspace predicate integrated behind that seam rather than as an independently rebased Vulcan patch.

- **Failure-mode comparison:**
  - Current serialized rebase is safe if ordering is followed, but still depends on two owners coordinating an exact patch position in a money-path file.
  - A single narrow seam makes default suppression structural, makes the Workspace predicate independently testable, and prevents activation on an unversioned or wrong processor.
- **Cost:** one additional Gate2 interface contract and focused default-suppression/readiness tests. It may delay the Vulcan patch until Mars’s exact candidate is available.
- **Rollback:** remove the Workspace predicate or return the default suppression decision; the independently accepted product candidate remains intact.
- **Limit:** this must remain a narrow seam, not the generic admission-hook framework the candidate explicitly declines unless Mars’s accepted interface already provides it.
