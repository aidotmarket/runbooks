## Answers to the six required questions

### 1. Can an old same-pair W order, another window/order, P/N, or altered canonical purchase binding gain signed TEST refund admission?

**No, not under the revised design.**

The two-stage design closes the predecessor’s purchase-scope gap:

- Stage A durably records the complete fixed seller02/buyer01 order-ID baseline before activation/purchase under `LOCK TABLE orders IN SHARE MODE NOWAIT`.
- Stage B recomputes the complete fixed-pair set, requires every baseline ID to remain present, and requires the entire delta to be exactly one order. It accepts no caller order ID or host snapshot.
- The selected order is validated against the actual source chain: order → purchased version → publication → approval → DeliveryAuthority → seller-owned CloudConnection, with source-backed `review_hash`, `manifest_hash`, and `immutable_scope_hash` fields.
- The registration table uniquely binds window, order, transaction, Payment, PaymentIntent, charge, actors, publication/version/authority/connection, amount, currency, protocol, pins, and canonical receipt.
- Its immutable trigger rejects UPDATE/DELETE.
- The webhook exception is at the actual signature/dedup/suppression seam: `aidotmarket/ai-market-backend@c3a62af8:app/api/v1/endpoints/webhooks.py:476-576`.
- P/N uses different persisted authorities and actor/provider identities; Mars’s accepted product spec explicitly requires separate exact persisted authorities.
- A closed/recovery window retains only the originally registered provider identities; it cannot bind a second order.
- Changed source bindings or receipt hashes fail comparison against the immutable registration.

This is a design conclusion only. The required real ASGI and PostgreSQL tests must prove old order, wrong window, P/N crossover, altered binding, revoked connection, post-close replay, and same-ID convergence.

### 2. Can concurrent purchase, duplicate binder, or surgical reset defeat baseline, cardinality, or history preservation?

**Concurrency design: no. Reset design: not fully, as shown by Finding 1.**

For public writers and duplicate binders:

- PostgreSQL `SHARE` conflicts with the `ROW EXCLUSIVE` lock taken by order INSERT/UPDATE/DELETE. `NOWAIT` causes an active writer to refuse immediately; after SHARE is acquired, a later writer cannot change order cardinality before commit.
- A preexisting `SELECT FOR UPDATE` holds compatible `ROW SHARE`; the design correctly handles that case with later `NOWAIT` row locks.
- The complete delta cannot silently exclude an unpaid extra order.
- Duplicate binders serialize on the window row with `FOR UPDATE NOWAIT` and database uniqueness.
- The accepted transaction→money-state→Payment→Refund row order is preserved, orders are never updated during binding, and no table-lock upgrade is allowed.
- Bounded timeouts, rollback, complete retry, and exact immutable reconciliation cover deadlock, timeout, and uncertain commit.
- The required two-session PostgreSQL tests explicitly cover writer-active, writer-arriving, preexisting row lock, duplicate binder, timeout/deadlock, and extra-order cases.

For reset, seller02/buyer01 W orders are protected by the advisory lock, window-row inspection, strict SQL path, RESTRICT FKs, and default seed/reset/up refusal. However, the design expressly leaves seller01/buyer02 surgical resets unchanged even though those targets can destroy protected P/N history. That is Finding 1 and is blocking.

### 3. Can credential/provider activation or recovery overwrite another generation, reassign a Party, or duplicate a resource?

**No, as revised, within the honestly stated private-operator boundary.**

The design removes the predecessor’s unsafe destructive race:

- It performs no provider DELETE, PATCH, or upsert, including recovery.
- First creation requires authenticated 404 and a durably recorded generation before POST.
- Conflict, timeout, 403, or empty parse never means absence.
- Uncertain create is reconciled against exact scope/name/marker/digest/UUID/version.
- A changed, deleted/recreated, or unverifiable retained generation refuses; it does not re-enroll.
- Reuse requires exact retained UUID/version/digest/marker/scope/name and no unresolved operation.
- An external write after the last GET cannot be erased because no destructive operation follows.
- Connect account creation uses complete pagination, marker uniqueness, durable idempotency identity, and no fresh account after expiry/uncertainty.
- Foreign Party ownership is proved before projection; the known dangerous reassigning upsert is forbidden.
- Provider accounts and custody remain retained; deactivation explicitly means `inactive_with_retained_custody` or `deactivation_incomplete`, not secret absence.

Actual source confirms the hazardous cases the design guards: User Stripe readiness fields are strings, `TOTPService` encryption is unchanged, and the existing Connect upsert can reassign ownership. Finding 2 notes that digest/marker derivations still need exact golden definitions.

### 4. Can an unauthenticated caller, wrapper bypass, substituted host artifact, wrong image/pin, or secret transport gain authority or leak secrets?

**No public/wrapper bypass is visible in the design; the trusted operator limit is honest.**

- The receiver is private `docker exec` infrastructure, not an HTTP route.
- Every mutation enters the existing absolute-command lock path and unchanged `--guard seed`; both exit 1 and 2 refuse before first write.
- `status` is read-only and creates no lock, token, audit, or credential.
- Owner selection uses only a guarded `current.json`, not directory listing/latest selection.
- Owner authorization, protected evidence, and runtime artifacts are canonical, hashed, write-once, regular files under guarded private directories.
- Backend compares stdin operation identity, mounted artifact bytes, persisted copies, test environment flags, and spec pins.
- The host independently discovers the current backend container and local Docker Image ID, source SHA, source label, versions.env hash, and accepted spec identities. OCI index/manifest digests are excluded.
- The design does not pretend the mounted artifact authenticates a malicious operator; it explicitly says the authenticated local operator is the trust boundary.
- Workspace secret transport is one bounded UTF-8 JSON stdin object with strict nested schema and duplicate-key/trailing-data rejection, no TTY, and only nonsecret `PYTHONPATH=/app`.
- Required canary tests inspect the actual child boundary.

I did not verify a running container because no implementation or runtime action was permitted. Finding 4 asks for the secret-environment canary wording to be scoped to Workspace credentials rather than the accepted application environment.

Opening, binding, closing, and deactivation are correctly distinct. A closed row cannot reopen or be deleted. A no-purchase window can close only on an empty complete delta. ## SIMPLER

**No simpler overall alternative preserves the exact signed proof, persisted authority, protected state, retained custody, recovery, and release obligations.** I tried to remove:

- the backend window/registration state machine — rejected because it is what closes cross-window and old-order admission;
- retained custody — rejected because deletion reintroduces the unprovable external-writer race;
- owner/runtime artifact verification — rejected because caller strings cannot authenticate the deployment;
- complete order-delta proof — rejected because a row lock/READ COMMITTED query alone does not exclude phantoms;
- the separate host helper — rejected because custody/docker orchestration and in-container DB mutation have different trust and filesystem roles.

The simplest correction for Finding 1 is to reuse the already specified advisory-lock/reset guard for all four protected fixture identities whenever Workspace lineage exists. It removes the two unprotected seller01/buyer02 destructive routes without adding a table, provider operation, or generic reset framework.

## BETTER

A materially better narrow structure is a single backend **Workspace protected-lineage guard** that maps a reset/teardown target to the declared protected collections and refuses whenever any W window, audit lineage, or custody lineage is present.

- **Compared with the current fixed-pair-only test:** it prevents destruction rather than merely detecting drift at closure; it also avoids duplicating actor-specific checks in each destructive path.
- **Failure modes:** broader false refusal if the target mapping is too conservative. That is safer than irreversible paid-history loss and can be relieved only by a reviewed collection map.
- **Cost:** one small shared predicate plus tests for seller01, buyer01, buyer02, seller02, unrelated targets, no-lineage, active, closed, and no-purchase states.
- **Rollback:** revert to the fixed-pair guard only with an explicit reviewed acceptance that P/N evidence may be damaged but later refusal is acceptable; the current requirements do not support that rollback.
