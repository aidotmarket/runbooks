## 4. Answers to the numbered questions

**Q1 — Does the corrected contract preserve actual TEST-only W authority and production/non-W isolation without claiming source equality or that the E2E flag alone proves either?**
Yes. The correction changes only the checkout branch rationale and its test expectation; it explicitly leaves W admission gated by the independent chain — `ENVIRONMENT=test`, strict `STRIPE_TEST_MODE=true`, fixed pair, immutable purchased source, owner/runtime/protected/pin state, and readiness — none of which a canonical checkout order satisfies. The production markers are real and verified in the embedded seam: `_stripe_event_has_s1656_test_shape` fails closed on `environment in {prod,production}`, `FRONTEND_URL == https://ai.market`, `RAILWAY_ENVIRONMENT`, `PRODUCTION`, `livemode is not False`, `"account" in event`, `normalized_stripe_account is not None`, all before any admission lookup, and signature/scope/dedup + both S1681 predicates precede W (W is the last `or` disjunct). The correction does not claim source equality: it distinguishes the canonical branch (`:149`) from the legacy guard (`:192`) at the line level and requires the final matrix to assert the default resolution (NIT-1) and unchanged non-W/production paths with **zero optional-W lookups** before rejection. The W-last optional-lookup boundary is preserved and is now source-consistent.

**Q2 — Are the branch and default/no-override tests precise and sufficient, with public checkout 200 distinct from real signed capture/registered refund? Is retained legacy behavior adequately bounded without manufacturing a green paid path?**
Yes. spec:75 now requires: (a) prove `ENABLE_CANONICAL_TX` absent from Compose/test-process and resolves to default true; (b) exercise the real canonical checkout under E2E false **and** true — both create order+transaction; (c) a **clearly labeled auxiliary** `ENABLE_CANONICAL_TX=false` test where flag=false → 403 before effects and flag=true → the legacy branch with real effects retained; and critically (d) "The final selected canonical/flag-true path must additionally prove the actual public checkout → normal signed capture → committed Workspace registration → normal signed full refund/replay lifecycle… merely obtaining a checkout URL is not this paid proof." That last clause is a strengthening: a 200 checkout URL is explicitly declared **not** paid proof. The legacy path is bounded to an auxiliary override that "must not be used as final Compose proof" and must not be called "canonical real paid capture." No green paid path is manufactured — the original false-403 case is retained as a documented failure (exit=1, logs retained), and the spec states outright "Do not merely change an assertion to obtain a green suite."

**Q3 — Are original paragraph 71/75 requirements and historical R3/R4 dispositions explicitly reconciled, and are unchanged true/[]/[] settings, service guards, monitor alert and upgrade inventory preserved?**

**The explicit boundary question — "is a new canonical guard necessary, or is the fail-closed W authority adequate? Reject rather than waive if not adequate."**
The private cooperating-owner boundary plus fail-closed W authority is **adequate**, and a new canonical checkout guard is **not necessary** to approve this correction, for four independent reasons: (1) the candidate changes documentation only — checkout.py behavior is untouched and checkout.py is deliberately not one of the fourteen backend targets; (2) W authority isolation is independent of the checkout status code — no canonical order can satisfy the owner-window/registration/readiness chain, so a 200 checkout cannot become W authority; (3) the canonical default is inherited M7 behavior (`BQ-BIZ-CANONICAL-TX`), pre-existing at `d766b8e4`/`c3`/`aca73` and not introduced by S1712; (4) the correction honestly declines to certify inherited synthetic checkout safe in every production config and books it as a reportable dependency for a separate release gate. Requiring a new canonical guard would itself be an unreviewed production-relevant behavior change — the opposite of the conservative scope this candidate keeps. The one concrete inherited path (mixed-synthetic bypass on the canonical branch) is a release-gate concern I record as NIT-2, not a mandate, because it neither affects W isolation nor is introduced here.

**Adjacent N-to-W lookalike regression assessment.**
Sound and correctly bounded. The failing node swaps only the N order/transaction actors to seller02/buyer01 on a **seller01-owned generic listing** (verified in `f1_pair` and the failure XML: `update {orders,transactions} set seller_id=seller-02,buyer_id=buyer-01`), with no purchased-version/publication/DeliveryAuthority — so it is a **forged non-W lookalike**, and the correct classification is terminal 200 suppression, not a genuine-W 500. The rejected alternative (declare every fixed-actor charge ambiguous-W → 500 when W schema absent) is correctly refused: it would broaden the optional-W dependency to non-W lookalikes and mask the classifier defect. The selected fix — check listing seller ownership and human/browser transaction binding **before** optional W reads — is the right direction and aligns with the standing invariant "a definitely unrelated/non-W event returns false without consulting optional W tables/mount." The critical guardrail is explicitly retained as a build requirement, not waived: `tests/test_refund_webhook_protocol.py` stays a non-target with its 200 expectation intact; final qualification must prove **zero optional-W lookups for the forged case** *and* genuine/registered-W unavailable → durable 500 with same-ID recovery, and must ensure classification "cannot silently discard a previously registered W charge when a later binding is damaged." That last point is the real risk of over-correcting, and it is named. This is context for scope, explicitly **not** Gate3 acceptance of MP247 source or a classifier shortcut — consistent with the candidate's documentary status. No blocker; the requirement to retain genuine/registered-W 500 recovery is the verification criterion I would hold the eventual implementation to.

### BETTER
One materially better *end-state* (not a mandate on this documentary candidate): enforce the intended TEST purchase-stop with a **narrow, explicit canonical gate** rather than leaning on the E2E flag semantics — i.e. a reviewed setting that stops canonical checkout for the fixed W pair during a closed/incident window, instead of relying on operational discipline ("Owner-controlled TEST purchasing must stop operationally on closure/incident"). Failure modes compared: the current design leaves purchase-stop as an operational obligation whose violation is caught only after the fact by cardinality/terminal-success refusal (extra orders invalidate success but are not prevented); a narrow canonical gate would prevent the extra order but is a new backend behavior/target with its own review, monitoring, and production-config surface — exactly what this candidate correctly refuses to smuggle in. Cost/rollback: the gate is a code+config change (larger blast radius, symmetric config rollback); the current approach is documentation-only (zero rollback). On balance the correction's choice is right **for a documentary Gate2 correction** — the gate belongs to a future reviewed product amendment if the owner wants prevention rather than detection, and the spec already provides that reject/amend path. Recorded as advisory, not a mandate: no scope violation or material W-isolation risk supports elevating it.
