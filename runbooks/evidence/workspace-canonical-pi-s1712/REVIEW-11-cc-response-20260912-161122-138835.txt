## 4. Answers to the six feared-failure questions

**Q1 — Can an old/other-window W order, P/N, or altered purchase gain signed refund admission?** No, by design, and the design is grounded. Admission requires an immutable `workspace_refund_test_authorities` row bound at bind-purchase with UNIQUE `order_id`(PK)/`window_id`/`transaction_id`/`payment_id`/`payment_intent_id`/`charge_id`, RESTRICT FKs, fixed-actor CHECKs, and canonical `registration_json` capturing `immutable_scope_hash`, `approval_review_hash`(=`SellerListingApproval.review_hash`=`SellerListingPublication.review_hash`, never `request_hash`), `listing_manifest_hash`, and full pins. Bind requires the persisted baseline's complete fixed-pair set to still exist and the new-order delta to contain **exactly one** paid order (never "latest", never silently filtered). The webhook predicate only *locks and compares* existing rows (order→transaction→order_money_states→Payment→Refund, sorted IDs, SELECT FOR UPDATE NOWAIT), performs no DML, does not create missing state, and requires runtime-pin match; an old same-pair unregistered order, P/N, another window's order, changed scope, or mismatched pins is rejected before W processing. Post-close/recovery windows retain authority only for their originally registered charge/order. Verified anchors: schema fields, `lock_order_money_sync` genuinely inserts (so "do not call it" is load-bearing), suppression seam converges the same signed event ID normally once ready.

**Q2 — Can public purchase, duplicate binder, or reset destroy protected history or defeat exact cardinality?** No. **Reset vector (the R3 fix): verified closed.** `SurgicalResetService` unconditionally refuses the four normalized UUIDs after auth/allowlist/apply-review and before `_execute`; since `reset()` is the sole entry and `_execute`→`_reset_database_rows`/`_reset_objects` the sole deletion path, the four cannot reach deletion at all — independent of W table/mount/pointer/audit/window state, in both dry-run and apply, and immune to the `_safe_scalar/_safe_execute` rollback-and-continue that defeated R2's advisory lock. No host-file/advisory serialization fiction remains, and none is needed (there is nothing to serialize against a path that cannot delete). **Cardinality/duplicate-binder:** `LOCK TABLE orders IN SHARE MODE NOWAIT` before row locks conflicts with public order ROW EXCLUSIVE writers (bounded, TEST-only), the `namespace where state<>closed` partial unique index enforces one nonclosed window, and same-window `SELECT FOR UPDATE NOWAIT` + unique constraints serialize duplicate binders. An extra paid order after bind cannot gain authority and forces the named preservation-incident (retain `recovery_required_extra_order`, converge only the registered refund, no silent deletion, no auto-close). Bounds require the specified PostgreSQL two-session tests (measured, not sleep-based) — UNVERIFIED at runtime by design.

**Q3 — Can activation/recovery overwrite a generation/Party or duplicate provider resources?** No, by design. No DELETE/PATCH/upsert on TOTP custody (Infisical raw API has no atomic versioned DELETE; a local lock excludes no external writer — acknowledged); create-once with exact GET reconciliation, `recovery_required`/`abandoned` states, timeout≠absence. Connect: complete pagination, foreign-Connect-binding proof and Party/auth_user lock **before** projection, with the explicit warning that the existing upsert reassigns party ownership and must not run first; expired/uncertain idempotency never authorizes a fresh account. Restoration restores only the enumerated seller02 readiness fields and removes only the exact newly-owned Connect row; never deletes Party/auth_user; `User.updated_at` correctly not touched (unmapped — verified). Typed readiness restoration and drift→`deactivation_incomplete` are specified. Provider-stub tests (pagination, duplicate-marked, uncertain create, aged idempotency) required — UNVERIFIED at runtime.

**Q4 — Can caller/bypass/artifact/image substitution gain authority or leak a new Workspace credential?** Not beyond the honestly-declared trust boundary. The design explicitly states the authenticated local operator is the trust boundary and that a hash/actor/UID/flock does not authenticate a malicious operator, an owner attestation is **not** cryptographic external verification, and the backend cannot self-measure its image (host's separate Docker verification, retained as evidence). The design does not overclaim application-wide secret-freedom (the R1 CC over-assumption is explicitly disavowed). This is the correct honest posture; residual exposure is the trusted-operator assumption, stated plainly.

**Q5 — Are lifecycle transitions, immutable schema/readiness, locks, and implementation files concrete and complete?** Yes, at design altitude. Two new tables with immutable triggers (reject DELETE and mutation of opening/baseline/identity), forward-only transitions (open→bound/closing/recovery, bound→…, closing→closed/recovery, recovery→closing) with `revision`+1 and paired terminal fields + nonnull `closed_at` set together, closed fully immutable; readiness verifies tables/columns/FKs/CHECKs/unique indexes and enabled trigger definitions alongside order-money readiness, with sync-admission and async-processor both rejecting drift. ## SIMPLER

For the **reset vector specifically, none simpler found** — and this is the point: R3 *is* the simplification. It removed a per-namespace `pg_try_advisory_xact_lock`, a strict-destructive fixed-party branch, and per-target lineage inspection (workspace_test_windows lookups on the reset path), replacing all of it with a normalized four-constant membership check before `_execute`. What remains is near-minimal. The only micro-reduction available: place the guard *before* the allowlist check rather than after, so protection is a single unconditional constant-set test that does not depend on allowlist ordering or on the four being allowlisted for the `workspace_protected_fixture` category to appear — removes one ordering dependency, zero behavior change. Advisory, marginal.

For the **overall two-stage authority**, none found without losing a requirement: the persisted baseline + unique registration + immutable-hash comparison + bounded synchronized locks are each load-bearing for "exactly one registered order, old/other orders excluded, paid history preserved." Dropping the registration table (the previously rejected no-table option) reopens Q1; timestamp-only cardinality or disabling registered-refund convergence are explicitly out (and correctly so).

## BETTER

**Considered and rejected as a mandate: database-level protection of the fixture rows** (a row trigger or non-deletable flag on the four users and their paid order/refund/transaction history, refusing deletion at the DB layer regardless of code path). It would beat the app-level guard on one axis — it protects against a *future/forgotten* deletion path, not just the one known surgical-reset endpoint (the app guard's blast radius is exactly one service). **But its failure mode is disqualifying here:** the money proof's own clean lifecycle (`bin/reset`, settlement-guarded) legitimately resets seller01/buyer01/buyer02 between P/N runs before W; a blanket DB-level deletion block on those identities would break that authorized reset, and scoping a trigger to "paid history only, not readiness fields" is fragile and easy to get wrong. Cost: a migration + trigger + careful carve-outs; rollback: drop trigger (but any interim break of `bin/reset` stalls the proof). The design already keeps RESTRICT FKs as defense-in-depth and correctly locates the *conservative* block at the surgical-reset service — the one path that must never touch these fixtures — while leaving the settlement-guarded lifecycle free. So the app-level scoping is arguably the right layer, and I record the DB-trigger alternative as **advisory, not recommended**. No materially better approach found that preserves the clean-lifecycle reset requirement.
