## 4. Answers to the six required feared-failure questions

**Q1 — Can an old same-pair W order, another window/order, P/N or an altered canonical purchase binding gain signed TEST refund admission?** **No, by construction — this is the predecessor's blocking defect, now closed.** The opening baseline is captured under `LOCK TABLE orders IN SHARE MODE NOWAIT` and persists the *complete* fixed-pair order-UUID set in every state (`GATE2.md:75,81`), so an old order is inside the baseline and can never appear in the Stage-B delta, which must contain **exactly one** new order and must be actually paid with a unique canonical capture (`:83`). Admission then requires an exact immutable registration row (`workspace_refund_test_authorities`: `order_id` PK, unique `window_id`/`transaction_id`/`payment_id`/`payment_intent_id`/`charge_id`, fixed actors, listing/version/publication/authority/connection bindings, RESTRICT FKs, immutable trigger), revalidated by the predicate against the canonical receipt (`:75-79,89`). P/N cannot satisfy it (different seller/none-or-different authority kind; separate table, separate predicates — `s1681_refund_test_admission.py:266,270`), and a closed/recovery window keeps authority only for its originally registered charge and “cannot bind a second order” (`:89`). An altered binding changes the canonical hashes and refuses. Reproduction: static (spec + verified source below). The residual is L1 (unregistered = suppressed, not admitted).
**Declaration/protocol checks are real:** `DeliveryAuthority.authority_kind`/`legacy_serial_id`/`connection_id`/`immutable_scope_hash` with the workspace-connection CHECK (`seller_workspace.py:656-706`), publication→approval→version→manifest hashes (`seller_listing_publication.py:14,21`; `seller_listing_approval.py:20`; `marketplace.py:227`). **Not verified:** the invented-field prohibitions cannot be executed here; no test was run.

**Q2 — Can concurrent public purchase, a duplicate binder or a surgical reset defeat complete baseline/cardinality/history preservation?** **No on the stated design, and the specific hazard the design names is real.** I reproduced the trap: `_safe_scalar`/`_safe_execute` `await db.rollback()` on “does not exist” and continue (`surgical_reset.py:306-322`), which would drop a transaction-scoped advisory guard mid-reset — hence the strict path and “no swallowed rollback, reconnect or helper commit” requirement. Reset/seed guards do run before cleanup (`bin/reset:6-10`, `bin/seed:6-10`), and `workspace-fixture` is outside the guarded-name set, so the explicit `--guard seed` is genuinely required. The SHARE / ROW EXCLUSIVE conflict the design invokes is correct per PostgreSQL 17's documented matrix (SHARE conflicts with ROW EXCLUSIVE and is compatible with ACCESS SHARE/ROW SHARE/SHARE), so a concurrent order INSERT/UPDATE/DELETE cannot slip past `LOCK TABLE orders IN SHARE`; the design also explicitly refuses to claim a flock serializes public buyers. **Limit:** the spec itself requires genuine two-session PostgreSQL tests (writer already active, writer during SHARE, pre-existing `SELECT FOR UPDATE`, two same-window binders, timeout/deadlock recovery, extra order after bind); none ran here, so exclusion is **design-level only**. L2 records that the extra-order case has no defined exit.

**Q3 — Can credential/provider activation or recovery overwrite another generation, reassign a Party or duplicate a resource?** **Not on the design, and the destructive path is now gone.** The revision performs **no DELETE, PATCH or upsert** for custody and installs an explicit retained-custody terminal (`inactive_with_retained_custody` / `deactivation_incomplete`) with reuse/drift rules (`GATE2.md:123-135,153-163`); because nothing destructive is ever issued, an unseen post-read external writer can no longer have its value erased — which is exactly what makes the predecessor's read→name-DELETE TOCTOU moot rather than “handled.” Verified supporting facts: the packaged pool stores secret **names only** and rejects value-like tokens (`app/e2e/account_pool.py:17-34`); seller02 currently has no TOTP name, so the spec's “add exactly `E2E_SYNTHETIC_SELLER_02_TOTP`” is a planned edit inside the frozen target (I verified 0 occurrences today); `User` has no `updated_at` to fabricate, `totp_verified_at` is nullable, and the Stripe projections are strings (`user.py:71-87`); `TOTPService.verify_setup` commits and mints backup codes, so restricting activation to `_encrypt_secret` in the owned transaction is necessary and correct (`totp_service.py:69-105,238`). Provider duplication is bounded by 0/1/many marker enumeration and “idempotency expiry never authorizes a fresh account.” **UNVERIFIED:** Infisical write/absence semantics (no provider call; the no-CAS limitation is admitted by the design, and no fictional CAS/ACL is assumed).

### SIMPLER
**None found that preserves every requirement and invariant.** Everything I tried to remove is load-bearing: (a) the second authority **table** — removing it re-creates predecessor F1 exactly (any qualifying same-pair order would be admitted), which is the one thing the owner explicitly required; (b) the persisted **baseline** — removing it makes “exactly one window order” unprovable, since the webhook deliberately cannot trust a host snapshot; (c) the mounted **owner/runtime artifact** — removing it re-creates predecessor F2 (a pin with no referent / caller-supplied self-assertion); (d) the **`LOCK TABLE orders … SHARE NOWAIT`** — removing it leaves the phantom-insert hole the design itself calls out (“a local flock or READ COMMITTED alone does not exclude phantoms”); (e) **retained custody** — the destructive alternative is the predecessor's rejected HIGH. No scope violation is evidenced, so the only advisory micro-reduction I can offer is cosmetic (e.g., collapsing the paired `*_json`/`*_sha256` columns into one canonical-text column with a generated hash) and it would weaken the “hash only the preimage bytes” rule; not recommended. **None found.**

### BETTER
**One materially different structure, advisory only (no scope violation or material risk evidenced).** Anchor Stage B’s authority in the **authenticated provider object** rather than in a persisted pre-purchase baseline plus a global table lock: bind the registration to the exact PaymentIntent/charge already observed pre-lock and additionally require `orders.created_at > window.opened_at` (read under the same snapshot), keeping the existing per-order immutable registration, uniqueness and RESTRICT FKs. **Failure modes vs current:** the current design’s SHARE lock briefly blocks *all* order writers in the TEST database and creates the L2 dead-end where a stray purchase permanently blocks closure; the provider-anchored variant removes both — a stray purchase simply never gains authority (which the current design already asserts) and no longer poisons close. Its own new failure modes are a dependency on provider `created` monotonicity and loss of the “exactly one new order” anomaly *signal* (it would become a diagnostic instead of a hard refuse). **Cost:** drop the baseline/delta machinery and roughly the eight concurrency tests the spec requires for it; add one provider-timestamp comparison and its tests. **Rollback:** trivially revert to the baseline+SHARE design, since the registration table and predicate are unchanged. I do **not** mandate it: the SHARE-lock design is deliberately minimal-visibility (it cannot modify the public purchase path), which is a legitimate reason to prefer it, and the design's own requirement to *measure* real lock bounds is the honest way to settle it.
