**Q2 — Does the exact shared-lock/inner-guard protocol preserve run25 and fail closed on every error?** Yes. I verified the wrapper mechanics line-by-line (path-only `--lock`, token + ancestor + held-lock revalidation, guarded-name set missing the new command, exit-code propagation, 30-min deadline) and the live `pending_settlement` checkpoint, so today an `activate` through `--lock bin/workspace-fixture` + `--guard seed` refuses with exit 2. run25 is preserved by three independent facts: the amendment is an opt-in overlay, the S1681 harness is not in the allowlist, and the protected checkout sits at `03d3f30` with both pins `519b1d58`. **Q3 — Are before-state custody, idempotent provider creation, recovery and deactivation sufficient?** Yes at design level, with three Gate2 concretions: (a) the audit schema/version, the enumerated restorable seller-02 fields (`totp_enabled`, `totp_verified_at`, `totp_secret_enc`, `backup_codes_hash`, `stripe_account_id`, `stripe_onboarding_complete`, `stripe_payouts_enabled`, `stripe_details_submitted`) and the secret ownership/version discriminator must be frozen (the current TOTP path writes `user.totp_secret_enc` directly with no version token); (b) the "refuse preexisting incomplete-readiness accounts, never repair" rule must apply to activation and deactivation; (c) `bin/reset`/`bin/seed` must be *taught* to refuse when an active/inconsistent audit exists — that refusal is required, not current behavior. ### SIMPLER

**None found for the fixture/refund interface itself.** I tried to remove: (a) `seed/workspace-host.py` in favour of hosting the enrollment mode in `bin/workspace-fixture` — rejected, because the receiver must run inside the container against the read-only `./seed` mount (`/s1656`) or backend code, so one host-side entrypoint cannot do both jobs; (b) folding activation into `bin/seed` — rejected, the default seed must retain its baseline while refusing gained readiness; (c) dropping the committed evidence JSON because it duplicates the `outputs/` file byte-for-byte — rejected, the in-repo copy is precisely what makes the authority resolvable and re-verifiable (GLM M1). The nearest real reduction is N1: replace the machine-local absolute path in `:114` with the in-repo relative path + blob sha256 — removes one unresolvable dependency, zero functional change, zero invariants touched.

### BETTER

**Replace the prose hash method with a committed, machine-checkable identity manifest** (e.g. `specs/evidence/S1712-source-identity.json`: file → git-blob SHA + SHA256 + the exact extraction command per range), generated by a script and re-run at Gate2/Gate3. Compared with the current sentence: the failure mode it removes is exactly F1-style ambiguity (a documented digest that does not reproduce), plus the human-prose step between "revalidate source identity" and a pass/fail; its own failure mode is manifest drift if hand-edited (mitigable by generating it in the same step that freezes pins), cost is one small committed file and one generation step, and rollback is trivial (docs-only, no product or environment effect). A second-order alternative — moving the admission predicate behind a Mars-owned seam — was proposed in Round 1 (CC BETTER) and is now explicitly **not selected** by the fold unless Mars's accepted interface already provides it; I do not re-propose it as a mandate, since the serialized-integration decision plus requiring Mars's accepted contract is an evidence-supported, non-blocking choice.
