## 4. Answers to the six numbered questions

**Q1 — Can old/other-window/P/N/changed-purchase authority gain signed W admission, or can a terminal unregistered refund be fabricated into convergence?**

**No — and I am correcting my prior Q1 wording here.** The actual branch (verified at `admits_workspace_refund@e621c760:344-386` + seam `webhooks.py:559-578`, and matching the design at §"Authority precedence after stable classification" and §"Post-authority Transaction comparison"):
- **Definitely non-W / P/N / production-shaped traffic** → `return False` on shape/actor/amount or empty fixed-pair discovery **before any optional W schema/mount lookup** (the S1681 negative/failed_run disjuncts run first; W is last). Its existing 200/response path is unchanged; zero optional-W dependency.
- **Fixed-pair W charge, fully available compatible authority, no registration** → `return False` → the seam's existing synthetic path suppresses it: **HTTP 200 `e2e_scope_suppressed`, `stripe_events.status='completed'` (terminal suppression)**. This is honest and non-convergent: "signed event suppression is terminal and acknowledged, no registered authority exists and there is no compatible convergence path" (§close-window incident disposition). It is not fabricated into convergence — the window becomes an un-closeable `recovery_required_unregistered_refund` incident (§close-window).
- **Registered/qualifying W charge with missing/incompatible readiness, mismatched runtime pins, uncertain lookup, or post-registration binding drift** → `raise WorkspaceTestAuthorityUnavailable` → the critical `charge.refunded` path: rollback, durable failed/retryable event, **non-2xx (500)**; the same signed event ID converges exactly once after readiness is restored.
- **Registered, all bindings intact** → admitted → normal signed W refund.

Old-pair unregistered / other-window / P/N / changed-purchase authority cannot reach admission: window-scoped authority is enforced by the two tables (unique `order_id`/`window_id`/`transaction_id`/`payment_id`/PI/charge; one-nonclosed-window partial unique index; immutable registration), and post-resolution comparison raises (`OrderMoneyConflict`/`WorkspaceTestAuthorityConflict` wrapped as `WorkspaceTestAuthorityUnavailable`) rather than returning terminal `False`.

**Correction to my prior wording:** my earlier response said unregistered fixed-pair traffic "invokes `_validate_registration`/refuses." That is inconsistent with the actual branch: `_validate_registration` (:324) runs **only after** a registration row is found (registered path); unregistered fixed-pair traffic with available compatible authority returns `False` and is **terminally suppressed at 200**, not refused with a 500. The 500/durable-failed path is reserved for registered/qualifying-but-uncertain charges. The design behavior is correct as written; only my description was wrong, and it is retracted. **Not blocking** — this is the answer's correction, not a defect in the candidate.

**Q2 — Can either cleanup service or concurrent purchase/binder destroy history/cardinality?**

**No, by design.** Both `SurgicalResetService.reset` and `TeardownService.teardown` unconditionally refuse all four fixture UUIDs via the shared pure `is_protected_workspace_fixture` (verified in both services), independent of any W table/mount/pointer/audit/lineage — so the four identities and their P/N history cannot be deleted before, during, or after a window, or when lineage is missing/damaged (§"Surgical reset preservation…"). This resolves the R2/R3 sibling-teardown MEDIUM (GLM G2-revised MEDIUM#1; DeepSeek R3 M1; GLM R3 MEDIUM#1a). Concurrent purchase/binder: Stage A/B use `orders SHARE NOWAIT` before row locks with bounded `lock_timeout=250ms`/`statement/idle=2s`/host-5s and full-transaction rollback; a new order after binding cannot gain authority (unique window/order binding) and makes closing refuse on cardinality; same-window duplicate binders serialize via `SELECT FOR UPDATE NOWAIT` + unique constraints (§"Persisted two-stage W authority and concurrency"). Honest scope limits: the contract does not claim protection against privileged arbitrary SQL, future unguarded routes, authorized Docker-volume destruction, or that a DB lock serializes a host-file writer — all correctly stated. The composite discovery FK (design-proposed) additionally freezes the registered order's `(id,seller,buyer,listing,PI)` against post-registration mutation. Cardinality/immutability proofs are LOW-flagged (L1/L2) as MP/Gate3 work. **Not blocking.**

**Q3 — Does final TEST synthetic checkout work under explicit reviewed settings while both cleanup services remain protective?**

**Yes, by design, with the canonical-vs-legacy correction correctly applied.** `compose.yaml` sets the three literals (`E2E_TEST_ROUTES_ENABLED:"true"`, empty reset/teardown allowlists); the flag gates **only** the legacy synthetic checkout branch, while default `ENABLE_CANONICAL_TX=true` returns via the canonical branch *before* that guard (§"Workspace TEST runtime configuration"; §"Proposed canonical checkout correction"). The contract explicitly corrects the earlier erroneous generalization that flag-false yields a 403 on default checkout, retains the failed `test_fresh_main_lifespan_public_checkout_reviewed_settings[False]` node as discovered evidence rather than relabeling it passed, and mandates a fresh-start ASGI branch/config/paid-flow matrix. Crucially, "the same flag imports both account cleanup routes, so the unconditional shared four-UUID service refusal remains mandatory even if an isolated test deliberately populates the allowlists" — so arming does not create a destructive escape (resolves GLM R3 MEDIUM#1b). The expected `e2e_routes_over_armed` P1 monitor alert is retained and attributed, not suppressed. The full canonical paid lifecycle (checkout → signed capture → committed registration → signed full refund/replay) is required as proof, "merely obtaining a checkout URL is not this paid proof." Any discovered production exposure is an explicit release dependency, not silently accepted. Execution of these tests is MP/Gate3 (L1). **Not blocking.**

**Q4 — Can activation/recovery or substitution duplicate resources, overwrite generation/Party, or leak a new Workspace secret?**

**No, by design.** Custody performs no DELETE/PATCH/upsert ever (create-once; reuse only on exact retained UUID/version/digest/marker/scope/name agreement; drift/uncertainty → `recovery_required`/`inactive_with_retained_custody`/`deactivation_incomplete`, never re-enroll), which is the accepted resolution of the Infisical TOCTOU (GLM G2-design HIGH#2) — "Since no delete/upsert/patch occurs, an unseen post-read writer cannot have its credential erased" (§"Custody protocol"). Account creation is create-once with marker/idempotency reconciliation, multi-match refusal, and no fresh account on idempotency expiry. Party/auth_user identity is never deleted; projection validates and locks the exact Party binding and proves no foreign Connect identity before owned-identity creation in one transaction; the broad `upsert`/`ensure_local_users()`/`establish_parties_and_assertions()` helpers are forbidden. The child-boundary canary asserts no plaintext TOTP/custody secret in argv/env/output/audit/exception; responses are bounded allowlisted nonsecret JSON; only `PYTHONPATH=/app` is permitted (the one nonsecret assignment, resolving DeepSeek G2-design F4). Runtime pins separate `backend_local_image_id` (local Docker Image ID) from any registry/OCI index digest (resolves GLM G2-design MEDIUM#3); `owner_window_id` derives from the owner-issued artifact + persisted row, not a caller pin (resolves DeepSeek G2-design F2). Real-subprocess/PG proofs are MP/Gate3 (L1). **Not blocking.**

**Q5 — Are schema/lifecycle/readiness/recovery/target files and immutable columns concrete, with no invented money field or inserting helper?**

**Yes.** The two tables, columns, CHECKs, the one-nonclosed-window partial unique index, and the immutability/forward-transition triggers are concrete and DB-enforced (verified in `20260912_002…`); the immutable-column set and the exactly-mutable lifecycle columns (`state,revision,closed_at,terminal_json,terminal_sha256`) match the contract precisely. Readiness verifies ancestry/columns/constraints/unique indexes and exact enabled trigger definitions, and (design-proposed) the extended catalog for the parent UNIQUE + composite FK + RI triggers. **No invented money field:** no refund-outcome column on the authority row — "outcomes stay in canonical financial/event tables and separate terminal receipts"; readiness/predicate never manufacture capture. **No inserting helper in the predicate:** the predicate uses read-only `lock_existing_workspace_money_sync` (verified), must not call the creating `lock_order_money_sync`, and refuses a missing row "without db.add/INSERT or repair" (I confirmed no `db.add`/INSERT in the admission path). The 17-backend-target list is concrete; the three added test modules and the discovery-reference schema are flagged as requiring fresh review (which this is). **Not blocking.**

**Q6 — Are support/upgrade/release obligations honest and complete?**

**Yes, and unusually disciplined about what is *not* proven.** The maintainer diagnosis map binds symptom→evidence→recovery→prohibited-shortcut for every category; the support bundle enumerates included nonsecret identifiers and excluded secrets/URLs/raw provider bodies. Upgrade qualification refuses unknown audit versions without rewriting, tests all audit phases incl. provider-response-loss and DB-commit/host-receipt-loss, and forbids old payment binaries over new authority absent a proven cutover. The release sequence keeps run25/holds/quiescence/provider-reconciliation/external-transport/BQ-Gate4/full AWS-S3+R2 as **separate execution gates**, and repeatedly states design acceptance ≠ implementation/release. Honest residual limits are named, not hidden: the §17.3 transport gap, the unmapped `BillingEntity.doppler_key_prefix` inherited defect (bounded source inspection only), the historical-observation-vs-fresh-availability distinction, and the toy-probe/external-copy limits (L2). **Not blocking.**

### SIMPLER

**None found that preserves every invariant.** The binding constraint is "zero optional-W dependency for non-W / forged-N traffic": the cheap classifier must decide W-vs-not by reading only `orders`/`listings` *before* any W-authority/mount lookup. That forbids resolving the order via the immutable registration row (reading it is itself an optional-W lookup), so the order's own discovery columns must be frozen; the only two options are the validated composite FK (chosen) or a hand-written core-mutation trigger on `orders` (explicitly rejected as broader/less-introspectable). The composite FK is already the minimal viable core-schema touch, and it retired the R3-era advisory-lock + strict-destructive-branch complexity entirely (§"Surgical reset preservation…": "Remove the superseded reset/open `pg_try_advisory_xact_lock` and strict destructive fixed-party branch"). What I tried to remove — the `orders` UNIQUE/FK — cannot go without reintroducing the registered-drift hole or violating zero-optional-dependency. The redundant-looking `uq_s1712_order_discovery` is not removable either: it is the *referenced key* the composite FK requires. Advisory only.

### BETTER

**None materially better — and the one prior BETTER proposal is already incorporated.** DeepSeek's a4 BETTER ("make the registration lookup authoritative before any shape filtering; validate every retained binding and *raise* on mismatch; keep unregistered-200 and registered-uncertainty-500 structurally disjoint rather than ordering-dependent") is exactly what this candidate adopts in §"Post-authority Transaction comparison and exception routing" (the field→exception table wrapping `OrderMoneyConflict`/`WorkspaceTestAuthorityConflict` as `WorkspaceTestAuthorityUnavailable`; "No mutable Transaction comparison may return terminal False before or after registration resolution") and §"Authority precedence after stable classification." A declarative, `convalidated`, catalog-checkable composite FK has strictly better failure modes than a PL/pgSQL trigger (introspectable by readiness; cannot be silently bypassed by a mis-authored branch) or an application-layer re-check (cannot be skipped under concurrency). Its one cost — the migration-time `ACCESS EXCLUSIVE` index build on core `orders` — is L1-flagged, mitigable, one-time, and trivially rolled back, guarded by the retained-authority `downgrade()` refusal. No materially better structure found.
