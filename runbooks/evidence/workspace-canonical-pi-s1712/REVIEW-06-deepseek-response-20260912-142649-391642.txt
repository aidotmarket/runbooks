## 1. Verdict

**REVISE**

The artifact itself is genuine and every identity I could reach reproduces exactly (spec bytes, blob, base/candidate, dependencies, Gate1 responses). But the Gate2 package was dispatched to close two named blocking determinations, and it closes neither: the W admission authority is deliberately left purchase-scoped rather than window-scoped, and the machine-checked `owner_window_id`/`owner_window_sha256` pins have no defined artifact anywhere in the accepted dependencies. Two MEDIUM (blocking) findings below.

## 2. Findings (highest severity first)

### F1 — MEDIUM (blocking) — The W refund-admission authority is purchase-scoped, not window-scoped; the artifact concedes the gap and defers the decision instead of deciding it.
- **Evidence.** `aidotmarket/runbooks@e138f16a:specs/SELLER-WORKSPACE-ACTIVATION-S1712-GATE2.md:53-58` — predicate = order → purchased_version → SellerListingPublication → DeliveryAuthority → seller-owned CloudConnection (`authority_kind=workspace_connection`, `legacy_serial_id=null`, listing/seller/version equality, immutable approval hash). Line 57: *"Mars4152 concurs that this persisted chain provides W/N separation and permits revoked-authority refunds, but explicitly does not prove membership in a particular host window. Gate2 review must explicitly assess whether this predicate scope matches the accepted exact-order authority requirement."* Line 23 repeats it as *"an explicit blocking design question for Gate2."* Accepted dependency `aidotmarket/runbooks-s1714-refund-release-spec@26588d35:specs/BQ-REFUND-SAFE-PRODUCTION-S1714-GATE2.md:149` (§8) states the requirement the artifact must meet: *"N is seller01/buyer01 S1681; W is seller02/buyer01 Workspace. They use separate exact persisted authorities, never actor-only permission."* Seam verified in source: `aidotmarket/ai-market-backend@c3a62af8:app/api/v1/endpoints/webhooks.py:559-576` (synthetic suppression with the N/`applied_refund_replay` exception list).
- **Observed:** the DB predicate admits any workspace purchase matching the fixed seller02/buyer01 chain — correct on actors, payment-intent/charge binding and capture, but with no window term (no run/window ID, no time bound, no per-window registration). A prior window's still-unrefunded W purchase satisfies the predicate identically. **Expected:** the admission authority and the evidence authority are the *same* object, so an order outside the owner-authorized window cannot be admitted by the exception. Per-order scope is satisfied ("exact persisted authority, never actor-only"); window membership is not — and the artifact does not decide which is required.
- **Reproduction:** static evidence only (spec text + `webhooks.py:559-576`; schema fields confirmed present at `app/models/seller_workspace.py:662-697` and `app/models/seller_listing_publication.py:12-22`, so no silent schema extension is hidden in the predicate itself).
- **Impact:** the suppression exception is broader than the window it exists to serve; an off-window same-pair W refund would be processed (TEST-only, provider-signed, and re-validated by the normal processor, so financial-corruption risk is low — authority-scope and evidence-integrity risk is not). It also means W's authority is weaker than N's (an immutable registered row bound to exact orders under the owner lock).
- **Smallest required outcome:** close the choice in the spec. (a) *No new table:* declare per-order purchase scope as the accepted W authority, require the owner's (Mars) written concurrence recorded as an artifact, and state + test the residual that an off-window same-pair workspace order is admitted. (b) *Registration:* add the minimum immutable registration — one product table keyed by `owner_window_id` (UUID) holding the exact order/PI/charge/listing/version/authority/connection/buyer/seller IDs, written by a private operator CLI under the existing `S1681` owner lock (same pattern as §8 `register-test-negative`), read by the W predicate, with cleanup and tests (off-window refused, duplicate refused, wrong window refused). Option (b) exceeds the current frozen allowlist and therefore itself needs the explicit scope extension the artifact already anticipates.
- **Verification criterion:** for (a) an explicit accepted-authority record plus a test that an off-window same-pair order's `charge.refunded` event is admitted *by design*, with the justification; for (b) a test that it is refused.

### F2 — MEDIUM (blocking) — `owner_window_id` / `owner_window_sha256` are load-bearing pins with no defined source artifact.

### F3 — LOW — Exclusive custody is asserted as a condition but is not a recorded/attested precondition; the read→DELETE TOCTOU residual is not stated as an accepted limit.
- **Evidence.** `...GATE2.md:74-77` (*"Bind the exact ID/version/value digest and operation marker, re-read immediately before delete under the owner-held shared fixture lock, and require exclusive ownership of this fixture secret for the entire operation. Verified premise: `aidotmarket/runbooks-s1714-refund-release-spec@26588d35` and the artifact correctly refuse to claim a CAS endpoint (Infisical DELETE is by `secretName`).
- **Observed:** "any observed drift preserves the item" is enforceable only for drift observed *before* the last read; a write between the verified read and the name-based DELETE is unobservable and would be destroyed. **Expected:** the invariance ("never delete a changed or foreign credential") is provided by the *exclusivity* condition, not by the read, and that condition must be a positive, recorded attestation (owner window open, shared lock held, no other authorized writer for `E2E_SYNTHETIC_SELLER_02_TOTP`), with creation itself gated on it, not only deletion.
- **Reproduction:** static evidence only.
- **Impact:** low (TEST fixture, single name, operator-controlled), but the spec currently reads as if the read-then-delete sequence provides the guarantee.
- **Smallest required outcome:** state explicitly that atomicity is unachievable by contract, that the enforceable condition is (i) recorded exclusivity attestation as a precondition of creation *and* deletion, (ii) `id/version/digest/marker` equality at the last read, (iii) post-DELETE authenticated-absence verification, and (iv) preserve-and-report on any drift or uncertainty — and add the tests the spec already lists (external version change, delete-response loss, 404-vs-403, deleted/recreated same name).
- **Verification criterion:** audit schema contains the exclusivity attestation; tests exercise a post-read write and assert no foreign value is destroyed / cleanup is reported incomplete.

## 4. Answers to the numbered questions

**Q1 — Can the W exception admit another order, P/N, an arbitrary synthetic actor or an out-of-window refund?** *P/N and arbitrary actors: no. Out-of-window same-pair W order: yes, by design (F1).* The predicate binds the exact persisted PI/charge → order → purchased_version → publication → delivery authority → seller-owned connection, requires `authority_kind=workspace_connection`, `legacy_serial_id=null`, listing/seller/version equality and the immutable approval hash — that is an *exact per-order* authority, not actor-only, and it cannot match N (seller01, serial/`legacy_serial_id` delivery) or P. It has **no window term**, so a stale same-pair workspace order is admitted identically; the artifact says so and asks Gate2 to rule. Window membership exists only on the host side (delta vs complete pre-window snapshot, "no arbitrary order parameter", refuse zero/multiple new paid orders) and in the W receipt — which the predicate deliberately cannot use. Signature/synthetic/refund seams and normal processor locks are as described (`webhooks.py:476-576`; suppression is the only thing bypassed; refunds remain possible after revocation because the predicate reads retained immutable bindings, not active download eligibility). **Blocking condition:** the exact authority (per-order scope, or window registration) must be *decided and written into the spec* — today the choice is open, which is exactly what the requester forbade ("do not … authorize a build on an incomplete choice").

**Q2 — Can activation/cleanup overwrite or delete another generation or party?** *Not under the stated controls, but the control is operational exclusivity, not a provider guarantee (F3).* Verified: `DELETE` by `secretName` has no documented ID/version precondition; nothing in the design claims otherwise, which is correct. Required concrete outcomes: create-once (no PATCH/UPSERT); bind `id`+`version`+value digest + nonsecret operation marker; verify `marker`/scope/name/ID/version before any mutation; delete only the item this operation created and only while the shared owner lock is held; immediately re-read before DELETE; post-DELETE authenticated absence for the same fixed name; a *new/changed* item is preserved and reported; plaintext never returned or logged; `User` Stripe fields treated as strings; TOTP encrypted via the unchanged `TOTPService`; Party/auth_user never deleted and never reassigned via the Connect upsert (proof of no foreign identity precedes projection); uncertain create reconciles by marker/digest, never a fresh create after idempotency expiry. The residual that cannot be closed (a write between the last verified read and the name-based DELETE) must be stated as an accepted limit and covered by the exclusivity attestation — this is the enforceable condition, not a CAS endpoint (which is correctly not demanded).

**Q3 — Can a wrapper bypass the lock/guard, mutate before refusal, leak a secret or repair audit state?** *No, on the evidence — with one wording defect (F4).* Verified placements: `bin/seed:8-10` / `bin/reset:8-10` take the inherited `--lock` and then `--guard seed|reset` before Infisical injection, S3 upload/cleanup and container destruction; `check-settlement:340` refuses `pending_settlement` with exit 2 and `:366` propagates the refusal to children; `workspace-fixture` is outside the guarded-name set, so an explicit `--guard seed` is genuinely required; `status` is specified read-only and must not create token/audit/lock. Proposed private stdin transport (≤16384 bytes, read ≤16385, single UTF-8 JSON, reject duplicate keys/trailing data/unknown keys/wrong types before fixture imports, no argv/log/Compose/secret-file) is sound and matches the proven `/s1656/seed.py` + stdin pattern. Local image ID vs OCI index are correctly distinguished in the receipt schema, and audit fsync + same-directory rename + no-rewrite-of-corrupt is specified. "Missing audit with gained readiness = drift, not a fresh activation" is stated. Note the ambiguity in "no docker environment assignment" (F4).

**Q4 — Can crash/retry/deactivation lose a paid role or duplicate resources?** *No unimplementable transition was found; the boundaries are enumerated.* Every boundary is named: custody create/retrieve/delete (marker+digest reconciliation, prepared-generation discriminator before a new create, uncertainty preserved), Connect create (durable payload/ToS/idempotency identity persisted before creation; zero/one/many marker-match rules; expired idempotency never authorizes a new account; foreign-identity proof before upsert), DB commit vs host receipt (inspect exact expected state, never re-enroll to fit the audit), audit phases (`preparing/active/deactivating/inactive`, completed steps only), deactivation (locked comparison, restore only enumerated fields, remove only the exact newly owned Connect row, never delete Party/auth_user, retain financial-history accounts with explicit disposition, refuse destructive cleanup on uncertain payout/refund/aggregate). Failed/uncertain payout/refund is explicitly preserved and terminal W financial disposition is a precondition of cleanup — the one state transition I would want frozen in the final candidate is the exact ordering of "refund admitted → refunded → cleaned" vs "audit pause", because the receipt's `phase` enum is the only place those meet; that is a Gate2-bind item, not an observed defect.

**Q5 — Does the frozen eight-environment/four-backend scope implement the whole accepted Gate1 without copying over F1 or changing normal money behavior?** *Substantively yes; traceability is incomplete (F5) and one required pin is undefined (F2).* All 12 targets exist at the stated pins except the four correctly-marked new files (absent, verified); F1 is *not* copied over — the fourth fixture is the accepted, already-integrated `buyer-02` (Mars `1db2ecc`, ancestor of the accepted environment candidate; `seed/seed.py:53-80`, `bin/seed:41-45`), and the spec correctly orders the seed/reset refusal *before* secret/provider/S3/container side effects; the receiver path `/s1656/seed.py` is real (read-only `./seed` mount at `compose.yaml:94-96`); the synthetic W predicate is the same suppression seam; the packaged account configuration resolves P→buyer01/N→buyer02/W→seller02 exactly (verified, not hardcoded). Missing: the two Gate1 runbooks-document targets are not dispositioned (F5), and `owner_window_id`/`owner_window_sha256` are required pins with no implementation target (F2) — both blocking under this question's own criterion. Advisory (not required): the `bin/seed` textual guard duplicate could be tested once rather than twice; suggested refactors are not mandates.

**Q6 — Are support, upgrade and live-acceptance obligations concrete and correctly separated?** *Largely yes.* Separation is explicit and verified: design vs implemented source vs future runtime proof (`...GATE2.md:106-112`), "a seed fixture, test account, health check or unanimous design review does not prove full AWS/R2 production release" (`:157`), protected run25 untouched (`03d3f30`, both pins `519b1d58`, hold `2026-09-13T23:41:11.491739Z`; hashes still match), P/N genuine 48-hour holds precede a separate W namespace/window, production trigger freeze/quiescence/reconciliation remain execution gates, and rollback is forward-only (close new admission, preserve paid rights and uncertain operations, reviewed compatible combination). The diagnosis map, support-bundle allowlist, upgrade qualification (unknown audit versions refuse without rewriting; never run an old payment binary over new authority) and the receipt/predecessor-binary preservation are concrete. Gaps: the CI evidence deficiency (F6), the unverified "123 index/check" claim, and the fact that the two named historical advisories (raw-HMAC/VC transport gap, wallet/VC limits) are preserved rather than silently dropped — which is correct, but they must stay in the final release manifest. Design approval here certifies nothing implemented: no test for any proposed command exists yet, and I confirmed the four new targets are absent from both repositories.

### SIMPLER

**Advisory only (no scope violation or material risk found).** The nearest real reduction is to fold the host helper into the wrapper — implement custody retrieval + `docker exec` inside `bin/workspace-fixture` instead of a separate `seed/workspace-host.py`, removing one file from the environment allowlist (8 → 7 targets) and one process hop. I do **not** mandate it: the private stdin boundary and the host-vs-container split are the reason Gate1/DeepSeek reversed their earlier "collapse it" position, and the container-side receiver must stay in the read-only `/s1656` mount. Things I tried to remove and could not: the W receipt envelope (needed as evidence, and the only place phases live), the phase/receipt schema (needed for crash recovery), and single-writer custody (needed to keep plaintext out of the container). The one genuinely droppable component is `owner_window_sha256` (F2) — dropping it removes a pin with no referent.

### BETTER

**A materially better approach: make the W admission authority a first-class persisted registration produced by the same private operator CLI pattern already accepted for N (Mars §8 `register-test-negative`).** Write one immutable row at window open under the existing owner lock — `owner_window_id` (UUID) + exact order/PI/charge/listing/version/authority/connection/seller/buyer IDs — and have the W predicate require a match; the receipt then references the same row.
- **Failure modes vs current:** the current design asks a webhook predicate to infer a window it cannot see (F1) and compares pins to an owner-window digest that does not exist (F2); the registration removes both, makes admission authority and evidence authority the same object, and is directly testable (off-window, duplicate, wrong-window refusals). Its own failure mode is added write-path surface in a money file — mitigated by reusing the accepted CLI/lock pattern rather than a new one.
- **Cost:** one migration + one operator CLI branch + predicate read + the listed tests — which *exceeds* the frozen 12-file allowlist and therefore requires the explicit scope extension the artifact already anticipates.
- **Rollback:** drop the table and revert the predicate branch; purchased right and financial rows are untouched, and no runtime/pin change is involved.
- If the owner instead accepts per-order purchase scope (Option (a) in F1), the materially better move is to make that acceptance an artifact with an explicit exemption test, so the residual is documented rather than implicit.
