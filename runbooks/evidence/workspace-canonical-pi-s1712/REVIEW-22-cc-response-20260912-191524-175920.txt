## 4. Answers to the six numbered questions

**Q1 — Does the named composite Order-discovery reference plus the existing published-Listing guard preserve all forged non-W optional-isolation and registered-drift retry/refusal cases?**
**Yes (not blocking).** The cheap classifier queries only Order⋈Listing on the fixed seller02/buyer01 pair + exact PI + `Listing.seller_id=seller02`; the composite `fk_s1712_registered_order_discovery` freezes `orders(id,seller,buyer,listing,PI)` (all five child columns NOT NULL → `MATCH SIMPLE` always enforces; PG17 probe confirms). Forged P/N cannot match the fixed pair; a stale same-pair *unregistered* order has no authority row → `_validate_registration` refuses; a *registered* order whose Transaction actor fields drift still matches the (frozen-tuple) classifier → authority resolves → `_purchase_binding`/`validate_order_binding` **RAISE** (`WorkspaceTestAuthorityConflict`/`OrderMoneyConflict`, wrapped to `WorkspaceTestAuthorityUnavailable` → 500/no effects), never returning terminal False. Zero optional-W lookup occurs on non-W events. Verified against real helpers at `e621c760`.

**Q2 — Are the RI enforcement / readiness / catalog / lock proofs sufficient and precise?**
**Yes as design (not blocking).** RI semantics are proven for the exact tuple by the 22-case PG17 probe; the named-object fresh/repeat preflight + collision refusal is precisely specified (verify canonical def, column order, validity/nondeferrability, RESTRICT/MATCH SIMPLE, index validity/readiness/immediacy, enabled RI trigger; abort — never drop/overwrite — on same-name conflict; no `ADD CONSTRAINT IF NOT EXISTS`, no exception-swallowing); DDL lock/quiescence/index qualification + money-fingerprint byte-equality are named as mandatory pre-implementation gates. **Q3 — Does terminal closure include NULL-linkage signed siblings, one-sided identity ambiguity, finite READ COMMITTED cutoff and multiple valid replay events without extra financial effects or reversed event locks?**
