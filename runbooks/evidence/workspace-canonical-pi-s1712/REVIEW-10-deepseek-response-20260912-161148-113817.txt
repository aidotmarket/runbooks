## 4. Answers to the six feared-failure questions

**Q1 — Can an old/other-window W order, P/N, or altered purchase gain signed refund admission?** **No, by construction.** Stage A persists the *complete* fixed-pair order-UUID baseline under `LOCK TABLE orders IN SHARE MODE NOWAIT` (`GATE2.md:81`); Stage B recomputes the delta from that persisted baseline, requires every baseline ID to still exist, and requires the entire new delta to contain **exactly one** paid order with a unique canonical capture and no unregistered refund (`:83`); admission is then the immutable `workspace_refund_test_authorities` row (`order_id` PK, unique `window_id`/`transaction_id`/`payment_id`/`payment_intent_id`/`charge_id`, fixed actors, publication/version/authority/connection bindings, RESTRICT FKs, immutable trigger) located by provider IDs and re-compared against all immutable bindings and canonical hashes (`:75-79,:89`). An old same-pair order is inside the baseline; another window's order has no row; P/N uses a different seller and/or `legacy_serial_id` delivery authority; an altered binding changes the hashes and refuses. A closed/recovery window “retains authority only for its originally registered charge/order … cannot bind a second order.” Signature/scope/dedup genuinely precede the seam (`webhooks.py:476-576`), and the lock chain is existing-rows-only (verified `lock_order_money_sync` would INSERT, hence its prohibition). The residual is L1 (unregistered/terminal suppression ordering). This closes predecessor F1/GLM-HIGH#1.

**Q2 — Can public purchase, duplicate binder or reset destroy protected history or defeat exact cardinality?** **Concurrency/cardinality: no. Reset: yes for `SurgicalResetService`, no — and that is the gap — for the sibling teardown path (M1).** PG17 `SHARE` genuinely conflicts with `ROW EXCLUSIVE`, so an active order writer fails fast (`window_busy`) and a later one cannot change cardinality before commit; the design correctly disclaims flock-serializing public buyers and requires real two-session tests measuring the actual bounds. Because the canonical HTTP path permits `created/unpaid` and is not a concurrency exclusion (verified `checkout.py:97-111,204-215`), the table lock — not a row lock or READ COMMITTED — is the right tool. Extra orders are preserved/reconciled, never filtered or deleted. For the reset endpoint the four-identity refusal is unconditional, correctly placed (before `_execute`, covering dry-run/apply and object ops), and the obsolete advisory-lock/strict-destructive branch is removed; unrelated targets keep the existing rollback-and-continue behavior. **But** `ap/e2e/teardown.py` can still destroy the same four identities and their protected collections (M1).

**Q3 — Can activation/recovery overwrite a generation/Party or duplicate provider resources?** **No, as designed.** No DELETE/PATCH/upsert anywhere (create-once; authenticated-404 required before first creation; durable pre-POST generation record; conflict/uncertain reconciles by exact scope/name/marker/digest/UUID/version; timeout/403/empty ≠ absence; drift refuses and preserves; reuse only on exact retained-generation agreement). The custody preimage and provider marker grammar are now frozen and I independently reproduced the golden digest; connect marker/idempotency key are exactly derived from the retained original provider operation; account creation uses complete pagination with 0/1/many marker rules, and expired/uncertain idempotency never authorizes a fresh account; foreign-Party proof precedes projection (the reassigning upsert is forbidden); readiness restoration is typed and `User.updated_at` is correctly not fabricated. Residuals: exact field types re-verified only via retained evidence (coverage), and M1’s teardown path can delete the identity rows this whole protocol protects.

**Q4 — Can caller/bypass/artifact/image substitution gain authority or leak a Workspace credential?** **No, under the honestly stated trusted-private-operator boundary.** The design explicitly refuses to claim that a hash/actor/UID/flock authenticates a malicious operator, that mounted artifacts are a signature, or that the backend can measure its own image; it splits the pins (`backend_local_image_id` = running container `.Image` = `docker image inspect .Id`, plus the independent `ai.market.s1656.backend-sha` source label — verified `compose.yaml:5`), excludes OCI index/manifest digests from pins, and requires direct container re-discovery. Every mutation enters the `check-settlement --lock` → unchanged `--guard seed` path with exits 1/2 both refusing before the first write, and `workspace-fixture` being outside the guarded-name set means the inner guard is genuinely required (verified). stdin is one bounded UTF-8 object with duplicate-key/trailing/unknown-key/type rejection before fixture imports, only the nonsecret `PYTHONPATH=/app` exception, a read-only `/s1656` mount and append-only owner directories, and a real child-boundary canary scoped to the Workspace credential (not a false whole-application secret-free claim). Real ASGI regression classes are required so the new disjunct cannot perturb S1656/S1681/production-shaped traffic. **UNVERIFIED:** none of this was executed; no image inspected.

**Q5 — Are lifecycle transitions, immutable schema/readiness, locks and implementation files concrete and complete?** **Substantively yes, with M1 as the completeness gap.** The window state machine, immutability triggers, one-nonclosed-window index, distinct receipt kinds, commit/receipt-loss recovery, retained custody, default seed/reset/up preservation guard, and readiness assertions are concrete and named; I confirmed the migration parent is a single head, that the readiness/lock/eligibility interfaces match the spec verbatim, and that the new files are absent (design-only). Gaps: the identity guard is not applied to the second destructive backend path in the same router (M1); the pre-registration-refund disposition text is imprecise (L1); `ResetRefusal` needs a category carrier (N1).

### SIMPLER

**Simplest concrete alternative that preserves every requirement and invariant:** implement the four-identity refusal as **one shared predicate** (e.g. `is_protected_workspace_fixture(uuid)` with normalization + the four fixed constants) consumed by **both** `SurgicalResetService.reset` and `TeardownService.teardown` (plus their tests).

- **What it removes:** the M1 gap itself, and the duplication of the identity set across call sites. Quantitatively it adds *zero* new tables, routes, mounts or schemas; it is one small helper + **two** call sites + two test blocks (four identities × dry-run/apply × zero-delete/zero-object-call assertions). It removes any need for a second, divergent protected-target list.
- Things I tried to remove and could not: the second table (`workspace_test_windows` + `workspace_refund_test_authorities`) — folding them re-creates the predecessor’s purchase-scope admission defect; the persisted **baseline** — removing it makes “exactly one window order” unprovable since the webhook deliberately cannot trust a host snapshot; the `LOCK TABLE orders … SHARE NOWAIT` — removing it leaves the phantom-insert hole the design itself identifies; **retained custody** — the destructive alternative is the rejected HIGH; the owner/runtime artifacts — removing them re-creates predecessor F2. None of these is droppable; no scope violation is evidenced, so simplification here is advisory except M1.

### BETTER

**One materially better structure: make protection of the four fixture identities a database-level invariant rather than a per-service code check.** Add a reviewed migration installing a `BEFORE DELETE` trigger (on `users`, and on the protected order/transaction/device collections, or via a guard function called from those tables) that raises for the four fixed UUIDs regardless of which code path issues the `DELETE`.

- **Failure modes vs the current design:** the current design must enumerate every destructive path (and already missed one, M1) and silently fails open for any future path; the trigger fails closed for **every** path — reset, teardown, ad-hoc SQL, future callers — which is exactly the invariant the design claims at `:99`. Its own new failure modes: the refusal surfaces as a database error rather than a categorized `ResetRefusal` (so keep the application-level check in front of it for the audit category/clear message, using the DB trigger as a backstop); it must ship in a migration and be verifiable by tests; and it **cannot** cover the environment lifecycle `bin/reset` (`docker compose down --volumes` drops the volume, bypassing all triggers), which the design already treats as a separately authorized owner lifecycle.
- **Cost:** one migration + trigger/guard function + focused PostgreSQL tests (four identities, unrelated target, dry-run/apply). **Rollback:** a separately reviewed migration dropping the trigger; paid authority/history rows and financial state are untouched (no product code change), and the archival-reset path remains explicitly out of scope.
- **Comparison:** the current application-level-only approach is cheaper to write but requires the design to keep an accurate, exhaustive inventory of destructive paths — which R3 has already shown it does not yet have (M1). A mixed approach (app-level for category/audit, DB-level backstop for the invariant) is strictly stronger at a bounded cost. I record this as advisory; only M1 is a mandate, because only M1 is supported by concrete evidence of an actual unaddressed destructive path.
