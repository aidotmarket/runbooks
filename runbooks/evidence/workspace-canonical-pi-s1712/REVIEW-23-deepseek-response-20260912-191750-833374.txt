## 4. ANSWERS

**Q1 — Does the named composite Order discovery reference plus the published-Listing guard preserve forged non-W optional isolation and registered drift retry/refusal?** Yes, at design level. The classifier is narrowed to Order+Listing, so a registered charge with mutated `Transaction` fields no longer returns terminal `False`; after registration resolution `lock_existing_workspace_money_sync` + `_validate_registration`/`_purchase_binding` compare all six mutable fields, and every conflict is wrapped as `WorkspaceTestAuthorityUnavailable` → durable failed 500, same-event convergence after restoration. The forged-N case still rejects on the Listing-owner discriminator with zero optional W lookups. The composite FK freezes the Order tuple and the existing publication guards freeze the published Listing. Verified against real e621 source; execution remains Gate3.

**Q2 — Are RI enforcement/readiness/catalog/lock proofs sufficient and precise?** Yes for design. Required catalog facts are named (column order, `convalidated`, `condeferrable/deferred=false`, `MATCH SIMPLE`, RESTRICT actions, internal RI triggers normalized via constraint/relation identity, `indisvalid/indisready`), refusal on any single missing/disabled/misbound invariant, the `ACCESS EXCLUSIVE` orders lock and maintenance-window quiescence, and the fingerprint byte-equality gate. The 22-case probe is correctly labelled native semantics only — it is not W qualification, and the artifact says so.

**Q3 — Does terminal closure include NULL-linkage signed siblings, one-sided identity ambiguity, the finite READ COMMITTED cutoff, and multiple valid replays without extra effects or reversed locks?** Yes, explicitly: OR-inclusion over linkage columns **and** signed `payload_json.data.object.payment_intent`/`.id`, so NULL-linkage signed siblings cannot disappear; contradictory/malformed pairs refuse; three-field conjunction; 4096+sentinel under READ COMMITTED; only one applied Refund may account for the amount; replay IDs cannot add effects; no event lock after money locks.

**Q4 — Are the eight newly reachable failure dispositions scope-safe, preserving node20's `paid_at`/`transaction_events` assertions and all 15 original identities without six-baseline expansion?** Yes. All 8 rows preserve business outcomes, prohibit stubs/shortcuts, and are confined to the three named modules; node20 keeps both raw SQL assertions (verified in `tests/test_webhook_audit.py:661–665`) and the corrected diagnosis (missing stored `transaction_id` / reverse-lookup fixture) is source-grounded; the 15 identities are reproduced and explicitly not added to the six inherited exceptions. Only the two refund-inline rows *replace* obsolete inline assertions with stronger persisted-outcome assertions, and the artifact requires actual PostgreSQL for those, not mocks.

**Q5 — Does full lifecycle/custody/cleanup/default-canonical/legacy/mixed-synthetic/route/monitor design remain coherent?** Yes. No-DELETE custody with `inactive_with_retained_custody`/`deactivation_incomplete`, unconditional four-UUID refusal in both `SurgicalResetService` and `TeardownService` via a pure shared helper, split incident dispositions, one-nonclosed-window index, retained P1 `e2e_routes_over_armed` alert (observed, not suppressed), upgrade inventory. ## SIMPLER

**None found that preserves every invariant.** The candidate already removes the genuinely removable complexity (second-window no-table option, `pg_try_advisory_xact_lock`, strict destructive fixed-party branch, DELETE from custody). The one structurally removable object — the redundant 5-column `uq_s1712_order_discovery`, whose uniqueness is implied by `orders.id` — cannot go while keeping (a) zero optional-W dependency for non-W traffic (which forbids resolving traffic through the W authority table first) and (b) a declarative RESTRICT reference; the only alternative is a hand-written core `orders` trigger, which the design deliberately rejects as broader and less introspectable. I tried to remove the parent index, the closure OR-inclusion, and the auxiliary legacy-flag test; each removes a distinct invariant. Advisory: if the extra index's steady-state write cost ever matters, `CREATE UNIQUE INDEX CONCURRENTLY` + `ADD CONSTRAINT … USING INDEX` is available — the design deliberately declined the concurrent variant in favour of a transactional maintenance-window change, which is an acceptable, now-named tradeoff.

## BETTER

**None materially better found.** The two alternatives were examined: (i) a core mutation trigger on `orders` — fewer DDL objects, but not introspectable by `CATALOG_SQL`, and it weakens the very readiness/catalog proof this design relies on; (ii) an application-layer re-check only — skippable under concurrency and defeats the drift invariant. The chosen composite FK is cheaper to verify, cannot be bypassed by a mis-authored branch, and its failure modes are strictly bounded (a one-time `ACCESS EXCLUSIVE` build now named in the cutover obligations, trivially satisfiable because the key is redundant, and irreversibility inherited from the migration's own downgrade refusal — see N1). Cost/rollback: the constraint is retained rather than rolled back, matching the design's forward-only rollback model; no additional financial or custody rollback surface exists. Advisory only, not mandated.
