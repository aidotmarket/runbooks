## 4. Answers to the six required questions

**Q1 — Can old/other-window/P/N/changed-purchase authority gain signed W admission, or a terminal unregistered refund be fabricated into convergence?**
No, at design level. Admission is a new immutable `workspace_refund_test_authorities` row (`order_id` PK; unique `window_id`/`transaction_id`/`payment_id`/`payment_intent_id`/`charge_id`; RESTRICT FKs; fixed actors; `spec:85`) located by provider IDs and re-compared against canonical bindings; Stage A's persisted complete baseline + "exactly one new paid order" delta (`spec:81‑83`) exclude old/other orders, and a closed/recovery window "cannot bind a second order" (`spec:89`). The signature now matches the S1681 peer shape and is called at the real seam (`webhooks.py:552‑578`); the predicate locks existing rows only and does not call the inserting helper (verified it inserts). The two incident classes are now dispositioned distinctly (`spec:97`, `spec:103`-section): a pre-registration `charge.refunded` is terminal suppression with no convergence path, whereas an extra post-registration order keeps `recovery_required_extra_order` while the originally registered refund converges. This closes DS R3-L1. **Blocking condition (per the spec's own rule):** none identified — but the required PostgreSQL/ASGI tests are unexecuted here.

**Q2 — Can either supported account cleanup service or concurrent purchase destroy history/cardinality?**
No for the two cleanup services — this is R4's central fix. `SurgicalResetService.reset` and `TeardownService.teardown` both get the same pure normalized four-UUID refusal, `SurgicalResetService` after auth/allowlist/request/apply-review and before `_execute`/`_reset_database_rows`/object ops, `TeardownService` after `build_guard_context`+`claims/target_email` and before `validate_inventory`/`_collect_hitlist`/`_execute_deletes` (all verified against actual source), with the preceding `_catalog_snapshot` read-only (teardown.py:147). The refusal is independent of W schema/mount/pointer/audit/custody/window state, so no-linage/pre-open/closed/damaged cases are all covered, and the R2 advisory-lock/strict-destructive branch is correctly removed (a DB advisory lock never serialized host file publication). Carrier behaviour verified: reset → HTTP 400 `detail="workspace_protected_fixture"`; teardown → 202 + background task, `except TeardownRefusal` → audit `outcome="refusal"`, `reason=str(exc)`, `executed_counts={}` (guard precedes hitlist so `executed` is empty), surfaced by `GET /e2e/teardown/status/{run_id}`. **No missed supported path:** repo-wide, no other user-row deletion exists; only the two services are account-destructive. Concurrency is bounded `orders SHARE NOWAIT` + unique constraints + existing money-row locks, explicitly disclaiming that flock serializes public buyers. **Not verified:** the two-session PostgreSQL bounds (required tests, unexecuted).

## SIMPLER

**None found that preserves every requirement and invariant.** R4 *is* the simplification relative to R2/R3: one pure `is_protected_workspace_fixture(UUID)` constant-set predicate at two service entrypoints replaces the rejected per-target advisory lock + strict-destructive branch + W-lineage lookup + host-file serialization reasoning; net it adds one small module, two service edits and two teardown test files, and removes any need to reason about reset↔host-file races. Things I tried to remove and could not: the second window/registration table (removing it reopens cross-window admission); the persisted baseline (removing it makes "exactly one window order" unprovable to the webhook); `orders SHARE NOWAIT` (removing it leaves the phantom-insert hole); retained custody (the destructive alternative is the rejected R2 HIGH); the owner/runtime artifacts (removing them recreates the caller-self-assertion defect). The only micro-reduction I can name is cosmetic (dropping the `*_json`/`*_sha256` column pairing for a single canonical-text column with a generated hash) and it would weaken the "hash only the preimage bytes" rule — not recommended.

## BETTER

**One materially better approach, advisory.** Decouple synthetic-public-purchase arming from destructive-E2E-route arming: introduce a narrow, runtime-pinned synthetic-purchase enablement checked by the checkout guard, leaving `E2E_TEST_ROUTES_ENABLED` false so the destructive router is structurally absent — the shared four-UUID service guard then becomes belt-and-braces. This is exactly the alternative GLM raised at R3 (and correctly carried into `spec:259` as "advisory and not selected").
- **Failure modes vs current:** the current design necessarily imports both destructive routes and (per F1) drives the product's armed-window monitor to a permanent P1; the narrow-flag variant confines failure to purchase refusal and keeps the routes absent, at the cost of one new reviewed setting in the checkout path (the thing the spec is wary of) and the loss of the "routes are actually registered when armed" coverage unless a separate test arms them.
- **Cost:** one reviewed setting + one checkout-guard change + ASGI tests + an explicit scope amendment (it touches the public checkout guard, so it cannot be an MP improvisation — as GLM itself noted).
- **Rollback:** set the narrow flag false / remove the W disjunct; paid rights, authority rows, custody and financial rows are untouched; no migration.
- I record it as **advisory, not a mandate**: the selected design is guarded, the blast radius is TEST-only, and the owner's Q3 requirement ("no new checkoutflag", literal empty allowlists) is met by the current choice. If the owner prefers a single reviewed flag, F1's documentation fix is sufficient.
