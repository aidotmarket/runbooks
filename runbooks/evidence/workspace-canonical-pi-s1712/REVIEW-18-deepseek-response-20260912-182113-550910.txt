### SIMPLER

**None found for the checkout correction itself** — the change *is* the simplification: it deletes a false requirement (flag=false → 403 on the canonical path), deletes the claim that the E2E flag is a canonical arming control, and replaces both with the actual branch order plus an explicitly labelled auxiliary legacy test. Nothing further is removable without losing a requirement; I tried to remove (a) the auxiliary `ENABLE_CANONICAL_TX=false` test — rejected, it is the only remaining way to exercise the legacy 403 carrier; (b) the probe-limit paragraph — rejected, it is what makes the evidence honest; (c) the two-runbook edits — rejected, the operator guide is where the stale "arming" reading would otherwise persist.

For the classifier, the simplest concrete alternative that preserves every requirement is a **two-step predicate**: (1) cheap actor/PI rejection on the `Order` tuple alone (seller02 + buyer01 + payment_intent), returning False only for non-matching traffic; (2) for a matching fixed-pair charge, resolve registration — existing authority ⇒ validate; absent authority with available and compatible store ⇒ terminal suppression; unavailable/incompatible ⇒ raise. Quantified effect: it removes the join-based discriminator (4 columns), removes the "return False before authority" branch, and preserves both the forged-non-W 200 and the registered-drift non-suppression. It costs one extra query ordering constraint and the drift test in F1's verification criterion.

### BETTER

**One materially better approach: make the whole classifier decision a function of the registry, not of row shape.** Store the exact `(payment_intent, charge)` pair in the registration row (it already is: `workspace_refund_test_authorities.payment_intent_id`, `charge_id`, both UNIQUE) and drive the predicate as: lookup by provider IDs first; if exactly one row → validate immutable bindings and return the authoritative answer (raise on any mismatch); if no row → apply the cheap fixed-pair rejection; if the store is unavailable → raise for fixed-pair traffic only. Compared with F1's current failure mode, it removes the possibility that a dangling join silently converts a registered refund into terminal suppression, and it makes "unregistered 200" and "registered-with-uncertainty 500" structurally disjoint rather than ordering-dependent. Cost is a re-ordering of two reads (plus a bounded index lookup already required) and the same tests; rollback is a predicate revert with authority and financial rows untouched. Its own new failure mode — an extra read on non-W traffic if the ordering is done carelessly — is contained by gating the authority lookup behind the cheap actor/PI tuple, which the spec's Q1/W-last boundary already requires. I record this as a recommendation; only F1's precedence statement and test are mandates.
