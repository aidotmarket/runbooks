Real public checkout invokes TransactionService.initiate/create_checkout. create_checkout consumes only the returned Stripe Session id/url, stores the Session ID on Order and commits the Order/Transaction pair. ## Concrete successor design selected after Mars4675

This complete amendment supersedes the earlier provisional proposal. It remains proposed until fresh joint review. Baseline is817f7331a07d07929a67198b28a82ed9b98baa56. Choose database uniqueness, not application advisory serialization. An advisory lock would require every existing and future writer to share one hashing/key convention before money locks, including legacy and agent paths; a missed writer would evade the guarantee, and adding it after existing locks risks inversion. Native unique constraints arbitrate conflicting writes from all database clients without introducing a new application lock tier. They preserve multiple NULLs for unpaid Orders/Transactions. They do not, alone, establish cross-table identity; the existing exact reverse-pair and money-field validation remains mandatory.

### Shared helper API, transaction ownership and state table

Place bind_initial_order_payment_intent_sync(db, *, order_id, payment_intent_id, expected_transaction_id, mode) and its async run_sync adapter in order_money_service.py. mode is a closed internal enum: checkout_completion, direct_payment_completion, signed_capture_recovery. It is never user input, a setting or a bypass flag. The function returns the locked Order and optional exact linked Transaction; it does not commit, create money authority or invoke providers. The caller owns one bounded transaction and must not enter with unrelated staged writes that would be discarded. Use the existing reverse-Transaction query ordered by Transaction.id, reject cardinality greater than one, and compare Order.transaction_id exactly. Never acquire another Order after those Transaction locks.

Read all identity/money fields again under locks. Reject all differences other than the specifically permitted absent dedicated PI fields. Existing non-NULL Order PI or Transaction PI must equal the supplied PI. Nonempty metadata PI must also match. Existing Session/event/provider identity is checked at its owning validated caller; the helper cannot turn untrusted metadata into permission. No broad OR allowing an arbitrary matching field.

State decisions:
- Both equal supplied PI: no binding DML, preserve existing processing/replay policy. Any unrelated identity/money mismatch still refuses.
- Order created, both PI NULL, coherent canonical pair, validated checkout completion: atomically establish both PIs, then normal paid transition. Conflicting other-row PI uniqueness produces rollback and retryable conflict, not success.
- Order created with matching PI and Transaction NULL, coherent pair and validated completion: establish Transaction PI; do not overwrite Order identity.
- Order NULL and Transaction already populated: refuse automatic binding, even if supplied PI matches Transaction; this unexplained asymmetric history is outside the demonstrated producer defect.
- Already paid/pending_delivery Order with matching PI, linked Transaction paid/fulfilling and NULL PI, original signed capture event failed before finance, no retained W registration, no Payment/refund/payout/captured authority and no independent revocation/dispute/reconciliation: allow only signed_capture_recovery. Require actual matching stored Session, fresh provider metadata for both IDs, exact amount/currency/platform scope and original persisted signed event/payload. Complete Transaction PI, then capture in the same transaction. No status or paid_at rewrite. If a pre-existing empty OrderMoneyState is present, refuse this recovery pending explicit adjudication; absence is required for this narrow case.
- Both NULL in already-paid history, any conflicting non-NULL PI, unknown/ambiguous authority, captured/refunded/settled/disputed/revoked state, or retained W registration with missing PI: refuse. No deletion, automatic backfill or reactivation.
- Legitimate legacy Order without any reverse Transaction: normal checkout completion may set compatible Order PI only; signed capture retains existing legacy rules. No creation of a Transaction.

These rules explicitly recover the demonstrated state without redelivering the already-completed checkout event. The original failed payment_intent.succeeded ID is retried directly after deployment; the capture branch performs the narrow initial completion. Same completed-checkout dedup remains completed and is not reopened. Original event payload/signature mismatch still refuses. Any newly bound PI and new finance roll back together on capture failure; an uncertain commit is reconciled by original-ID replay and exact stored finance, never a second transaction or provider purchase.

### Exact concurrency and deadline behavior

Use event→Order→Transaction→money authority→Payment→sorted Refund→agent key. PI unique-index checks happen during the permitted paired writes; they are not a new advisory-lock tier. Each operation modifies only its one validated Order/Transaction pair. A same-PI competing Order write cannot both commit because the Order unique constraint arbitrates it; competing Transaction PI writes cannot both commit because the Transaction unique constraint arbitrates it. The loser must roll back; it cannot retain a one-sided binding. A raw cross-table mismatch is not prevented by uniqueness alone, and continues to be refused by strict pair validation. No assertion that unrelated raw SQL gains valid ownership merely by satisfying unique constraints.

The helper transaction sets lock_timeout250ms and statement_timeout2000ms; every statement uses remaining time from a five-second monotonic deadline, and async callers also have a five-second cancellation boundary followed by rollback. Sync timeout/cancellation must propagate as retryable failure after transaction rollback. SQLSTATE23505 for these named PI constraints is a binding conflict; 55P03/40P01/57014 and connection/commit uncertainty are not success. Do not swallow other integrity failures. Repeated exact equal state does no DML and cannot recreate paid events.

Capture provider preflight has at most10seconds per read and20seconds total, outside event/money locks. Cancel/timeout retains the original failed event and does no binding DML. No provider write is introduced. Checkout completion uses its existing authenticated signed event facts and does not add network reads inside mark_paid. Existing agent external creation receives no new binding/event/money lock before its provider call; database uniqueness is checked when persisting its returned PI. Full original provider-unknown/retry/cutover obligations are not waived by this amendment.

### Direct-mode state clarification and actual caller transaction ownership

The direct_payment_completion mode has only two allowed cases: (1) an already equal, coherent pair is a no-op before existing direct method semantics; (2) Order is created with its dedicated PI already equal to the supplied PI, the exact reverse Transaction is checkout_pending with NULL dedicated PI, and there is no existing money/Payment/refund/payout/registration history, revocation, dispute or reconciliation. In case2 it may complete Transaction PI inside the caller-owned transaction and then follow the existing direct method's normal transition. Both-NULL direct calls refuse: an internal method argument alone cannot establish the Order's PI ownership. Paid-history NULL completion is exclusively signed_capture_recovery, never direct mode or checkout dedup repair. No other direct state is allowed. Tests assert the complete allowed/refused table using actual service calls.

Actual webhooks source510-545 keeps the synchronous dedup claim's event lock through dispatch. The normal checkout path reads Order/Transaction without money row locks in _handle_checkout_completed, then calls an independent async OrderService session at683. Therefore this amendment must NOT perform synchronous PI binding or acquire Order/Transaction locks before entering that async session. The async mark_paid owns Order→Transaction locks, initial binding and paid transition and commits together under its existing auto_commit=True behavior. Its helper cannot read or lock the event row owned by the synchronous caller. After the async session commits/releases its locks, the synchronous caller may perform its existing metadata/paid-at/event work. Crash after async commit but before event completion must be tested: failed original event replay observes a coherent bound pair and does not duplicate paid transitions or capture.

For the existing inline synthetic branch, no async mark_paid is entered (marked_paid_inline=True). Its synchronous session owns event→Order→Transaction, binds and changes status/events in that one transaction; no second session can re-enter money locks. Legacy mock checkout calls async mark_paid(auto_commit=False) in its existing request transaction; the helper must neither commit nor discard caller writes. Any validation failure rolls back the full request through the existing endpoint boundary.

The existing _repair_canonical_payment starts with a Transaction FOR UPDATE. Since this branch now participates in the explicitly reviewed checkout lock protocol, change it to acquire and verify Order first, then its exact reverse Transaction, without taking any new event lock. Preserve its current paid_at/event dedup purpose; it must not bind missing dedicated PI columns or reopen a completed checkout event. It is not the recovery route for the demonstrated capture defect. Paid-history initial PI completion remains owned by the original failed signed capture branch only.

The PI-success webhook writes and commits its retryable finance_pending checkpoint before the independent async BillingService call. Fresh authoritative provider reads occur outside event/money locks. The async capture session then owns event→Order→Transaction and initial completion/capture together. The completed checkout event is not locked/reopened. The failed capture ID and exact original payload are retained; unrelated failed events cannot acquire ownership. A completed capture replay must not re-enter paid transitions.
