## SIMPLER

**None found that preserves the invariants — and I tried the obvious two.** (a) *Drop the Transaction filter entirely and rely on the Order/Listing guards* is the candidate's own direction, but it removes the `:356` expectation without replacing it, i.e. it trades a suppression bug for an unenforced-drift bug (F1); a preserving variant is a two-step predicate — cheap actor/PI rejection on the Order tuple alone, then registration resolution, with drift at any point raising rather than returning False. That *removes* the join filter (4 columns + its early `return False`) and adds one ordering constraint. (b) *Drop the composite FK and keep only the existing publication guards* preserves nothing for the Order tuple (`orders.seller_id/buyer_id/listing_id/stripe_payment_intent_id` have no immutability trigger) and reopens the R4/Q1 defect. The genuinely removable item is the redundant `uq_s1712_order_discovery` **if** the FK were re-pointed at `orders.id` with an immutability trigger on the four remaining columns — but that swaps a declarative object for a hand-written trigger, which the candidate deliberately declines, so I record it as advisory only. No scope-violation evidence supports mandating it.

## BETTER

**One materially better structure, and it is small: make the registration lookup authoritative *before* any shape filtering, and let the FK protect only what it can actually protect.** Concretely: (1) resolve `workspace_refund_test_authorities` by `payment_intent_id`/`charge_id` first, using the Order tuple alone (never a Transaction-bearing join); (2) if exactly one row → validate every retained binding and **raise** on any mismatch (this is where the Transaction-field drift at `:356` is enforced, by construction rather than by hope); (3) if no row → apply cheap fixed-pair/Listing-owner rejection and return False; (4) if the store is unavailable → raise for fixed-pair traffic only. **Failure modes vs the candidate:** current — a registered refund either vanishes into terminal suppression (keep the join) or is admitted with unexamined drift (drop the join); better — `unregistered-200` and `registered-with-uncertainty-500` become structurally disjoint rather than ordering-dependent, which is exactly the split the candidate's own `:310`/`:343` text asserts but `:331` cannot guarantee. **Cost:** a reordering of two reads plus the receipt comparison already required, and the F1 test matrix; no new table, no new lock, no new route. **Rollback:** revert the predicate branch; authority rows, financial rows, and custody are untouched. It also subsumes F2's severity (the FK becomes defense-in-depth rather than the sole guarantee) and lets F3 be scoped to the one constraint that remains.
