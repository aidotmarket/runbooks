## 2. Findings (highest severity first)

### L1 — LOW — The `uq_s1712_order_discovery` UNIQUE index is a non-concurrent DDL on the core `orders` table; its build-time `ACCESS EXCLUSIVE` lock and its effect on the money-readiness fingerprint are not addressed in the release/quiescence sequence.

- **Evidence.** Spec request:619 mandates, *in the existing W migration*, "a named nondeferrable UNIQUE constraint on `orders(id,seller_id,buyer_id,listing_id,stripe_payment_intent_id)`, named `uq_s1712_order_discovery`" plus a composite FK. The embedded migration `alembic/versions/20260912_002_workspace_test_authority.py` (request:3473-3575) applies its DDL via `op.execute(statement)` (request:3574) — i.e. a plain, non-`CONCURRENTLY` index build. This is the first time the W design touches the `public.orders` relation schema; prior accepted rounds (R3/R4) confined W to new tables only.
- **Observed vs expected.** Observed: `ALTER TABLE orders ADD CONSTRAINT … UNIQUE` / `CREATE UNIQUE INDEX` takes `ACCESS EXCLUSIVE` and blocks all `orders` writes for the duration of the build; the Alembic chain (`down_revision=s1714_order_money_v1`, request:3479) is not environment-gated, so the DDL runs wherever `alembic upgrade head` runs, including production. The "Release and upgrade sequence" (request:520-528) and the quiescence runbook reference do not mention the index-build lock. Expected: the cutover sequence names this DDL as a locking operation (maintenance window or `CREATE UNIQUE INDEX CONCURRENTLY` + separate `ADD CONSTRAINT … USING INDEX`), and the mandated "money readiness fingerprint unchanged" proof (request:653) is bound as a build blocker.
- **Reproduction.** Static evidence only (design doc; DDL not yet written or executed).
- **Impact.** Low and bounded: (a) the UNIQUE is a superset of the `orders.id` PK, so it is *always satisfiable* and can never block a normal insert/update on correctness grounds — I verified `orders` carries `seller_id`, `buyer_id`, `listing_id` (checkout.py `create_order(buyer_id=…, seller_id=listing["seller_id"], listing_id=…)`, request:1703-1706) and `stripe_payment_intent_id` (order-money lock `order.stripe_payment_intent_id`, request:2289); (b) production cutover is a separately-gated procedure. The residual risk is purely operational (migration-time availability) plus the readiness-fingerprint perturbation the spec already flags.
- **Smallest required outcome.** Add two lines to the build/cutover obligations: (1) the `orders` UNIQUE/FK DDL is `ACCESS EXCLUSIVE`-locking and must run in a maintenance window or concurrently; (2) the accepted money-readiness fingerprint must be proven byte-unchanged by the `s1712`-named parent key before Gate3 (request:653 already states the latter; make it an explicit gate).
- **Verification criterion.** The cutover runbook enumerates the `orders` DDL as a locking step with its mitigation, and a readiness test asserts the money-path fingerprint is identical with and without the new constraint/index.

### L2 — LOW — Classifier stability for a registered charge rests on **two** immutability guarantees; only one (the composite FK) is introduced here, and the other (published-Listing seller immutability) is an existing-source claim not verifiable in this packet.

- **Evidence.** Spec request:621: "The existing publication guard prevents that published Listing seller from changing; the registration's Listing FK preserves its referenced row. Both guarantees are load-bearing and must be verified from actual catalog/source plus SQL mutation tests. Do not infer Order immutability from the publication guard alone." The cheap classifier (request:617, :629) discriminates on `Listing.seller_id == seller02`; the composite FK freezes the order's `listing_id` *reference* but not the referenced listing's own `seller_id`. The SellerListingPublication immutability guard source is not embedded in this packet.
- **Observed vs expected.** Observed: if a published Workspace listing's `seller_id` could be mutated after registration, a registered order's listing-owner discriminator could flip, reopening the misclassification the composite FK otherwise closes. Expected: the published-listing seller immutability is verified from actual catalog/source and a SQL mutation test, as the spec itself mandates.
- **Reproduction.** Static evidence only (existing-source guard not embedded → UNVERIFIED here).
- **Impact.** Low — the spec correctly identifies the dependency and refuses to infer it; this is a build-verification obligation, not a design gap. Flagged because it is load-bearing and not closed by the new FK alone.
- **Smallest required outcome.** Retain the spec's dual-guarantee mandate (request:621, :641, :653) as a build blocker: a SQL test must prove a published registered listing's seller cannot change, alongside the order-tuple FK tests.
- **Verification criterion.** A PostgreSQL test attempts to change `listings.seller_id` (and delete the listing) for the genuinely published registered listing and the existing guard/FK refuses — "Do not rely on a generic seller01 listing without publication" (request:641).

## 4. Answers to the numbered questions

**Q1 — Does the named composite Order-discovery reference plus the existing published-Listing guard preserve all forged non-W optional-isolation and registered-drift retry/refusal cases?**
Yes, by design, with two build-verification dependencies. The cheap classifier is reduced to `Orders⋈Listings` on the fixed seller02/buyer01 pair + exact PI + `Listing.seller_id=seller02` (request:617, :629) and explicitly *must not* filter on the mutable Transaction fields (`seller_id,buyer_id,api_key_id,buyer_type,origin,surface`) before authority lookup — those move to post-resolution comparison that **raises** `WorkspaceTestAuthorityUnavailable` on mismatch (request:617, :631, :642). The composite FK freezes the order's `(id,seller,buyer,listing,PI)` so a registered order cannot drift out of that classifier (request:619-621). Forged-N isolation holds: its listing is seller01-owned, so the listing-owner discriminator rejects it with zero optional-W schema/mount lookups and preserves HTTP 200 (request:629, :643). This is exactly DeepSeek c6bae F1's required outcome (request:9698-9700). Dependencies: L1 (money-fingerprint-unchanged proof) and L2 (published-listing seller immutability must be proven from source, not inferred).

**Q2 — Are the actual RI enforcement / readiness / catalog / lock proofs sufficient and precise?**
Sufficient as a design; precise at the catalog level. Readiness must recognize the parent UNIQUE + supporting index (`indisvalid/indisready`, column order, immediate enforcement) and the composite FK (`convalidated`, `condeferrable=false`, MATCH SIMPLE, RESTRICT actions, referenced/referencing internal RI triggers with enabled state), normalizing OIDs/trigger names through constraint/relation identity (request:653), plus the existing W registration/publication guards. Single missing/disabled/misbound invariant must refuse readiness (request:635, :655). The StageB lock discipline is preserved — `orders SHARE NOWAIT` before row locks, registration insert acquires the referenced-key RI check inside the same bounded txn, `lock_timeout=250ms`/`statement/idle=2s`/host 5s, no `orders` UPDATE, no table-lock upgrade, no creating money helper, no provider IO (request:623). Two build mandates: prove the money-readiness fingerprint is unchanged by the `s1712` parent key (request:653 / L1), and prove published-listing seller immutability by SQL mutation test (request:641 / L2).

**Q3 — Does terminal closure include NULL-linkage signed siblings, one-sided identity ambiguity, finite READ COMMITTED cutoff, and multiple valid replay events without extra financial effects or reversed event locks?**
Yes. Closure enumerates `charge.refunded` events by explicit OR inclusion (normal linkage columns **OR** `signature_valid=true` AND `payload_json.data.object.payment_intent|.id` match), with the payload relation required even when all linkage columns are NULL — so a pre-admission signed failure with NULL linkage cannot disappear; a contradictory/one-sided pair is ambiguous and **refuses** (request:657). The final observation is a read-only, `stripe_event_id`-sorted, 4096+sentinel-bounded READ COMMITTED statement that takes no event-row lock after money/order locks (preserving event→money lock order); exactly one applied Refund must account for the amount; multiple valid replay IDs map to that one Refund with no additional effect; the representative `refund_event_id` is the COLLATE "C"-smallest, frozen on retry (request:659). The READ COMMITTED boundary is explicitly finite — a late/uncommitted event is a late delivery that still converges on the immutable closed receipt, with no timeless-exhaustiveness claim and no reverse-order event locks (request:661). The B13/B14 "enumerate all refund/event records; refuse pending/ambiguous" requirement is made explicit and testable (request:648).

**Q4 — Are the exact three compatibility-test changes scope-safe, preserving assertions and all 15 original failure identities without six-baseline expansion?**
Yes — verified mechanically. The patch is 11+1+1 = 13 line-edits (request:800-931). The 11 `(event_id,)`→`(event_id,None)` edits in `test_webhook_audit.py` (fixing its 13 `IndexError` nodes — fewer edits than nodes because shared helpers contribute to several cases, request:678) and the 1 `_Result` dedup-sentinel edit in `test_e2e_stripe_isolation.py` together add a second column modeling "no prior `error_message`" (so not `fulfillment_pending`) — the only correct fix for a dedup RETURNING that is now 2-column (the 14 `IndexError`/`both_dedup_row_1:true` nodes, request:1088-1170). The single SQL edit updates a stale expected string to the already-accepted implementation SQL (adds `payload_json,signature_valid`, `cast(:signed_payload as jsonb)`, and the applied-refund-protection conflict-WHERE) and reconstructs byte-for-byte (whitespace-normalized) to the captured failure at request:1084. No handler/mapping/`_result` logic, suppression reason, HTTP code, commit/rollback, retry, or refund assertion is touched (request:678-684). All 15 failures reproduce identically on `c3a62af8` and the MP247 head — they are stale doubles, explicitly **not** added to the six accepted inherited exceptions (request:688-690), and no `xfail/skip/deselection` is authorized (request:694). Scope-safe.

**Q5 — Does the full lifecycle / custody / cleanup / default-canonical / legacy / mixed-synthetic / route / monitor design remain coherent?**

### SIMPLER

**None found that preserves every invariant.** The binding constraint is the "zero optional-W dependency for non-W / forged-N traffic": the cheap classifier must decide W-vs-not by reading only `orders`/`listings` (never the W authority table or mount) *before* authority lookup. That forbids resolving the order via the immutable registration row (which is the obvious way to avoid core-table DDL), because reading it is itself an optional-W lookup. Given that, the order's own discovery columns must be frozen, and the only two options are (a) the validated composite FK (chosen) or (b) a hand-written core-mutation trigger on `orders` — which the spec explicitly rejects as broader/less-verifiable (request:625). The composite FK is therefore already the minimal viable core-schema touch; it removes the R3-era advisory-lock and destructive-branch complexity entirely. What I tried to remove — the `orders` UNIQUE/FK — cannot go without reintroducing the DeepSeek-F1 drift hole or violating zero-optional-dependency.

### BETTER

**None materially better found.** A declarative, `convalidated`, catalog-checkable composite FK has strictly better failure modes than the alternatives: versus a PL/pgSQL trigger it is introspectable (readiness can assert `convalidated/condeferrable/confupdtype/confdeltype`), cannot be silently bypassed by a mis-authored branch, and imposes no function-maintenance surface; versus an application-layer re-check it cannot be skipped under concurrency. Its one cost over "do nothing to core" is the migration-time `ACCESS EXCLUSIVE` index build (L1), which is mitigable with `CONCURRENTLY` and is a one-time operation with trivial rollback (`DROP CONSTRAINT/INDEX`, guarded by the retained-authority `downgrade()` refusal at request:3578-3579, which must be reconciled for any intentional teardown). The design's own instruction — return for review if implementation needs anything beyond this exact schema amendment (request:625) — is the correct guardrail.
