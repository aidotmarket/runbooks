## Actual device S3 credential refresh graph

1. HTTP `POST /orders/{id}/download/refresh` uses `OrderService.refresh_device_s3_delivery` (order_service.py1415). It locks the order, calls `_authorize_download_access`, checks applicable S3 delivery type, purchased version and stored identity even when credentials expired. This layer already admits legitimate delivered partials through `_has_delivered_access`.
2. The legacy HTTP `POST /orders/{id}/refresh` independently rejects partial at orders.py850. Its query835 lacks prior-delivery evidence and transaction ID. Its existing valid-URL short circuit869–885 is not refresh proof and must not disclose to an independently closed partial. It later invokes the same real FulfillmentService at896. `success:false` or `already_pending` is returned unchanged; HTTP200 alone proves nothing.
3. `FulfillmentService.request_fulfillment(..., is_refresh=True)` locks order161, but its SELECT lacks the evidence/closed-access fields; allowed_states197 excludes partial. Preserve non-refresh191–200 semantics and Workspace178–184 routing. Do not make partial a universally fulfillable state.
4. S3 refresh228–250 freezes `pending_refresh_request_id`, `pending_refresh_generation` and `pending_refresh_device_id` in delivery_config, using the current credential_generation and seller device. Existing pending refresh is deduplicated. `_send_fulfillment_request`550 and `_queue_fulfillment`601 send `vai.fulfillment.deliver` with the frozen refresh request ID and device; dedup is order plus refresh attempt. Both online/offline paths retain the tuple.
5. `trust_outbound_writer.py` enqueues by device/dedup/pending-message status, then sends by message expiry, subscription and capacity. Its `delivered`/`pending` comparisons concern outbound transport, not orders. ACK updates pending_fulfillments only when pending/sent_to_device; it does not grant order access. No partial-status gate was found here and no edit is indicated.
6. Device completion for this path is **`vai.fulfillment.response`**, not `vai.fulfillment.complete`. `trust_websocket._handle_fulfillment_action`1288 parses actual nested/flat frames and retains raw access URL. It locks and binds order, listing and seller1304–1312. Delivered/completed replay1317 is allowed only without a matching pending tuple. Its allowed-order-state gate1325 rejects partial even with a perfect request/device/generation match. This must be corrected narrowly with current authorization; no weakened device/listing binding or unauthenticated request-ID propagation.
7. `FulfillmentService.handle_fulfillment_response`303 locks full order; refreshing310–314 requires request ID, device ID, and pending generation equal current generation. Matching refresh already rechecks `_authorize_download_access`323–327. A failed device response returns `DELIVERY_REFRESH_FAILED`. It validates purchased version and immutable S3 identity369–381. For S3 refresh389–392 it updates only delivery_config, increments generation, removes pending tuple, completes pending fulfillment and commits. It preserves partial order status, delivery history and financial rows. This path can support partial once the upstream gates admit it; it is not necessary to reimplement it.
8. Fresh `issue_download_token`1190 and `redeem_download_token`1381 both use current `_authorize_download_access`, purchased version and stored identity; redemption also enforces token reservation and generation. Old generation must fail after refresh; fresh token must redeem to the exact raw refreshed URL. Scoped credentials use `_issue_s3_scoped_delivery`424 and its purchased-version check; no delivered/completed-only status gate remains there.

## Other fulfillment actions: no indiscriminate widening

- `vai.fulfillment.metadata` -> listener.handle_metadata94. Order ownership is locked and status146 permits only pending_delivery/paid/in_escrow before creating a new transfer. - `vai.fulfillment.chunk` -> validate_authorization_tuple and handle_chunk. Stored transfer/order/listing/seller equality binds chunks. No delivered/completed refresh gate is involved.
- `vai.fulfillment.complete` -> listener.handle_complete288. It locks transfer then `_lock_owned_order`311. That helper527 only checks order/listing/seller ownership, **not order status, revoked flag, closed transaction or prior delivery**. Completion then issues a token406 and unconditionally UPDATEs status='delivered'416–431. A transfer started before partial/full refund may complete afterward and attempt to overwrite refund state. Existing PostgreSQL triggers may refuse specific financial transitions, but this source has no intentional current-access refusal; real migrated-PG race proof is required. Do not claim a static trigger assumption closes it. Preserve first delivery, financial status and lock ordering without inventing partial streaming refresh.
- Complete replay315 returns existing token ID when transfer already COMPLETE; this is not the S3 refresh tuple and must not be used as proof of refreshed credentials.
- `vai.fulfillment.error` -> listener.handle_error. `_lock_owned_order` checks ownership; UPDATE order delivery_failed511 is already conditional on initial states, protecting partial status from this particular write. - Staged download endpoint fulfillment_download.py54–102 calls listener.consume_download_token576. ## When it breaks

When a partially refunded buyer cannot download, first bind order buyer/listing/purchased version and current transaction reverse link without printing secrets or signed URLs. Establish actual prior delivery separately from current access restrictions. Identify the precise surface: access info/reference, raw token, device-S3 refresh, agent broker, or staged token. For S3, inspect only presence/hash-safe identifiers of pending request/device/generation and pending fulfillment/outbound states; match them to the actual response action. An outbound ACK or HTTP200 is not finalization. Verify the post-response credential generation and financial status, then normal buyer token issue/redeem in the approved test environment.
